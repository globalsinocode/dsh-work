# main 流程加固六批次设计

## 1. 目标与基线

本设计把 `docs/development/main-flow-breakpoint-review-2026-10-21.md` 中确认的 21 个流程断点拆成 6 个可以独立实现、验证、发布和回滚的批次。每个批次拥有独立实施计划、分支、测试证据和发布结论，禁止把六批次合成一次大改后再统一验收。

- 审阅基线：`main` 提交 `8277d76b0f470585421fb328ab45a6e53e26c2f0`，Release `2026.10.20-05`。
- 设计日期：2026-10-21。
- 当前迁移基线：`0083_file_extraction_attachments.sql`。
- 执行边界：所有 Agent 执行继续走 Product Session / Task / Run / Attempt → Runtime Adapter → DSH；任何批次都不得增加第二套 Agent Loop、直接模型调用或生产 Mock 回退。
- 数据事实：PostgreSQL 是业务事实来源；浏览器 Store、SSE 本地快照和 DSH 日志只作为投影或执行轨迹。
- 发布原则：数据库变化只做可前向兼容的扩展；先迁移、后服务端、再前端。旧版本代码必须能在新增表/列存在时继续运行。

## 2. 已确认的拆分方案

采用“一份边界设计 + 六份独立实施计划”，而不是一份大计划。六个实施者可以从同一 `main` 基线创建独立 worktree；每个批次只对自己的验收标准负责。共享热点文件通过小提交、最小改动和明确所有权降低合并冲突。

推荐分支名：

1. `codex/hardening-b1-conversation-reliability`
2. `codex/hardening-b2-content-contracts`
3. `codex/hardening-b3-notifications`
4. `codex/hardening-b4-automations`
5. `codex/hardening-b5-version-export`
6. `codex/hardening-b6-auth-acceptance`

建议预留迁移号：批次 1 使用 `0084`，批次 2 使用 `0085`，批次 3 使用 `0086`，批次 4 如需 schema 变化使用 `0087`。开始实现前必须以当时 `main` 的最新迁移重新确认编号；若编号已占用，只顺延文件名，不改变迁移语义。

## 3. 公共设计规则

### 3.1 幂等与失败语义

- 幂等键绑定一次“用户业务意图”，而不是一次 HTTP 调用。
- 网络断开、超时、502/503/504 等结果不确定时保留原键；只有收到确定终态、确定的 4xx 拒绝，或用户明确选择“再次执行”时才生成新键。
- 页面重试必须区分“重试同一意图”和“再次执行新意图”。服务端继续使用现有幂等记录返回原消息、Run 或自动任务执行。
- 已经形成持久化业务事实的操作不得只返回笼统失败；响应必须让前端区分“未接收”“已接收但处理失败”和“结果未知”。

### 3.2 数据新鲜度

- 首次装载、路由重新进入、窗口从隐藏恢复可见和本地写操作完成，是四个标准刷新触发点。
- SSE 用于已有活动对象的低延迟变化；有界条件刷新用于发现其他标签页、后台调度和断线期间产生的新对象。
- 页面级读取不能因为无关接口失败而清空已经成功的投影；部分成功必须保留最近一次有效数据，并给失败模块独立重试入口。

### 3.3 权限与版本

- 前端能力控制只改善体验，服务端继续执行对象级授权和执行前复核。
- Agent、Skill 和团队 Agent 成员都以不可变版本引用进入 Session/Run；业务 ID 只用于发现，不作为运行版本事实。
- 撤权后客户端应收敛导航和按钮，但不能以客户端刷新代替服务端即时拒绝。

### 3.4 测试与发布证据

- 每个关键旅程先更新 `e2e/TEST-CATALOG.md`，再实现代码。
- P0 只证明页面和确定性交互；涉及 PostgreSQL、权限、迁移和状态机的行为必须由 P1 专用可丢弃数据库验证。
- 真实 DSH、OIDC、对象存储和目标机行为单独保留 P2 证据，不得被 P0/P1 替代。
- 每个批次至少包含：相关单元测试、PostgreSQL 集成测试、前端组件/Store 测试、对应 Playwright 旅程、`pnpm verify`、`pnpm check:architecture`、类型检查和构建。

## 4. 批次 1：会话、Run 与重试可靠性

### 4.1 所有权

主责问题：F-06、F-11、F-12、F-14、F-19，以及 F-18 的 Run/最近对话发现部分。

### 4.2 设计

1. 建立前端“用户意图”模块，为发送讨论、启动 Run、继续会话和自动任务手工触发生成稳定幂等键；对结果不确定的失败保留键和请求指纹。
2. 把新 Session 明确建模为未激活草稿：只有首条讨论消息或首个 Run 成功受理后才进入历史/最近对话。失败重试沿用原草稿；服务器仅在确认没有消息、Run、附件和并发写入时回收草稿。
3. `SessionResumeView` 不再自行复制附件上传循环，统一复用带部分成功跟踪和删除补偿的 Store 服务。
4. 团队无 Run Session 的恢复入口复用团队 composer：普通发送写入讨论消息；只有用户显式选择可用的 `workspaceAgentMemberId` 后才启动 Run。
5. Run 收到终态 SSE 后执行有界快照对账。投影滞后和瞬时 GET 失败均继续退避重试；对账完成或达到明确失败上限后才关闭恢复任务。
6. `taskStore` 增加显式 `refresh`，在路由返回、窗口恢复可见和自动任务/其他标签页可能创建 Run 后拉取增量列表，并为新发现的活动 Run 建立现有 SSE。

### 4.3 数据与接口

- `0084` 仅增加草稿状态、客户端意图关联和安全回收所需字段/索引，不物理删除历史 Session。
- 旧 `POST /sessions` 和 Run 接口保持兼容；新增或扩展响应必须返回是否为幂等重放、确定的 Session 状态及稳定资源 ID。
- Session 草稿回收必须由服务端事务检查，不允许前端直接删除可能已有并发内容的 Session。

### 4.4 独立发布条件

- 模拟“服务端提交后响应丢失”，同键重试只产生一条消息、一个 Run 或一个自动任务执行。
- 多附件第二个失败、启动 Run 失败和切换路由均不遗留不可见附件。
- 团队纯讨论从全局历史恢复后可以继续讨论，并能选择 `@Agent` 启动 Run。
- 一次终态快照 GET 失败后仍能自动收敛到完整终态。
- 仅发布本批次时，文件、通知、自动任务列表、版本选择和导出仍保持旧行为，不依赖后续批次。

## 5. 批次 2：团队文件与工作空间读取契约

### 5.1 所有权

主责问题：F-02、F-03、F-04、F-05、F-08、F-10、F-13。

### 5.2 设计

1. 上传新版本在对象写入前完成可安全完成的逻辑文件、空间状态和权限预检；事务内继续执行最终复核。
2. 对无法消除的“对象已写、数据库事务失败”窗口建立 GC candidate 日志。清理器只在宽限期后且确认没有任何 `file_objects` 或版本引用时删除对象；对象内容和 storage key 不进入普通日志。
3. 首次上传只要逻辑文件和版本已经持久化，就返回统一文件投影。解析失败用 `parseStatus=failed` 和安全错误码表达，不再把整个上传显示为未发生。
4. 上传、列表、版本恢复和解析状态接口共享同一服务端投影函数，统一返回 `canReference`、`canDownload`、`parseStatus`、`versionCount` 等派生字段。
5. “引用团队文件”接入当前团队空间的受权文件选择器，提交稳定 `logicalFileId`；在选择器完成前不得用纯文本 `@工作空间文件` 模拟引用。
6. viewer 的首次上传、版本上传和空状态按钮都使用同一能力投影隐藏/禁用；服务端 `denyViewer` 保持不变。
7. `GET /workspaces` 收窄为计数和少量摘要；Files Tab 改用已有分页端点。`contentStore` 将工作空间、成果和 Agent 拆为独立加载、错误和缓存状态。

### 5.3 数据与接口

- `0085` 增加对象 GC candidate 表、状态、宽限时间和必要索引；清理任务幂等并带审计。
- 工作空间列表响应保留旧字段一个兼容窗口，但新前端不再依赖完整 `files` 数组；删除旧字段必须另起后续兼容清理任务。
- 文件上传响应和列表行使用同一 DTO，避免前端猜测权限或解析状态。

### 5.4 独立发布条件

- 无效 logical file、并发归档和并发撤权场景不会形成不可追踪对象；GC 只清理无引用候选。
- 解析失败文件立即出现在 Files 列表并可明确重试，不重复创建逻辑文件。
- 上传成功后无需刷新即可按权限引用。
- viewer 看不到任何上传入口，伪造请求仍被服务端拒绝。
- 成果或 Agent 接口失败时，空间列表仍显示成功加载的数据和独立错误提示。
- 仅发布本批次不要求通知模型或会话幂等改造存在。

## 6. 批次 3：团队通知、动态与已读闭环

### 6.1 所有权

主责问题：F-01、F-07、F-09。

### 6.2 设计

1. 共享动态和个人通知分层：workspace activity 描述可在空间内展示的事件；notification delivery 保存接收人、读状态和稳定事件游标。
2. 新增讨论、回复、成员提及、Agent Run 完成和失败事件。元数据只保存稳定对象 ID、事件类型和安全展示字段，不保存消息正文、回答正文、文件内容或隐藏推理。
3. 默认收件规则：讨论/回复通知会话现有参与者但排除操作者；明确 @成员只通知被提及者；Run 完成/失败通知请求者；文件与成员类事件沿用有访问权的空间成员。静音只抑制 badge/主动提醒，不删除动态事实。
4. 每个可通知事件获得单调 sequence。已读 API 提交用户实际看到的最大 sequence；禁止使用 `now()` 作为 watermark。
5. 员工壳层提供全局通知入口，工作空间卡片显示未读 badge，空间详情实时更新动态摘要。跨空间发现使用账号级通知 SSE 或有界轮询，并支持 Last-Event-ID/sequence 恢复。
6. 撤权、退出空间或归档后，通知读取再次执行当前对象权限；失去访问权的对象不再泄露标题或摘要。

### 6.3 数据与接口

- `0086` 扩展 activity kind、增加单调 sequence、notification deliveries 和 sequence watermark。
- 新接口必须支持分页、未读计数、按空间过滤和游标已读；旧通知接口在一个兼容窗口内映射到新模型。
- 写事件与业务事务使用同一事务或可靠 outbox，不能在业务提交失败后留下虚假通知。

### 6.4 独立发布条件

- 两名成员的讨论、回复、@、Run 成功/失败产生正确且最小化的收件人集合。
- 并发写事件与“全部已读”不会吞掉之后提交的事件。
- 用户停留在其他页面时能发现新通知；断线重连不重复、不丢失。
- 非成员、已撤权成员和 viewer 的可见范围符合当前权限。
- 仅发布本批次时仍能消费旧会话和文件事件，不依赖其他五批次。

## 7. 批次 4：自动任务生命周期与执行历史

### 7.1 所有权

主责问题：F-15、F-16，以及 F-11 的自动任务手工触发部分、F-18 的自动任务状态刷新部分。批次 4 在自动任务 Store 内独立实现稳定意图键，不依赖批次 1 的会话 Store。

### 7.2 设计

1. 明确状态语义：暂停是可恢复的停止调度；现有 `disabled` 在产品上改称“归档”，默认列表隐藏但可通过归档筛选查看、恢复和读取全部历史；暂不提供物理删除。
2. 新增恢复归档任务的受权服务和端点。恢复时重新校验当前用户、Agent 版本、工作空间和 scope ceiling，不沿用过期授权直接启用。
3. 执行历史改为稳定游标分页，响应包含 `items`、`nextCursor` 和 `hasMore`；前端抽屉提供加载更多并明确展示范围。
4. 抽屉仅在可见且存在非终态执行时做有界轮询；完成后停止。窗口隐藏、抽屉关闭和账号切换立即释放计时器。
5. 定时触发、Worker 状态变化和本地按钮操作都复用同一执行投影，不在前端复制第二套运行状态机。

### 7.3 数据与接口

- 优先复用现有 `disabled` 数据值，避免破坏历史；如恢复需要时间或操作者，`0087` 仅增加 `archived_at`、`archived_by` 等审计字段。
- 旧执行历史数组接口保留兼容包装；新前端使用分页 envelope。

### 7.4 独立发布条件

- 归档任务从默认列表消失，但可在归档筛选中查看历史并恢复。
- 超过 50 条的执行可以完整分页，不重不漏。
- 打开运行中执行时，无需关闭抽屉即可看到终态和结果状态；终态后没有残留轮询。
- 恢复任务会重新执行当前授权检查。
- 本批次不改变 DSH、Run/Attempt 或定时调度的执行职责。

## 8. 批次 5：不可变版本选择与完整导出

### 8.1 所有权

主责问题：F-17、F-20。

### 8.2 设计

1. Agent/Skill 广场 DTO 同时返回业务 ID、不可变 version ID/reference、展示版本和发布时间。
2. 从广场进入新对话时把所见版本引用带到 composer；创建 Session 提交该版本引用，服务端验证它仍已发布、可见并满足工具闭包。
3. 老客户端只提交业务 ID 时继续按当前版本解析，保证兼容；新客户端不得静默从用户所见版本切换到更新版本。版本不可用时返回明确冲突，要求用户重新确认。
4. 导出动作拆分为“导出本次 Run”和“导出完整会话”。完整会话由服务端受权导出端点读取 Session thread，而不是使用侧栏 `TaskRun.messages`。
5. 导出文件包含范围、生成时间、Session/Run 脱敏标识和是否截断；团队 Session 包含用户有权读取的讨论与多轮 Run，不包含隐藏推理、内部事件或无权对象。

### 8.3 接口

- `POST /sessions` 增加可选不可变版本参数并保持业务 ID 兼容路径；服务端保存和响应实际绑定版本。
- 新增 Session/Run 导出端点，使用流式或有界分页组装，避免把大型会话一次性装入浏览器内存。
- OpenAPI 与前端 domain types 同步更新。

### 8.4 独立发布条件

- 用户看到 v1 后即使管理员发布 v2，新 Session 仍绑定 v1；若 v1 已停用则明确要求重新选择。
- Session、Attempt 和运行展示的版本引用一致且可追溯。
- 团队完整导出包含纯讨论和多轮 Run；本次 Run 导出只包含对应 Run，两个文件名和说明不混淆。
- 大会话导出有界，不阻塞前端主线程，不越权读取其他空间内容。
- 本批次不要求通知、自动任务或文件批次先落地。

## 9. 批次 6：撤权后的客户端收敛与全量验收

### 9.1 所有权

主责问题：F-21；同时负责六批次共用的发布证据模板、目标机只读回填和最终回归矩阵，但不接管其他批次的功能实现。

### 9.2 设计

1. 管理端 auth store 增加可并发合并的 `refresh()`，窗口恢复可见、进入受保护路由和收到授权相关 403 时触发有界刷新。
2. API 错误区分未登录 401、当前对象无权访问 403 和身份能力已变化。403 仍返回原业务错误，同时至多触发一次身份刷新；禁止形成请求重放或无限跳转。
3. 刷新后重新计算导航、按钮和路由守卫。当前路由已无权访问时跳到用户仍可访问的第一个管理页；完全失去管理权限时进入明确的无权限页，而不是循环登录。
4. 员工端复用同一刷新原则更新角色和 data scopes，但不扩大 F-21 的服务端授权范围。
5. 建立六批次共同的发布核对表：迁移、兼容窗口、P0/P1/P2 证据、回滚条件、监控指标和目标机只读取证。

### 9.3 独立发布条件

- 管理员降权、角色停用和权限范围收回后，已打开页面在一次刷新周期内收敛导航和写入口。
- 403 不触发自动重放写请求，不造成登录循环；服务端始终保持 fail-closed。
- 员工端数据范围变化后 UI 在窗口恢复可见时更新，旧入口消失。
- 本批次自身可单独发布；全量回归矩阵只有在六批次都合并后才标记整体验收完成。

## 11. 并行开发与共享热点

六批次可以并行编码，但下列文件是潜在冲突点：

- `apps/workbench-web/src/stores/tasks.ts`：批次 1 主责；其他批次通过新增独立 Store/helper 接入，不直接改其状态机。
- `apps/workbench-web/src/stores/content.ts`、`WorkspaceDetailView.vue`、`WorkspacesView.vue`：批次 2 主责；批次 3 的通知 UI优先新建组件后由一次小提交接入。
- `apps/workbench-web/src/layouts/EmployeeShell.vue`：批次 3 与批次 5 都可能接入；分别保持通知入口和导出菜单为独立提交。
- `server/src/http/workbench/conversation-routes.ts`：批次 1 与批次 5 都可能修改；新增请求解析应放入各自 schema/helper，路由接线保持小提交。
- `e2e/TEST-CATALOG.md`：每批使用独立小节和唯一用例编号，避免改写同一段落。

每个批次从同一基线建 worktree，先提交测试目录/契约，再提交实现，再提交 E2E/文档。推荐合并顺序是 1 → 2 → 3 → 4 → 5 → 6，但这只是降低文本冲突的顺序，不是功能依赖；任一批次均必须能独立部署到基线系统。

## 12. 发布、回滚与观测

### 12.1 单批发布

1. 在专用测试数据库应用该批迁移并跑 P1 集成旅程。
2. 运行该批相关单元/前端/E2E，再运行 `pnpm ci:check` 和架构检查。
3. 构建独立 Release，记录 commit、迁移和 DSH lock；目标机先做只读 preflight。
4. 发布后观察错误码、重复记录、SSE/轮询连接、对象 GC、响应体大小和 403 分布。
5. 只有该批验收证据通过，才把它标记为已发布；其他批次状态保持独立。

### 12.2 回滚

- 数据库迁移默认不下滚；代码回滚到旧 Release 后忽略新增表/列。
- 新事件、草稿状态和自动任务归档必须保证旧代码不会读取为可执行状态。
- 对象 GC、轮询和通知投递都必须有停用入口；回滚代码前先停止新任务认领，不能删除已记录事实。
- 若新前端与旧服务端版本不兼容，反向代理应原子切回同一 Release 的前后端组合，禁止混发。

### 12.3 目标机证据

复用 `docs/development/main-flow-breakpoint-target-questions-2026-10-21.md`，每批只回填自己负责的章节。目标机只读取证不能替代专用测试环境的故障注入；需要写操作或真实任务时必须进入明确的 P2 验收窗口。

## 13. 不纳入本轮

- 不新增另一套 Agent 框架、直接模型 API 或生产 Mock Runtime。
- 不改变个人空间的既有数据模型和合法使用范围。
- 不物理删除 Session、自动任务、通知、文件版本或审计记录。
- 不把通知扩展成通用企业 IM，也不实现任意订阅规则编辑器。
- 不借本轮重构所有大型 Vue 文件；只提取能降低本批风险的明确组件/helper。
- 不用降低断言、固定延时或静默重试换取测试绿灯。
