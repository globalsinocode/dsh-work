**范围：** 成员／会话／共享文件三类可见统计（方案 §6.6）。不含来源限制、发布／撤回与多层派生（随 T2 取消、2A／2B 放弃）。

## 2. 指标口径（解读前必读）

- **计数单位是 SQL 语句数，不是网络往返数。** postgres.js 的 `debug` 钩子每个语句触发一次；本工具用 `prepare: false`，带参语句会先发 `Parse/Describe` 再发 `Bind/Execute`，即**每条带参语句约两次线级往返**。选语句数是因为它与实现代码一一对应、可稳定复现；换算成线级往返时带参语句大致 ×2。
- **测量层次是服务层**（`PostgresContentService` / `PostgresConversationRepository` / `PostgresAuthorizationService`），**不含路由层与 JSON 序列化**。每个真实 HTTP 读请求会先执行 `authorization.authorizeWorkbench(...)`（实测热态 3 条语句），团队读路由还会再加 `workspaceTypeOf` 与 `requireTeamRole`；因此**页面端到端会高于本表的服务层数字**（量级：`listWorkspaces` 16→约 19，`listArtifacts` 3→约 6，`listWorkspaceFiles` 3→约 6，`listWorkspaceSessions` 1→约 7）。
- **连接池类型探测（`pg_catalog.pg_type`）已从计数中排除。** 它属于池启动开销，不是被测调用的成本；早期版本未排除，导致「冷启动」与「并发」两栏被池预热污染。
- 「冷启动」= 该测量进程内首次业务调用；「热路径」= 同一调用重复 20 轮后的分位数。「冷启动」对 `listArtifacts` 才等价于「授权缓存为空」，其余三个方法内部不查授权缓存。
- **绝对毫秒数随机器、并发与连接池状态变化，不要当预算用**；语句数、相对量级与随规模的增长趋势才是本基线的信号。

## 3. 结论摘要

| 读取路径 | SQL 语句数（基线规模） | 判定 |
| --- | --- | --- |
| `listWorkspaceSessions` 首页／深翻页／标题搜索 | **1** | 达标：单次 keyset 查询，深翻页与首页同量级 |
| `listWorkspaceFiles` 首页／深翻页／名称搜索 | **3** | 达标：3 次为「空间可访问性 + 成员角色 + 列表」固定开销，与行数无关 |
| `listArtifacts`（200 条成果） | **6 冷 / 3 热** | 达标：按空间去重复核，与成果行数无关（见 §4） |
| `listWorkspaces`（可见空间统计） | **2 × 可见空间数 + 4** | **待优化**：每个可见空间 2 条语句（成员名册 + 文件），线性放大（见 §5） |

三类列表（会话／文件／成果）均已是「服务端可授权查询 + 游标分页」，**没有**先取全量再在前端过滤，也没有逐行门禁的 N+1 残留。

## 4. `listArtifacts` 的可见范围过滤：同批数据上的可复跑 A/B

T4 把成果列表的可见范围过滤从「逐行门禁」改为「列表查询内取 `w.workspace_type` + 按空间去重复核一次」。两种形态都写进了同一工具，可在**同一批数据**上直接对照（200 条团队成果）：

| 实现形态 | SQL 语句数 | p50 (ms) |
| --- | --- | --- |
| 当前实现：按空间去重复核 | **6 冷 / 3 热** | ≈34 / ≈26 |
| 候选实现：逐行门禁（T4 修复前形态） | **404** | ≈240 / ≈214 |

结论：语句数从「与成果行数同阶」降到「与可见空间数相关」，200 行时约 **1/67**；这由可提交的候选实现表达，任何人可复跑验证，不依赖评审口述的历史数据。（T4 提交信息里引用的 201／~1001 来自评审对另一版未提交候选的实测，本基线不再引用那组数字。）

**个人空间**：同一成员个人空间的成果不触发可见范围过滤（`workspace_type = 'personal'` 直接放行），实测 10 条成果 3 条语句，与空间内成果数无关。**已知变异**：个人空间单次测量在 1–3 条语句间波动（多数为 3），原因未定；不影响结论，复跑时不要把它当精确值。

`listArtifacts` 当前**无 `LIMIT`**（返回该成员全部成果）；200 行时服务层 p50 约 26–34ms。若单成员成果进入千级，需要与前端分页一起决策（记录为待办，不预设方案）。

## 5. 待优化：`listWorkspaces` 的按空间子查询（N+1）

**现象（实测）：** 固定其他参数、只改团队空间数 N（可见空间 = N + 1，含自动建立的个人空间），语句数严格线性：

| 团队空间数 N | 3 | 5 | 8 | 12 |
| --- | --- | --- | --- | --- |
| 可见空间数 | 4 | 6 | 9 | 13 |
| `listWorkspaces` 语句数 | 12 | 16 | 22 | 30 |

拟合为 **语句数 = 2 × 可见空间数 + 4**。按 SQL 形状拆解可确认每空间这 2 条分别是：按空间取成员名册（`select u.display_name … from workspace_members`）与按空间取文件（`select f.id, f.storage_key …`）。实现位置：`postgres-content-service.ts` 的 `listWorkspaces`，在 `Promise.all(rows.map(async row => …))` 中对每个可见空间分别发起这两条查询。

**为什么这是问题：** 方案 §6.6 要求「优先用服务端可授权查询、按租户／空间／作者／状态的索引和聚合后关联」。当前是每空间两条语句，随空间数线性放大；6 个可见空间时热路径 p50 ≈ 27ms。

**候选修法（未实施，待评审决策）：** 把这 2N 条子查询改为**主查询里一次聚合**（成员名册与文件分别用 `array_agg`/`json_agg` 按空间聚合），或改为一条 `IN (…)` 批量查询后在内存分组。属「有证据后再优化」，本任务只出证。

**主聚合本身的规模：** 主查询把「空间 × 成员 × 会话 × 成果」展开后再 `count(distinct)`。基线规模下中间结果 **8656 行**、`Buffers: shared hit = 17919`（其中 `artifacts` 索引被扫 8656 轮、命中 17312 次缓冲但 0 行——该场景成果表为空，规划器选了嵌套循环）。放大来自空间×成员×会话的乘积，**不是**缺 `workspace_id` 连接条件（连接条件完整，计划里可见 `Join Filter: (s.workspace_id = w.id)`）。`count(distinct)` 会把重复计数掩盖成正确值，**因此计数断言无法保护这条退化**，只能靠计划与缓冲次数观测。

## 6. 并发

10 路混合读取（4 类调用交错）共 **59 条语句**、p50 约 60ms（多次运行 59–62ms），无错误、无超时。该值等于 `3×16 + 3×1 + 2×3 + 2×1 = 59`，即并发下没有出现额外放大或串行化（池探测已排除）。

## 7. 独立验证发现的方法论问题（已修）

首版基线经独立验证代理复核：结论与数字可复现，但方法论上被指出以下问题，均已修正并重测。

| 问题 | 处置 |
| --- | --- |
| `debug` 统计的是 SQL 语句而非网络往返 | 全文改为「SQL 语句数」，§2 说明与线级往返的关系（带参语句约 ×2） |
| 「冷启动」「并发」两栏含连接池 `pg_type` 探测 | 计数钩子显式排除该探测；冷启动 `listWorkspaces` 由 22 降为 16，并发由 67 降为 59 |
| T4 修复前后对比不可复跑、引用了未提交实现的数字 | 把「逐行门禁」写成本工具内的候选实现，改为同批数据上的可复跑 A/B（见 §4） |
| 未披露路由层授权成本 | §2 明确测量层次并给出路由层叠加后的量级 |
| 公式把 N 说成可见空间数、截距解释有误 | 改为 `2 × 可见空间数 + 4`，可见空间 = 团队空间 + 个人空间 |
| 文档间数字不一致、把语句数与延迟相加 | 所有引用改为与生成文件一致；删除无效的「2.2 倍」推断 |
| 计划 SQL 与实现不完全等价（会话状态过滤）、成果计划在 0 行时采集 | 会话计划补 `status = 'active'`；成果计划改在 200 行数据上采集。计划仅用于确认索引命中与放大形态，行数／缓冲结论已在主聚合的实际实现 SQL 上复核 |

## 8. 未做与待办

- **TW-07 之后本基线部分过时（质量评审 F8/P3）**：`scripts/bench/team-workspace-statistics.ts` 里的文件列表与空间摘要查询仍按 TW-07 **之前**的形状建模（直接查 `file_objects`），既没有 seed `workspace_files`/`workspace_file_versions`，也没有覆盖新的 `join lateral`（取最高解析成功版本）与 `versionCount` 相关子查询。因此本基线的「`listWorkspaceFiles` 3 条语句」不能代表 TW-07 之后的成本。**复测前不要引用该数字**；TW-07 专项预算未定义（方案 §6.6 的基线属 1B），需要时再按新查询形状复跑。

- **不预设物化方案**：方案 §6.6 明确「在测量确认必要前不预设」。本基线给出证据；是否把 `listWorkspaces` 的子查询改为单次聚合、是否给 `listArtifacts` 加分页，留实施评审决策。
- **缓存与投影的收权约束**（方案 §6.6 末条）：若将来引入缓存或异步投影，必须能按当前身份过滤且在收权后失效；当前实现无此类缓存。
- **页签计数**：三个页签的计数目前不在独立接口上（会话与文件列表各自分页、不返回总数），因此本基线不含「页签计数」；若后续为页签加载总数，需复用同一可见条件并纳入本基线复测。
- **会话／文件的行数扫描**：本基线只扫描了可见空间数，未扫描「单空间内会话数／文件数」从百级到千级；两者是单次 keyset 查询，理论上与总行数无关，但**尚未实测验证**，列入后续复测。
- **多租户规模**：基线为单租户；已确认 `sessions_by_workspace`、`artifacts_by_workspace`、`workspace_members_pkey` 被命中，更多租户下的对比留待部署环境测量。
- **工具未纳入 `pnpm typecheck`**：仓库 tsconfig 只覆盖 `src/**`，`scripts/` 仅被 eslint 覆盖；这是既有约定（`scripts/runtime/*.ts` 同理），如需纳入应统一决策。
