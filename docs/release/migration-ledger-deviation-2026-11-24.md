# 生产迁移账本偏离记录（2026-11-24）

## 1. 背景

生产 Mac mini 的 `schema_migrations` 账本有 **179** 条，而上游 release 的
`server/migrations` 只有 **129** 条。2026-11-24 按部署手册 8.1 执行严格 `diff` 时：

- `only_in_release = 0`：release 的 129 条全部已在账本中，**没有待应用迁移**；
- 公共 129 条 `(version, checksum)` **0 处不符**；
- `NULL` checksum **0 行**；
- `only_in_ledger = 50`：生产库存在 50 条 release 不包含的历史版本，版本号
  `0082_…`–`0131_…`（dev 分支时期命名，清单见生产取证 `attachments/02-ledger-set-detail.txt`）。

这批版本是生产环境从 dev 分支时期沿用下来的既有状态：11-16 版本部署时即已存在；
11-24-01 与 11-24-02 的部署日志均显示 release 的 129 条全部 `skipped`、**零 DDL**，
说明它们不是本次发布引入，也没有在本轮被重新执行。

## 2. 裁决

**按“登记偏离”放行，不补迁移。**

理由：

1. 严格 `diff` 为空的目标是“无待应用、无 checksum 漂移、无 NULL”，这三项均已满足；
   多出的 50 条是**已执行的历史状态**，迁移执行器会按版本跳过，不影响本次发布。
2. 把 dev 历史迁移补进 upstream release 会让干净环境执行一套从未在 upstream 验证过的 SQL，
   风险和影响面都远大于收益；本次 11-24-02 与 11-25-01 均**没有迁移变更**。
3. 不得写库、不得删除账本行、不得修改已发布 migration。

## 3. 放行条件

每次发布前仍执行 8.1 的完整检查，必须同时满足：

- `only_in_release = 0`；
- 公共版本 `(version, checksum)` 0 处不符；
- `NULL` checksum 0 行；
- `only_in_ledger` 的集合与本文记录的 50 条清单一致（或能解释新增/减少）；
- 本次 release 的迁移文件集合与当前已部署版本逐文件一致（blob 哈希比较），或差异已单独评审。

任一条不满足即停止发布，重新裁决。

- 11-24-02 部署记录：`deploy-record-v2026.11.24-02-2026-11-25.md`（仓库外），同为零 DDL；
