## 3. 本期范围

本期只关闭目标机文档最后一轮列出的四组缺口。

### 3.1 工具治理方向决策

目标机同时存在两组互斥契约：

- `0104` 及一条合并血脉要求保留 `tools`、`tool_versions`、Binding 与审计；
- 另一条血脉的测试仍要求删除工具治理表，并把内置工具完全代码化。

本期首先形成一份唯一、可执行的治理决策，明确以下边界：

- DSH 普通业务工具是否继续使用 Tool Version 与 Binding；
- dsh-work 代码内置工具与普通 DSH 工具如何分界；
- MCP 是否只使用 Connector/Profile/能力摘要，不生成平台 Tool Version/Binding；
- Agent 发布、Runtime Manifest、停用复核和审计分别读取哪一个权威来源；
- 已有迁移数据和升级路径如何处理。

推荐保留 `0104` 已明确的治理模型，并把“内置工具代码注册”限制在 dsh-work 内置工具目录；但该推荐必须由产品/架构负责人明确确认。确认前不得修改互斥测试来制造绿灯。若最终选择删除治理模型，该选择会扩大到迁移、管理接口、发布快照、授权与审计，须另立 SDD，不在本修复计划内边做边删。

### 3.2 Agent 岗位权限能力摘要

目标机已经补齐岗位权限读写接口，但 `AgentAccess.capabilities` 投影、能力所需授权规划和前端摘要仍缺失。行为要求如下：

- 服务端返回当前草稿版本（优先）或活动版本的能力授权需求；
- 每项能力至少包含稳定标识、展示名、所需角色、所需数据范围和当前是否满足；
- 角色要求为“任选其一”时不得错误合并为“全部必选”；
- 数据范围按当前授权逐项判断；
- 未选择岗位角色且未选择数据范围时，接口可以返回需求，但页面不展示缺授权警告；
- 选择任一岗位角色或数据范围后，页面展示能力可用情况；
- 岗位角色选项中，当前能力需要的角色显示“能力需要”；含管理权限的角色继续显示“含管理权限”并保持靠后；
- 详情页可以提供“补齐所需授权”，只修改表单，不自动保存；草稿嵌入步骤不显示该按钮、不预选角色、不自动授予；
- 服务端验证与运行时授权仍是权威门禁，摘要不能代替真实授权检查。

能力需求的数据源取决于 3.1 的治理决策：保留治理时从精确 Tool 引用及权威授权元数据投影；若选择删除治理，则必须先在新的独立 SDD 中定义代码注册表里的等价授权元数据，不能继续读取被删除表，也不能并存两套不一致来源。

### 3.3 PF-MCP-01 生效快照一致性

目标机现象为：Bearer Token 轮换并检查后页面显示成功，但测试证据中的 `resolvedConnectionCount` 为 0，运行解析报告“已选 MCP Connector 不可用”。

必须保证管理面写入与执行面读取同一份生效能力事实：

- 正式登记、凭据轮换后的重新检查、能力确认都同步维护当前发现摘要与生效摘要；
- Connector 只有在 `healthy`、生效摘要存在且快照非空时可解析；
- 新增或 Schema 变化的 Tool 在确认前不进入生效快照；
- 人工停用、删除、凭据失效和摘要漂移仍然 fail closed；
- P1 浏览器夹具不得吞掉 `resolveConnections` 的真实异常后只返回 0，失败响应必须保留可诊断信息；
- 修复必须覆盖生产组合根中并存的 MCP service 与 Tool service，不只在测试路由旁路写数据。

## 6. 证据和停止条件

- 所有 PostgreSQL 集成与 P1 浏览器旅程只使用专用可丢弃数据库；
- 每轮运行结果写入 `e2e/catalog/verification-log.md`，记录命令、提交、层级、通过数、失败数和环境；
- 修复失败时只保留一个可证伪假设，一次修改一个原因；连续三次修复仍在不同边界暴露新问题时，停止叠补丁并回到架构决策；
- 目标机提交无法取得、工具治理未决、真实失败日志缺失或测试数据库不安全时，停止对应任务并报告，不用当前旧代码猜测完成状态。
