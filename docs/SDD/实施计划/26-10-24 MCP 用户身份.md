# MCP 用户身份 实现计划

> **面向实现者：** 按任务顺序做。每步先写测试并看到失败，再写最少实现。步骤使用 `- [ ]` 跟踪。提交只在用户明确要求时执行；未要求时停在工作区改动。
>
> **规格：** [26-10-24 MCP 用户身份](../规格文档/26-10-24 MCP 用户身份.md)

**目标：** 管理员仍在「MCP 连接器」登记外部 MCP；认证方式增加 `user_oauth` 后，每次执行只注入本次人类主体自己的访问令牌，未授权时按 `selected` 拒绝或按 `all` 移出，绝不回退到连接器级 Bearer 或他人令牌。

**架构：** 不新建 Agent 循环，不恢复已删除的 `agent_mcp_grants`。OAuth 客户端由平台扮演：交易、PKCE、换票放在新模块；密文沿用 `DSH_CREDENTIAL_MASTER_KEY`，但员工令牌的附加认证数据多绑 `userId`。`AttemptDispatcher.dispatch` 已有 `input.userId`（自动任务里就是所有者），把它传进 `getRuntimeSnapshot`，在写 Manifest 之前完成求交。DSH 注入仍走现有环境变量，补丁文件不落明文。

**技术栈：** 现有 Node.js 服务、PostgreSQL 迁移、Vue 3 管理端与员工端、`node --test` 与 Vitest。不新增 npm 依赖。传输仍是 Streamable HTTP。

**新建文件的目录：** 服务端新模块放在 `server/src/modules/tool/`，与连接器服务同目录，不塞进 `postgres-tool-connector-service.ts` 里重写 OAuth。员工端新组件目录是 `apps/workbench-web/src/components/external-connections/`，组件文件 `external-connections.vue`。**新建**员工端单测放在 `apps/workbench-web/src/__test__/components/external-connections/`。管理端已有旁路测试 `apps/admin-web/src/views/CapabilityManagementView.test.ts` 只改内容，不搬家。

**不改：** `none` / `bearer` 的登记字段、轮换接口、连接器级密文和全体共用上游身份；`connector-dsh-workspace`；Agent MCP 范围的三种模式；主导航五项；MCP Resources / Prompts / stdio；动态客户端注册；手填 PAT。

```ts
export interface McpUserTokenPair {
  accessToken: string
  refreshToken: string | null
  accessExpiresAt: string | null
}

export class McpUserCredentialStore {
  constructor(private readonly masterKeyBase64: string, private readonly keyId = 'v1') {}
  seal(input: { tenantId: string; credentialRefId: string; userId: string; tokens: McpUserTokenPair }): {
    ciphertext: Buffer; nonce: Buffer; authTag: Buffer; keyId: string

  open(input: {
```

### 任务 3：换票校验受众，state 只能用一次

**文件：**
- 创建：`server/src/modules/tool/mcp-oauth.ts`
- 测试：`server/src/modules/tool/mcp-oauth.test.ts`

导出这些函数（测试直接调用，不启 HTTP）：

```ts
export function createPkce(): { verifier: string; challenge: string }
export function authorizationUrl(input: {
  authorizationEndpoint: string
  clientId: string
  redirectUri: string
  scopes: string[]
  resource: string
  state: string
  codeChallenge: string
}): URL
export function assertJwtAccessToken(token: string, input: {
  resource: string
  authorizationEndpoint: string
  now?: Date
}): void
export async function exchangeAuthorizationCode(input: {
  tokenEndpoint: string
  clientId: string
  clientSecret?: string
  code: string
  codeVerifier: string
  redirectUri: string
  resource: string
  fetchImpl?: typeof fetch
}): Promise<{ accessToken: string; refreshToken: string | null; expiresAt: string | null }>
```

`authorizationUrl` 只采用登记端点的 origin、path 与已有 query，再追加 `response_type=code`、`code_challenge_method=S256`、`resource`。端点不是 `https:` 时抛错。

`assertJwtAccessToken`：能按 JWT 拆成三段时才校验。`aud` 等于 `resource`（字符串或数组里包含该值），`iss` 的 origin 等于授权端点的 origin，`exp` 晚于 `now`。否则抛「用户令牌受众或签发方不匹配」。三段都拆不开时函数直接返回，交给调用方把整段当作不透明令牌保存。

`exchangeAuthorizationCode` 用 `application/x-www-form-urlencoded` POST。有 `clientSecret` 时放表单字段 `client_secret`，不放进 URL。响应里的 `access_token` 先经过 `assertJwtAccessToken`。`refresh_token` 缺失则为 `null`。

- [ ] **步骤 1：** 测试覆盖：challenge 可被 verifier 的 S256 复算；授权 URL 的 host 等于登记端点而不是调用方传入的其他 host；`aud` 不对的 JWT 被拒；不透明字符串被 `assertJwtAccessToken` 放过；换票请求的 URL 不含 `client_secret` 与 `code`。用假的 `fetchImpl`，不要访问网络。JWT 用测试里当场 `HMAC` 无关的未签名三段 payload 即可，本函数只解码 payload，不在本期验证上游签名（签名由令牌端点的 TLS 与后续刷新失败兜住；不要在计划外引入 JWKS 发现）。

求交放在 `resolveMcpConnectionsForAgentVersion` 拿到健康连接器之后：

```ts
async applyUserGrants(
  pins: McpConnectionSnapshot[],
  scopeMode: 'all' | 'selected' | 'none',
  subjectUserId: string | null,
): Promise<{ pins: McpConnectionSnapshot[]; omitted: Array<{ connectorId: string; name: string }> }>
```

规则写死在该方法里：

- `auth_type` 不是 `user_oauth`：原样进入结果，仍走现在的 `resolveMcpRuntimeConnection` 取连接器 Bearer。
- `user_oauth` 且主体为空，或该主体没有 `status = active` 的授权：`selected` 抛 `authorizationDenied`，消息包含连接器名称；`all` 放进 `omitted`，不进入 pin。
- 有效授权：若 `access_expires_at` 已到，用该主体的刷新令牌调用令牌端点一次。成功则写入新访问令牌；上游返回新的刷新令牌就替换，没返回就保留原刷新令牌，`version` 加 1。失败则把 grant 标为 `reauthorization_required`，按上一条处理，不用旧访问令牌。
- 成功 pin 带 `grant_subject_id = subjectUserId` 与当前 `credential_version`。

`resolveMcpRuntimeConnection` 在 `user_oauth` 时只按 pin 上的主体和版本解密。版本对不上或主体对不上，抛 `authorizationDenied`，函数后半段现有的 Bearer 读取不可被执行到。
