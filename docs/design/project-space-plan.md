# 项目空间方案

**状态：** 产品决策已确认（2026-10-17）；S0 已实现（服务端集成测试与前端单测通过，P1 浏览器旅程 PS-E2E-00 未编写，见第 8 节），S1、S2 待实施。实施完成前，[功能规则第 3 节](../development/feature-rules.md#3-团队工作空间)仍描述现行行为，本文内容不得当作已支持能力。<br>
**更新日期：** 2026-10-17<br>
**范围：** 员工端团队空间的产品定位、命名、团队交付边界、项目简报、项目任务、团队成果与项目档案。个人空间不变。

## 1. 为什么要改

团队空间现在是“共享讨论 + @Agent + 共享文件”，形态接近“群聊 + @机器人 + 网盘”：没有共同目标，Agent 拿不到项目上下文，没有分工，成果散落在讨论里。

新定位：**项目空间是人与 Agent 协同完成一个项目的地方。** 主线为：

```
项目简报 → 项目任务（员工或 Agent 承接；Agent 任务即任务线程）→ 团队成果 → 项目档案（档案员自动维护）
```

交互模型参考 Claude Tag（线程即任务、线程内任何人可续接、记忆按空间沉淀、人人可纠正），但不采用其按频道授权：Agent 用自己的授权执行，空间不能扩大员工的企业数据权限。

## 2. 已确认的决策

| # | 决策 |
| --- | --- |
| D1 | **命名：** 界面上“团队空间”改为“项目空间”。代码、表、接口继续使用 workspace（`workspace_type = 'team'`），不改名。 |
| D2 | **一个项目空间就是一个项目：** 空间内不再分子项目；截止时间与结项可选，长期运营型团队可以一直进行。结项沿用现有归档（3.6 语义不变）。 |
| D3 | **协作节奏：** 以异步项目任务为主，讨论中 @Agent 为辅。普通讨论仍须 @ 才触发；Agent 不在讨论中主动发言。 |
| D4 | **执行身份与交付边界：** Agent 始终以自己的 Principal 和岗位授权执行（代码已如此）。团队空间内：**角色只取 Agent 授权**；**数据范围取 Agent 授权与全体现任成员数据范围的交集**（第 3 节）。发起人只用于归因和准入（可见角色、成员角色）。 |
| D5 | **被指派的 Agent 默认读取项目上下文：** 项目简报、项目档案、任务中指定的项目文件。不默认读取其他共享文件、普通讨论或成员私有内容。 |
| D6 | **团队成果：** 任务完成即产出团队成果，全体成员可见；**不设审核环节**。 |
| D7 | **线程即任务：** Agent 任务就是绑定了承接 Agent 的讨论线程，任务列表是这些线程的状态视图；员工任务是轻量待办项。 |
| D8 | **任务线程内续接无需 @：** 在绑定 Agent 的任务线程里，非只读成员回复即交给该 Agent 继续执行，回复人记为发起人。普通讨论线程仍须 @。 |
| D9 | **项目档案由默认“项目档案员”系统 Agent 自动维护**；非只读成员都可编辑或回退，人工修改优先（第 7 节）。 |
| D10 | **不做过度设计：** 首版只做下文列出的字段与状态；Agent 之间无委派，任务依赖由人编排。 |

## 3. 团队交付边界（S0）

**现状：** 每次 Run 的 Manifest 固定 `principal_context.disclosure_user_id` 为单个员工，授权决策把 Agent 的角色与数据范围裁到该员工的范围内（`authorizeRuntimeDecision`）。团队空间里 Agent 回复广播给全员，但范围按发起人裁剪——这是 3.4 记录的“已决策接受的泄露面”。

**目标：** 团队空间内的 Run，交付的数据不超过**全体现任成员（含只读成员）共同可见的数据范围**，使可见范围与交付范围一致：

- **角色：** 只取 Agent Principal 的岗位角色，不再与发起人或成员的角色求交（与主动任务一致：接收人只是交付边界，不提供执行角色）。工具可用性因此不随成员组成变化。
- **数据范围：** Agent Principal 数据范围 ∩ 各现任成员当前数据范围（共同数据上限）。
- 准入仍按发起人：发起人须是非只读现任成员，且满足 Agent 可见角色。
- Manifest 的交付对象从单个员工扩展为“空间成员”（携带空间与团队授权修订号）；Manifest 编译、执行前复核、队列领取与 Runtime 调用前复核同步改为按该对象校验。个人空间与员工个人请求保持现有单人契约不变。
- 成员加入、移除、角色变化都会推进 `team_auth_revision`；在途 Run 复核时，若 Manifest 中的数据范围超出新的共同数据上限，按现有撤权链路收敛（新增：**加入成员也可能收紧范围**）。
- 系统发起的任务（档案员）同样按空间成员交付。

**界面：** Agent 成员详情展示“在本空间可交付的数据范围”。添加成员会缩小共同数据上限时，在确认前提示受影响的数据范围。共同数据上限导致 Agent 缺少声明能力所需的数据范围时，按现有不可用状态展示具体原因。

**与验证的差异：** 发布验证以“Agent 授权中可见角色可及的部分”为角色上限（`resolveAudienceCeiling`）；团队空间 Run 使用 Agent 全部岗位角色。Agent 持有可见角色以外的岗位角色时，这部分能力在团队空间可用但未经验证；验证前检查的“能力所需授权”项会给出不阻断的提示。

**已知代价：** 跨部门项目的共同数据范围可能很小，Agent 能接触的数据随之减少；依赖特定数据范围的工具可能不可用。这是“空间不扩大员工权限”的直接结果，通过上述提示让负责人在加人时看到影响，不提供绕过方式。历史内容的可见性不变：新成员与现在一样可以读到加入前的讨论与成果。

## 4. 项目简报（S1）

- 空间的一个属性：目标、背景、范围与约束等自由文本，外加可选截止时间。
- 负责人与管理员可编辑，每次保存生成新版本（记录编辑人与时间）；成员和只读成员可读。
- Agent 任务的每次执行固定当时的简报版本，与文件引用一样可追溯。

## 5. 项目任务（S1）

术语注意：平台已有执行层的 Task（`tasks` 表，对应 Run/Attempt）。“项目任务”是业务层工作项，表名用 `project_tasks`，不复用或改写执行层 Task。

**字段（首版）：** 标题、说明、创建人、承接者（一位员工成员或一个 Agent 成员）、引用的项目文件（固定版本，最多 5 个，与单次 Run 上限一致）、可选截止时间；Agent 任务另关联其任务线程（Session）。

**Agent 任务（线程即任务）：**

- 创建并启动后生成一个绑定该 Agent 成员固定版本的团队会话，作为任务线程，首条消息为任务标题与说明；经既有 `createSession` / `startRun` 执行，不新增执行入口或无 Session 入口。
- 每次执行的输入：线程消息 + 固定版本的简报 + 当前档案版本（S2 起）+ 指定文件。
- 状态由线程最近一次 Run 推算，不单独存储：执行中 → 进行中；成功 → 已完成；失败或取消 → 执行失败。已完成后成员继续回复会再次执行，状态随之变化。
- 续接：任务线程内非只读成员的回复直接交给该 Agent，回复人记为发起人；执行中收到的回复排队，当前执行结束后作为下一次执行的输入。执行中途注入新指令需 DSH 支持，不在本方案范围。
- 停止沿用现有取消，并在线程中标注由谁停止；重试沿用 `/runs/:id/retry`（新 Attempt）。
- 讨论中 @Agent 产生的线程可由成员“设为任务”，该线程即成为任务线程。
- 改派只在没有执行中的 Run 时允许；改派给另一个 Agent 时新建任务线程（一个 Session 固定一个 Agent 版本）。

**员工任务：** 待办 → 进行中 → 已完成。完成时填写说明，可附空间内已有的共享文件；交付内容显示在任务卡片上，不进入“成果”页签。

**权限：** 非只读成员可创建任务、编辑自己创建的任务、在任务线程中续接；负责人与管理员可管理全部任务；只读成员只读。归档后只读。

**完成判定：** 以持久化证据为准（`task-result/v1`），模型自述完成不算。

## 6. 团队成果（S1）

- 团队会话产生的成果已对空间成员可见（TW-10，`listArtifacts`），S1 不新建成果机制，只为成果补充所属项目任务的关联与展示。
- “成果”页签展示 Agent 生成的成果，标注任务、承接 Agent 及版本与发起人；读取仍按当前权限复核，归档后只读保留。

## 7. 项目档案与项目档案员（S2）

**项目档案：** 精选后的项目知识（已采纳结论、关键决策、术语、当前进展），不是文件集合。每次变更生成新版本，记录来源（档案员的哪次运行、基于哪些任务成果，或哪位成员手动编辑）。非只读成员可编辑或回退到任一版本。

**项目档案员：**

| 项 | 规则 |
| --- | --- |
| 形态 | 平台内置系统 Agent，每个项目空间默认挂载，不占负责人手动添加的 Agent 名额；负责人可停用，停用后档案改为人工维护。 |
| 触发 | 项目任务完成后由平台触发（系统发起，不是 Agent 委派）；同一空间同时只有一个运行，期间完成的任务合并到下一次处理。 |
| 执行载体 | 每个空间一个“档案维护”会话，经 Run/Attempt → DSH，不启用无 Session 入口。 |
| 授权 | 以档案员自己的授权执行，按空间成员交付（第 3 节）。只读本空间的简报、当前档案与新完成的成果，不授予企业数据工具。 |
| 写入 | 只经平台工具提交新档案版本，不直接改写；每次变更写入最近动态。 |
| 人工优先 | 档案员下次运行以最新版本（含人工修改）为基础，不覆盖人工内容。 |
| 不做 | 不读取讨论消息、不读取任务未引用的共享文件、不主动给成员发消息。 |

**风险说明：** 成果不审核、档案自动更新、Agent 默认读取档案三者叠加，会让一次错误产出被当作项目事实传播。控制手段是档案版本化、变更进入动态、成员可纠正与一键回退；如实际使用中错误传播明显，再评估增加“档案变更确认”。

档案员按[通用 Agent 全生命周期模板](../development/agent-lifecycle-template.md)单独记录定义与扩展决策：MCP、持久化等待、记忆、无 Session 入口均不启用。

## 9. 不变的约束

- 所有 Agent 执行经 DSH；DSH 不可用时明确报告，不降级。
- Agent 之间无委派；档案员由平台在任务完成后触发，不是被其他 Agent 派发。Agent 不回应其他 Agent 的消息。
- 跨空间输入、执行前复核、读取复核当前权限、收权覆盖整条链路（3.8）均适用于项目任务与档案员。
- 空间角色不扩大员工的企业数据权限；Agent 能力不随加入空间扩大。
