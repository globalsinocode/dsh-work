# 企业知识库优化方案

**状态：** 决策 KO1～KO7 已确认（2026-11-11，KO6 当日修订）。O1～O3、O5～O12 已实施并合入（#116）；KO10 已于 2026-11-11 在本机完成（重排序生效、最小能力 Key 契约测试通过、门槛复核保持 0.5，见第 10 节），受控生产环境仍须按发布流程复核；O4/KO8 待对比，KO9 待设计，O8 的“校验嵌入模型”按钮未做（见第 8 节）。现行行为以合入后的[企业知识库接入 WeKnora 方案](weknora-knowledge-plan.md)（下称“原方案”）为准。<br>
**更新日期：** 2026-11-11<br>
**依据：** 2026-11-11 对原方案与一期实现的审核（`server/src/modules/knowledge/`、`attempt-dispatcher.ts`、`dsh-acp-runtime-adapter.ts`、`run-event-recorder.ts`、迁移 0115）；本机 WeKnora v0.9.0 的数据库与日志观察，以及 WeKnora v0.9.0 源码（`internal/router/routes_infra.go`、`internal/middleware/api_key_gate.go`、`internal/application/service/chat_pipeline/search.go`）。员工端与管理端页面代码、E2E 用例未纳入本次审核。

## 1. 结论与范围

一期的边界和权限是稳的，不需要调整方向：执行只走 DSH；权限全部在服务端校验，检索结果按本次传入的知识库再核对一次；API Key 加密保存且不会被发到新地址；WeKnora 不可用时有提示词约束、回答说明和审计。

需要优化的是三类问题：

1. **对话检索：** 员工添加了知识库，但实际没有检索到或没有检索时，员工和模型都得不到提示；检索质量受查询词拼接和“每篇只取一个分段”限制。
2. **配置与数据安全：** 嵌入模型 ID 不校验；更换连接地址后，旧知识库仍参与检索；WeKnora 中被人为配置摘要模型后，文档入库会调用对话模型。
3. **授权细节：** 两处与 WK11、5.4 意图不一致的边界情况。

本方案只列优化项和已确认的决策，不改变 WK1～WK20 中已确认的产品范围；需要修订原方案条文的地方在各项中注明。

### 2.1 实测结果（2026-11-11，本机 WeKnora v0.9.0）

方法：查 WeKnora 数据库和容器日志、读 v0.9.0 源码，没有调用接口，也没有改 WeKnora 的任何配置。本机平台使用的 API Key 明文存在 WeKnora 数据库里，没有读取，只看了它的能力范围。

| 待核实项 | 结论 | 依据 |
| --- | --- | --- |
| 入库是否调用对话模型（P3） | **平台建库的路径不调用。** 更正我此前的说法：“知识库1111”的摘要模型不是 WeKnora 自动带上的，而是建库 2 分钟后有人在 WeKnora 前端修改知识库时设置的 | 平台的建库请求不带摘要模型（日志中 `POST /knowledge-bases` 只有名称、类型和嵌入模型）；该库的文档 10:50 入库时日志为“Knowledge base summary model ID is empty, skipping summary generation”，摘要状态记为 failed 但没有外部调用；契约测试等平台建的库同样如此。摘要模型是 10:52 的一次 `PUT`（WeKnora 前端）之后才有的。另一个在 WeKnora 前端建的库，其文档确实生成了 119 字摘要 |
| 重排序是否生效、门槛是否适用（P7） | **（审核时）当前没有生效，0.5 的门槛仍适用于本机。** 2026-11-11 已按 KO10 放开并复核，见第 10 节。 重排序降级的原因是本机代理把 `dashscope.aliyuncs.com` 解析到 198.18.0.127，被 WeKnora 的 SSRF 检查拦截 | 检索日志：`Rerank model … unavailable, searching without rerank … hostname dashscope.aliyuncs.com resolves to restricted IP 198.18.0.127`，结果为 `rerank outcome: model_unavailable`。这正是开发与测试文档里已写明的 `SSRF_WHITELIST` 问题。生效后的分值没有测：要把该域名加入 WeKnora 的白名单并重启，属于改动你的 WeKnora，未经确认没有做 |
| 模型列表接口与 Key 能力（O8） | **原方案规定的最小 Key 读不了模型列表。** `GET /api/v1/models` 需要完全访问或 `manage_models` 能力，`retrieve`、`ingest`、`manage_kbs` 都不行。另外 WeKnora 建库时不校验嵌入模型 ID | 源码 `routes_infra.go`：模型路由组声明为 `apiKeyManageModels(apiKeyFullAccess())`。本机日志：填模型名称建库返回 201，上传后解析失败。**本机平台用的 Key（`dsh-work`）几乎有全部能力**（含 `manage_models`、`chat`），不是原方案 4.2 规定的最小 Key，本机的契约测试和验收因此覆盖不到能力不足的情况 |
| 混合嵌入模型检索（P9） | **不出错，各用各的模型。** 同一次检索里，WeKnora 按嵌入模型分组，每组算一次查询向量，各知识库用自己建库时的模型检索。某组嵌入失败时，带关键词索引的知识库静默降级为关键词检索（平台建的库都带），不报错 | 源码 `chat_pipeline/search.go`（`searchByTargets`）。未实跑：本机只登记了一个嵌入模型，日志里的检索都是 `unique_models=1` |

## 3. 优化项

### 3.1 对话检索

**O1 查了但没有相关内容时给出提示（P1）**

- 提示词：`knowledge_status` 为 `ok` 且没有注入片段时，加入“已查询用户添加的企业知识库，没有找到相关内容。不得把企业制度、规范作为确定事实回答；涉及时请说明所添加的知识库中没有查到，并建议用户换一种问法或确认知识库是否正确。”
- 回答末尾追加：“已查询所添加的知识库，没有找到相关内容，本次回答未引用企业知识。”
- 不新增 `knowledge_status` 取值，Manifest Schema 不变；只改 DSH 适配器的知识段和引用页脚。
- 修订原方案 4.5（`ok` 行“没有结果时不加”）与第 7 节（“检索成功但没有相关结果……不加提示”）。

**O2 添加了知识库但本次没有检索时给出提示（P2）**

判断顺序改为先读会话所选知识库；会话没有所选知识库时行为不变。有所选知识库时：

| 情况 | 现在 | 调整后 |
| --- | --- | --- |
| 连接停用、未配置或 API Key 读不出 | `not_applicable`，无提示 | `unavailable`，沿用第 7 节的提示词、回答说明和审计，原因分类记为 `not_configured` |
| Agent 不具备查看级别（WK14） | `not_applicable`，无提示 | `skipped`，回答末尾提示“当前 AI 同事未开通企业知识，本次未使用所添加的知识库” |
| 员工不具备查看级别 | `not_applicable`，无提示 | `skipped`，所选知识库按“你已无权查看”提示（与现有跳过提示一致） |

- Agent 的情况需要区分跳过原因：Manifest 新增可选字段 `knowledge_skipped_reason`（取值 `agent_not_permitted`），只供引用页脚使用，不进入提示词。
- 修订原方案 4.5 的 `not_applicable` 行与 5.7 的“WK-S2 实现说明”。

**O3 查询词改为先用本次提问，结果不足时再带上一条（P5）**

- 先只用本次提问检索；没有分段达到最低相关度时，再用“上一条提问 + 本次提问”检索一次。两次结果不合并，以有结果的那次为准。
- 话题切换不再被上一条提问带偏；单次追问仍能命中。连续多次追问仍可能查不到，由 O1 的提示兜底。
- 代价：追问场景多一次 WeKnora 调用，执行前等待上限由约 10 秒变为约 15 秒。
- 不调用模型改写查询词，原方案 WK4 的这条约束不变。修订原方案 4.3 的 `query` 行。

**O4 同一文档可以合并两个分段（P6）**

- 每篇文档保留得分最高的两个达到门槛的分段，按原文顺序合并为一条摘录，中间以“……”分隔，总长仍不超过 4000 字；文档数上限仍为 3。
- `knowledge_context` 的字段、上限和编译校验不变；引用快照的摘录与校验值按合并后的内容计算。
- 修订原方案 4.4 第 2 步。
- 实施前先用真实文档做一次对比（合并前后各 10 个问题），确认回答完整度提高而无关内容没有明显增加。

**O5 复核最低相关度（P7）**

- 确认本机 WeKnora 的重排序是否已生效，重跑契约测试的“最低相关度”用例，按结果调整门槛。
- 管理端保存连接或嵌入模型后，在页面提示“更换模型或启用重排序后须复核最低相关度”，对应[开发与测试](../development/development.md)中已有的要求。
- **新增建议（2.1 发现，未列入决策）：** 检索响应带有 `meta.rerank.outcome`，原方案 4.3 一期不记录。本机重排序已静默降级而无人知晓，建议记录最近一次结果并显示在管理端健康状态里，降级时提示。
- 复核时先把重排序模型的域名加入 WeKnora 的 `SSRF_WHITELIST` 并重启（需要你确认），再重跑契约测试的“最低相关度”用例。

**O6 引用页脚文案（P12）**

标题由“参考来源”改为“本次检索到的资料”。不做“只列模型实际引用的文档”：需要解析回答中的序号，模型漏标时会漏列。

### 3.2 配置与数据安全

**O7 防止知识库被配置摘要模型（P3）**

1. 实测结论见 2.1：平台建库默认没有摘要模型，入库不调用对话模型，不需要改建库参数。
2. 部署要求：WeKnora 前端只供运维使用，不得为平台创建的知识库设置摘要模型、问题生成、图谱抽取或多模态模型。原方案 4.1 的验收项由“嵌入模型和重排序模型”扩展为“WeKnora 中登记的全部模型”，同步数据防护方案 D2 与 6.3。
3. 管理端“全部知识库”读取 WeKnora 知识库列表中的摘要模型字段，非空时在该知识库上标“WeKnora 中已配置摘要模型，文档内容可能发往对话模型”。该列表本来就在读取（文档数与更新时间），不增加调用；字段是否稳定返回待在实现时用契约测试确认。
4. 契约测试增加断言：平台新建的知识库没有摘要模型，上传并解析完成的文档摘要状态不是 completed。

**O8 嵌入模型 ID 的校验与提示（P4）**

- 2.1 已确认：最小 Key 不能读取模型列表（需要 `manage_models` 或完全访问），所以不做下拉，也不要求管理员给平台 Key 加 `manage_models`：该能力同时允许新建、修改、删除模型和凭据，对平台只需要“读”来说过宽。
- 保存连接时检查所填值是否是 UUID 形状。不是时提示“这看起来不是 WeKnora 的模型 ID（应为 UUID，不是模型名称）”，要求管理员再点一次确认才保存，不直接拒绝：WeKnora 内置模型的 ID 格式未核实。
- 占位提示不再写“例如 bge-m3”，改为 UUID 的样子，并写明“WeKnora 模型管理中的模型 ID，不是模型名称；查看方法见部署手册”。
- 可选的“校验嵌入模型”按钮：新建一个临时知识库、上传一个很小的文本文件、等解析完成后全部删除，只用 `ingest`、`manage_kbs` 能力就能验证 ID 有效，代价是一次嵌入调用。只在管理员点击时执行；是否做放到 KO-S2 实施时再定。
- 部署手册补充查 ID 的方法（WeKnora 前端“设置 → 模型管理”看浏览器网络请求，或查询 WeKnora 数据库的 `models` 表）。
- 现有模型值无效的知识库（如本机“测试知识库”）已由“需重建”标记覆盖。

**O9 更换 WeKnora 地址时处理现有知识库（P8）**

- 保存的地址与原地址不同且已有未删除的知识库时，确认框提示“现有 N 个知识库属于原地址，更换后将标为不可用”。
- 保存后把这些知识库标为 `unavailable`（状态枚举已有该值）：不参与检索、员工端不显示，管理端标为“原连接已更换”，可删除。会话中已添加的这类知识库按现有跳过逻辑提示。
- 地址改回原值时不自动恢复，由平台管理员在管理端逐个恢复（需要新增“恢复”操作）或重建。

**O10 嵌入模型不一致的知识库（P9）——按 KO6 修订**

2.1 的源码核实推翻了此前的前提：WeKnora 对每个知识库用它建库时的嵌入模型检索，管理员更换连接上的嵌入模型后，旧知识库只要其模型仍登记在 WeKnora 中，就能照常检索，不需要排除。

- 此前写的“检索只传嵌入模型与当前连接配置一致的知识库”已按 KO6 撤销：它会让更换模型后所有旧知识库在重建前全部不可用，而这并不必要。
- “需重建”标记保留，文案改为“嵌入模型与当前配置不同，仍可检索；旧模型从 WeKnora 删除后将失效”。
- 真正的风险是模型无效的知识库（例如填了模型名称）：文档解析失败，没有可检索内容；若有关键词索引，检索不报错。这类库由 O8 的校验和管理端标记覆盖。
- 仍需实跑确认：在 WeKnora 中再登记一个嵌入模型，建两个库各上传文档后一起检索。完成前，原方案第 15 节该条保持“源码已核实，未实跑”。
- 修订原方案 4.6 第 2 条：说明“按建库时的模型检索，更换配置不影响旧库”。

### 3.3 授权

**O11 撤销授权的计数只算有效部门（P10）**

员工撤销授权时，“至少保留一个可见部门”只统计部门仍有效的授权，与可见范围的计算口径（原方案 5.5）一致。

**O12 管理员调整过的授权归管理员（P11）**

平台管理员修改已有授权的“含下级”时，授权来源同时改为管理员，员工不能再撤销。

### 3.4 暂缓

## 9. 与 WeKnora 自带问答的差距与后续方向（2026-11-11，KO8～KO10 已确认）

本节记录对比结论与后续方向，不属于 KO1～KO7 的范围。KO8～KO10 已于 2026-11-11 确认（9.4）；KO10 已在本机完成（第 10 节），KO8、KO9 尚未实施。

### 9.1 现在的调用方式

员工在对话中添加知识库后，每条提问只调用 WeKnora 的检索接口 `POST /api/v1/knowledge-search` 与文档元数据接口 `GET /api/v1/knowledge/batch`。平台丢弃低于最低相关度（0.5）的分段，每篇文档只留最相关的一段、最多 3 篇，写入 Manifest，由 DSH 中的 Agent 生成回答，平台在末尾附引用。WeKnora 的问答、Agent 对话与 MCP 一律不调用（原方案 WK5；AGENTS.md“Agent 执行统一使用 DSH”）。

### 9.2 差距

WeKnora v0.9.0 自带的流式问答（`internal/types/chat_manage.go` 中的 `rag_stream`）依次执行：加载历史 → 查询理解 → 并行检索 → 重排序 → 合并分段 → 取前 K 条 → 数据分析 → 组装提示词 → 模型生成。平台调用的检索接口只走其中“检索 → 重排序 → 合并分段 → 取前 K 条”四步；本机日志显示 WeKnora 实际使用的查询词就是平台拼接的原文，没有改写。

| 环节 | WeKnora 自带问答 | 平台 | 影响 |
| --- | --- | --- | --- |
| 检索、重排序、合并分段 | 有 | 有，同一套引擎 | 相同 |
| 查询理解（结合对话历史用模型改写问题） | 有 | 没有；只在本次提问无结果时拼上一条提问（O3） | 追问、指代效果较差 |
| 数据分析（表格类文档） | 有 | 没有 | 表格、数据类问题差距较大 |
| 送进模型的内容 | 取前 K 条（约 10 条） | 最多 3 篇，每篇 1 段，每段不超过 4000 字 | 答案分散在多处时容易答不全，差距最大 |
| 生成回答 | WeKnora 的提示词与模型 | DSH，带 AI 同事的人设、权限与防注入约束 | 风格不同；平台受权限、审计与数据防护约束 |
| 重排序 | 工作空间默认配置 | 同样使用工作空间默认配置 | 审核时本机因 SSRF 检查而降级（2.1）；2026-11-11 已放开并生效（第 10 节） |

### 9.3 可选方向（按收益从大到小）

1. **放宽注入上限。** 例如每篇保留 2～3 段、最多 5 篇。与 O4 合并处理：先用真实文档对比回答完整度与无关内容；需要同时放宽 Manifest 编译校验中 `knowledge_context` 最多 3 篇的限制，并评估提示词长度与费用。
2. **让重排序真正生效。** 在 WeKnora 中把重排序模型的主机加入 `SSRF_WHITELIST`，然后按 O5 复核最低相关度。本机已完成（KO10，第 10 节）。
3. **补上查询理解。**
   - **方案 A（建议评估）：** 给 DSH 中的 Agent 一个只读的知识检索工具，检索范围仍是会话所选且员工当前可见的知识库，由模型在 Attempt 内自行改写问题、决定是否再查。这推翻原方案 WK4 的“不向 Agent 提供检索工具”，需要重新决策；改写与多次查询都在 DSH 的 Agent Loop 内完成，不违反执行统一原则。还需设计工具调用次数上限、引用快照的写入方式与审计。
   - **方案 B（不建议）：** 平台在执行前单独调用一次模型改写问题。这是在 DSH 之外调用模型，违反 AGENTS.md。
4. **表格、数据类问题。** 走平台已有的 Python 执行或 MCP 取数，不依赖 WeKnora 的数据分析。

**不采用：** 直接调用 WeKnora 的问答接口回答员工。效果最接近，但绕开 DSH，也绕开平台的权限、审计与数据防护，属于 AGENTS.md 明确禁止的第二套 Agent 执行逻辑。

## 10. KO10 本机复核记录（2026-11-11）

**环境：** 本机 WeKnora v0.9.0；嵌入模型 `qwen3.7-text-embedding`、重排序模型 `qwen3-rerank`（均为阿里云在线服务，只用于本地开发，生产须换成内网模型，原方案 4.1）；工作空间默认重排序门槛 0.2。

**操作：**

1. 在 WeKnora 的 `.env` 中把 `dashscope.aliyuncs.com` 加入 `SSRF_WHITELIST`，只重建 app 容器。此前本机代理把该域名解析到 198.18.0.127，被 SSRF 检查拦截，重排序一直降级为 `model_unavailable`。
2. 在 WeKnora 新建只有 `retrieve`、`ingest`、`manage_kbs` 能力的 API Key，同时用于管理端连接配置（替换原先几乎全能力的 Key）与契约测试的 `WEKNORA_CONTRACT_API_KEY`。

**结果：**

- 契约测试两项通过：最小能力 Key 足以完成建库、上传、文档列表、元数据、改标题、预览、下载、重新解析、删除与检索；平台新建的知识库没有摘要模型；检索响应带重排序结果字段（契约测试断言该字段必须存在，未配置重排序时 WeKnora 也返回 `no_model` 或 `disabled`）。
- 重排序生效：相关提问的结果为 `ok`；与文档无关的提问出现 `fallback_top1`：没有候选的重排序模型原始分数达到 WeKnora 的重排序门槛（0.2）时，只保留最高的一条。平台看到的 `score` 是 WeKnora 融合重排序与检索分后的最终分值，与门槛比较的原始分数不是同一口径，所以这一条的最终分值（0.247～0.287）可以高于 0.2；它低于平台的最低相关度 0.5，会被过滤掉。
- 重排序后的分值（3 篇制度文档、12 个提问，即契约测试“最低相关度”用例的 8 个相关提问与 4 个无关提问；用例运行时输出每个提问的分值，不含正文）：

| 类别 | 分值范围 |
| --- | --- |
| 命中目标文档 | 0.624～0.905（最低为“报销要附什么材料”） |
| 相关提问中的非目标文档 | 最高 0.425 |
| 无关提问（天气、写代码、年会、采购订单审批） | 最高 0.394；`fallback_top1` 返回的一条为 0.247～0.286 |

**结论：** 门槛 0.5 保持不变：命中侧最低 0.624，高出门槛约 0.12；非目标文档最高 0.425，低于门槛约 0.08。与未配置重排序时（命中 0.56～0.83，非目标最高 0.45）相比，命中下限升高、非目标上限降低，区分度更好。样本只有 3 篇短文档，换成真实业务文档、内网模型或调整 WeKnora 的重排序门槛后须重跑契约测试复核（同一组提问，输出可直接对比）。

**未覆盖：** 平台对话链路中的重排序结果记录（管理端健康状态的“最近重排序”）没有在本机实际对话中确认，也就没有执行[开发与测试](../development/development.md)要求的复核前置检查（先确认“最近重排序”不是降级）；本次以 WeKnora 日志中的 `rerank outcome: ok` 代替；受控生产环境的复核按发布流程执行。
