# Runtime 执行架构渐进优化方案

**状态：** 进行中；各阶段状态见第 3 节。未标注交付的能力不代表已经可用。<br>
**更新日期：** 2026-10-16（按方案评审修订：范围收窄为执行观测、跨轮上下文与性能；工具定义与读写分类移出；按负责人决定不做中断后继续执行）<br>
**依据：** 当前 Run、Runtime Adapter、调度与恢复代码，以及 2026-09-15 对 Octop 的静态架构分析；尚未进行同条件性能压测。<br>
**执行基线：** macOS 开发与生产环境、Node.js 模块化单体、PostgreSQL、每个 Attempt 一个独立 DSH ACP Worker。

## 1. 目标与边界

让员工在执行过程中看得到进展、长对话通过摘要保留早先的要求；让管理员知道执行慢在哪一段。性能改动只在测量证明有瓶颈时进行。

保留现有职责：平台维护身份、权限、版本、Run/Attempt、调度、业务事务和审计；DSH 负责单个 Attempt 内的 Agent Loop、模型上下文和工具编排。所有改进经过既有 Runtime Adapter，不在业务后端实现第二套模型循环。

约束：

1. 已发布版本、Attempt Manifest 和终态不可覆盖；新一轮消息与重新执行必须明确区分。
2. **不做中断后继续执行（2026-10-16 决定）：** 部署重启、Worker 崩溃、模型或网络临时故障导致的中断，Attempt 以失败结束，员工或调用方重新执行，从头开始。审批等待后继续（PF-04）不受影响。
3. 独立 Worker 继续承担执行故障隔离。
4. PostgreSQL 保存业务事实和受控存储引用；运行状态文件放在受控文件存储，不把正文或二进制塞入数据库。
5. 未经当前 DSH 精确版本和适配链路验证的能力标记为不可用；上游有接口、有事件名称或保存了日志，都不能直接证明本平台支持。
6. 不为这些优化建设插件市场、通用工作流引擎或新的微服务；多节点调度不在本计划范围。

## 5. EX-01：执行过程可见

**已交付：** Attempt 结束（成功或失败）时，Adapter 从 DSH 会话日志读出每次工具调用及结果，用平台工具桥的类型化错误码补全平台工具的失败原因，按顺序发出 `tool.completed` 事件（每个 Attempt 最多 30 条），再发出终态事件。事件只含工具名、调用 ID、状态、错误码和固定中文原因，参数与输出留在会话日志。工作台执行步骤逐条显示，结果核验显示失败数。

**长时间无输出提示（2026-10-17 交付，2026-10-28 由逐步进度取代）：** 原做法是执行中连续 30 秒没有运行事件时显示“已 N 秒没有新的输出，任务仍在运行……”。员工反馈这种提示像故障告警，已移除。

**逐步进度（2026-10-28，EX-PROGRESS-01）：** “正在处理”卡片逐条列出已完成的工具调用与其间的思考段及各自耗时，当前步骤带每秒走动的计时（“正在读取文件 · 12 秒”“正在思考下一步 · 40 秒”），标题旁显示本次已用时间；结束后在回答上方收起为“已完成 N 个步骤（调用工具 M 次）”，可展开。步骤带来源事件类型、服务端事件时间，调用结果步骤另带同一调用的开始时间；已结束的耗时取服务端时间之差，进行中的计时按收到实时事件时测得的时钟差换算到本机。DSH 0.1.2-rc.1 只在一次模型调用结束后发出事件，平台收不到“正在思考”的信号，没有工具在运行即视为模型在思考；模型生成期间只有计时在走，要在生成中显示文字需 DSH 流式输出。

**实时工具步骤（2026-10-17 已交付）：** 适配器把 DSH 的 `tool_call` 转为 `tool.started`、把 `tool_call_update` 转为带 `live: true` 的 `tool.completed`；平台工具失败的类型化原因只取同一调用 ID 的工具桥结果。Attempt 结束时仍按会话日志对账：已实时完成的调用不再发出，未收到实时结果的调用照常补齐（含“未收到调用结果”），每个 Attempt 合计最多 30 条；`run.completed` 的调用总数与失败数仍以会话日志为准。员工端同一调用只占一行，“正在调用”原地更新为结果，“正在处理”提示显示“正在调用 工具名”；Run 结束后仍无结果的“正在调用”显示为“未收到调用结果”。事件只含工具名、调用 ID、状态与固定原因，不含参数和输出。

**剩余：**

- **验收：** 真实 DSH 下一个读取不存在文件的任务，执行步骤出现失败的工具调用且任务仍可完成（EX-TOOL-01 的 P2）；实时模式下事件不重复、顺序正确。

## 6. EX-02：跨轮上下文

**已交付：** 超时中断保留的部分回答带入重试；员工“继续修改”把上一轮成果作为只读输入挂载，同会话同名输出登记为下一版本（EX-ARTIFACT-01，2026-10-16 已通过本地真实 DSH 验收，范围见第 8 节）。

**对话摘要为主、裁剪兜底（2026-10-16 代码已交付；EX-CONTEXT-01 已通过本地真实 DSH 验收，范围见第 8 节）**

现行多轮输入上限（12 条、24000 字符）是平台自设的保守值；超出时从最早的消息开始静默丢弃，首条消息里的目标与约束最先丢失。改为以下结构：

1. **每轮带入三段：**
   - **首条用户消息原文**：目标与约束不经模型转述；
   - **中间部分的摘要**：记录已确认的要求、结论、引用过的数据与成果；
   - **最近若干轮原文**：保留当前话题的细节。
   三段合计受一个总上限约束，按模型上下文窗口 256K token 设定（见下方预算）。
   **预算（模型上下文窗口 256K token，2026-10-16 确定）：** 中文按每字符约 1 token 保守估算。窗口还要容纳系统提示词、Skill 指令、知识与经验摘录、输入文件（最多 1 MB 抽取文本）、执行中的工具结果和输出，因此对话历史只占约四分之一：

   | 项 | 上限 |
   | --- | --- |
   | 对话历史总量（三段合计） | 64,000 字符 |
   | 首条用户消息 | 8,000 字符，超出时保留开头部分 |
   | 摘要 | 8,000 字符 |
   | 最近原文 | 其余额度，按时间从新到旧填入 |
   | 触发摘要的阈值 | 历史原文超过 48,000 字符（总量的 75%），留出生成摘要的时间 |

   消息条数不再单独限制（现行 12 条上限取消），以字符总量为准。上述数值放在平台配置中，可按实际 Token 用量（EX-00）调整；Schema 的 `maxItems: 12` 与编译器的 24000 字符检查同步改为新预算。输入文件与历史合计可能接近窗口上限，EX-00 需统计实际每轮 Token 以验证预算。
2. **生成方式：** 会话的历史超过阈值后，在该轮 Run 结束时于后台发起一次摘要执行，不阻塞员工下一条消息。摘要为增量方式：以上一份摘要加新增消息生成新摘要，记录覆盖到的最后一条消息。摘要执行走既有 Run/Attempt → Runtime Adapter → DSH，使用新的系统用途（暂定 `session-summary`），不在平台直接调用模型；它没有工具、不读文件、只读取本会话消息。
3. **存储：** 新增摘要表（迁移），记录租户、会话、覆盖的消息范围、摘要正文、摘要值、来源 Run 与生成时间；每个会话只有一份当前摘要，旧摘要保留以便追溯。摘要正文按会话消息同等对待：会话被移除后不再读取，不进入审计正文。
4. **运行配置：** Runtime Manifest 增加 `conversation_summary`（正文、覆盖范围、摘要值），Schema、编译器与 Adapter 提示词同步修改；提示词说明它是平台生成的历史摘要，原文优先于摘要。
5. **权限：** 摘要只在其所属会话中使用。个人会话按会话作者读取；团队会话的讨论全员可见，摘要对现任成员共用；读取时与会话消息同样复核当前权限。
6. **容量：** 后台摘要占用 Worker，设独立并发上限并为交互任务保留余量（与自动任务的车道规则一致）；排队过久的摘要可丢弃，下一轮再生成。
7. **兜底裁剪：** 摘要尚未生成、生成失败、DSH 不可用或摘要过期（覆盖范围之后的新消息超过上限）时，退回裁剪：保留首条消息，从第二条开始丢弃最早的消息，直到满足上限。兜底过程不向员工展示提示。
8. **“继续”的语义（2026-10-17 已交付）：** 员工只发一句“继续”（含“请继续”“接着做”“continue”等，带标点亦可）且没有附件或已引用成果时，界面先问清意图：当前一轮失败或已停止且允许重新执行时，可选“重新执行上一轮”（原问题从头再跑）或“作为新消息发送”；当前一轮成功并留下可引用成果时，可选“继续修改《成果》”（作为只读输入引用，最多 5 个）或“作为新消息发送”。关闭对话框即取消，输入保留；其他情况照常发送。系统提示声明历史消息与摘要中的“同意”“可以”“继续”只是当时的对话内容，不构成对工具调用或外部动作的授权。
9. **权限复核：** 带入的历史、摘要、成果与文件逐项复核当前身份与对象权限；跨用户、跨空间、已撤权的内容不因历史对话重新进入模型。

**风险与约束：** 摘要可能遗漏细节或概括错误，错误会随后续每轮带入。因此首条消息始终保留原文，最近几轮保留原文，摘要只覆盖中间部分；摘要执行的模型用量计入用量统计。

**验收：**
- 超过阈值的长对话生成摘要，后续轮次的 Manifest 包含首条原文、摘要与最近原文，总量不超过上限；
- 首条消息与中间轮次中给出的约束，在第 20 轮之后仍被遵守（真实 DSH 用固定会话验证）；
- 摘要失败时自动退回兜底裁剪，任务正常执行；增量摘要覆盖范围连续、不重复；
- 并发发送消息时只生成一份当前摘要；团队会话中非成员读不到摘要，会话移除后摘要不再使用；
- 摘要执行不挤占交互任务的容量；
- 真实 DSH 完成“两轮修改同一成果”并下载两版核对差异；两个用户使用同一 Agent 时上下文不串用。

## 7. EX-04：按瓶颈优化执行开销

只优化 EX-00 证明占比明显的阶段，每次只验证一个有明确收益假设的改动。

| 测量结果 | 优先尝试 | 必须保留的边界 |
| --- | --- | --- |
| Skill 读取和准备占比高 | 缓存按摘要锁定的不可变包内容，减少重复读取 | 当前权限每次检查；不用可写硬链接把工作区连到共享包 |
| Schema/目录构建重复 | 按精确 Runtime/Tool 版本缓存描述和编译结果 | 不复用其他用户的授权结论或凭据 |
| Worker 启动占比高 | 先减少初始化中的重复工作，再评估预热 | 只有上下文、环境、连接、缓存和文件可彻底隔离及清理时才引入 Worker 池，并设资源上限与空闲回收 |
| 大部分等待来自排队 | 根据模型配额、CPU、内存和磁盘调整容量与准入 | 不以增大并发掩盖失败率、取消延迟或内存峰值 |
| 大部分等待来自模型或企业工具 | 缩小上下文规模、工具查询范围与结果大小 | 不把 Provider 延迟误归因于 ACP |

验收使用 EX-00 相同的环境、输入、版本、样本量和冷热条件对比；收益未达预算，或隔离、取消、结果正确性退化时不启用。

**并发 1 结论（2026-10-17）：** 按第 4 节阶段占比，对应上表“大部分等待来自模型或企业工具”。上下文规模已由 EX-02 的摘要与兜底裁剪约束，平台可控阶段合计约 1%，暂无值得改的平台环节，本阶段不做代码改动。其余两项都不在平台代码内：
- ACP 初始化约 1.2 s 发生在 Worker 内的 DSH 启动中。Worker 池在当前隔离约束下不可行：每个 Attempt 的系统提示、允许工具、审批模式与平台工具连接都在启动 Worker 时以环境变量传入，预热的 Worker 不能复用。只有 DSH 支持启动后再注入会话配置时才重新评估，作为上游需求记录。
- 回答没有逐字输出是 DSH 的行为（见第 4 节能力核实），平台无法提前展示。执行中的可见性由实时工具步骤与长时间无输出提示补足。

**预算（改动前确定）：** 以后若有改动，只在目标硬件上以相同场景对比，并满足：并发 1 的 Adapter 全程 p50 不劣于 10.6 s；并发 5 下失败率不高于并发 1，单 Worker 结束时 RSS p95 不超过 300 MB；为交互任务保留的执行位不被占用。

**待测量（目标硬件）：** 用 `pnpm probe:concurrency` 测 1/3/5 个 Worker 同时执行的耗时与 Worker 树内存峰值；在平台上同时发起 50 个员工任务，用 `pnpm report:run-timings --since <开始时间>` 输出排队等待、端到端与失败率，并记录 CPU、磁盘与模型配额。若排队等待成为最大阶段，按上表“大部分等待来自排队”调整容量与准入，再按预算验收。
