# Runtime 执行架构渐进优化方案

**状态：** 待实施；本文记录优化方向、实施依赖与验收条件，不代表运行能力已经交付。<br>
**更新日期：** 2026-09-15<br>
**依据：** 对 Octop 的静态架构分析，以及当前 dsh-work 的 Run、Runtime、工具目录与恢复代码；尚未进行两项目同条件性能压测。<br>
**范围：** 执行观测、工具适配、上下文延续、受控恢复和有测量依据的性能优化。<br>
**执行基线：** macOS 开发与生产环境、Node.js 模块化单体、PostgreSQL、每 Attempt 独立 DSH ACP Worker。

## 1. 目标与边界

让员工能连续完成文件分析、文档修改和多步业务任务，让管理员能判断工具为什么不可用、执行慢在哪一段、失败后能够怎样继续，同时降低接入一个已支持类型工具所需的重复开发。

保留现有职责：平台维护身份、权限、版本、Run/Attempt、调度、业务事务和审计；DSH 负责 Agent Loop、模型上下文和工具编排。所有改进经过既有 Runtime Adapter，不在业务后端实现第二套模型循环。

本计划遵循以下约束：

1. 已发布版本、Attempt Manifest 和终态不可覆盖；新一轮消息、重新执行、从检查点恢复必须明确区分。
2. 独立 Worker 继续承担执行故障隔离；平台工具所在业务进程、文件权限、网络和凭据边界仍需分别验证。
3. PostgreSQL 保存业务事实、索引与受控存储引用。包文件、脚本和拟引入的运行状态文件保存在受控文件存储，不把它们作为正文或二进制塞入业务数据库。
4. 未经当前 DSH 精确版本和适配链路验证的能力标记为不可用。上游有接口、已有事件名称或保存了日志，都不能直接证明本平台支持恢复。
5. 优先复用现有模块、端口、测试和页面；不为这些优化建设公共插件市场、通用工作流引擎或新的微服务。

## 2. 已核对的当前实现

| 当前事实 | 优势或问题 | 源码依据 |
| --- | --- | --- |
| 每个 Attempt 创建目录、准备输入和 Skill 文件、启动 Worker，并新建 ACP Session | 隔离边界清楚；存在重复初始化和文件处理，成本尚未测量 | [Runtime Adapter](../../server/src/modules/runtime/dsh-acp-runtime-adapter.ts)、[ACP Client](../../server/src/modules/runtime/acp-json-rpc-client.ts) |
| 多轮输入传递 user/assistant 历史消息 | 可以继续对话；超时中断的 Attempt 会把已生成部分回答落库并作为普通历史进入重试 Attempt（上下文延续，非步骤恢复）；没有复用原 ACP Session，不能等同完整工具状态和执行步骤恢复 | [Runtime 类型](../../server/src/modules/runtime/runtime-types.ts)、[历史输入构造](../../server/src/modules/runtime/dsh-acp-runtime-adapter.ts) |
| 重启恢复重新调度排队 Attempt，活动 Attempt 标记 SERVICE_RESTARTED；重试新建 Attempt | 业务状态可收敛；不具备已经验证的中断步骤续跑 | [Run Repository](../../server/src/modules/run/postgres-run-repository.ts)、[运行编排](../../server/src/modules/run/run-orchestration-service.ts) |
| ACP 权限请求通过策略回调决定；未配置回调时默认拒绝，approval_mode 为 never 时走一次允许 | 有请求与结果事件；没有产品级持久等待、审批收件箱和跨重启续跑闭环 | [权限请求处理](../../server/src/modules/runtime/dsh-acp-runtime-adapter.ts) |
| 工具候选由 DSH 描述与平台策略合成，未知工具默认不接入；输出 Schema 存在空对象 | 已有发现和治理基础；上游加载、平台适配、用户授权需要更明确的状态及契约 | [工具目录](../../server/src/modules/tool/dsh-built-in-tool-catalog.ts) |
| 平台工具桥使用通用处理器，但错误主要返回字符串和统一 HTTP 状态 | 复用传输有效；不同工具的错误、取消、重试提示和结果展示还可统一 | [平台工具桥](../../server/src/modules/runtime/platform-tool-bridge.ts) |
| 数据库锁住 Runtime 容量并原子认领 Attempt；运行以单节点为基线 | 已有准入控制；多实例租约、失联接管和跨节点调度不能直接假定存在 | [调度与恢复](../../server/src/modules/run/postgres-run-repository.ts) |

这些是优化依据，不代表上述机制全部有缺陷。例如启动 Worker 有成本，不等于它已经是主要瓶颈；现有权限限制也不能通过放开全部 DSH 工具来消除。

## 4. EX-00：执行观测与能力基线

### 改进内容

在现有运行编排和 Adapter 中采集分段指标，通过统一 Run/Attempt/trace 关联。首先扩展必要的事件元数据和指标，不预设另建监控服务。

| 指标 | 测量边界与用途 |
| --- | --- |
| 准入准备 | 请求受理到排队记录就绪，定位鉴权、版本解析和输入准备 |
| 排队等待 | 排队就绪到容量认领成功，区分容量不足和实际执行缓慢 |
| 资源准备 | Attempt 目录、输入挂载、Skill 校验和文件准备耗时与字节数 |
| Worker 启动 | 启动进程到 ACP 初始化、Session 就绪，分别记录关键点 |
| 首次输出 | prompt 提交到首个可展示回答事件；另记受理到首个可展示回答的用户等待时间 |
| 执行与工具 | prompt 执行总耗时、工具调用分项、次数和错误；工具耗时可能重叠，不能相加当作总时长 |
| 成果与结束 | 成果收集、最终事件落库、取消到回收完成的耗时 |
| 资源与可靠性 | 业务进程/Worker 的 CPU、RSS、文件量、失败率、超时率、待处理数量 |

同进程耗时用单调时钟；跨进程用关联标识和可校准的时间点，不直接相减无基准的时钟。没有观测到的指标保留缺失原因，不填 0；平台首次展示时间也不能命名为模型 Provider 的首 Token 时间。

基线覆盖纯文本、带输入文件、带 Skill、两轮修改同一成果、取消和故障任务。按 [开发与测试](../development/development.md) 使用 1/3/5 并发与 50 Run 排队场景；受控 Runtime 和真实 DSH 分开记录。开发兼容版本与生产正式 Lock 分开验证。

每组记录硬件、应用 revision、DSH 精确版本、模型路由、文件规模、并发、冷热条件、样本量、p50/p95、错误和资源峰值。真实模型测试设定次数与用量上限；失败样本计入分母，不以重试后的成功覆盖失败。

同时核对当前 DSH 的 Session 导出/加载、检查点、工具调用标识、人工审批暂停与恢复能力。区分“上游声明”“适配器可调用”“真实链路已验证”，不要猜测不存在的 ACP 方法。

### 验收与产物

- 同一任务可以区分排队、准备、启动和执行阶段；失败、超时与取消也有对应记录。
- 指标不含原始提示词、文件正文、凭据或内部推理；排障页面默认只显示阶段与简短原因。
- 在本阶段结果中确定后续优化的延迟和资源预算，再开始性能改动；预算不能在改动后为通过验收而降低。
- 提交可复现采集入口、基线结果、能力验证表和优先瓶颈结论。无数据时不宣称 Octop 或 dsh-work 更快。

## 5. EX-01：工具适配与结果规范

### 改进内容

在现有 `modules/tool` 和 `modules/runtime` 中统一重复的定义与适配，保持“平台维护执行器，工具声明能力”的边界。已有执行器类型的工具应能复用通用接线；新增执行器或特殊行为仍需开发与验证。

| 契约部分 | 最小内容 |
| --- | --- |
| 标识与兼容性 | 逻辑名称、精确 Tool Version、Schema 版本、适用的 Runtime 能力 |
| 输入 | 输入 Schema、字段约束；身份、Workspace、凭据及数据范围由服务端注入 |
| 执行 | 平台批准的执行器与绑定引用、超时、取消、资源限制、副作用和幂等语义 |
| 权限 | 所需角色/对象/数据范围、固定审批要求、当前 Attempt Allowlist；声明不等于授权 |
| 输出 | 可解释文字、结构化数据、成果引用和可选展示类型；按版本校验并限制大小 |
| 错误 | 稳定错误码、可读原因、可执行下一步及脱敏诊断引用；可重试标记不自动触发重试 |

以上是待落实的契约内容，不是已经存在的新 API。实施时以类型、Schema 和行为测试为唯一结构定义，避免在配置、目录和 UI 各维护一份。

工具目录分别展示：Runtime 是否加载、平台是否适配、是否已纳入目录、当前 Agent/用户是否获授权、必要依赖是否健康。这些是不同维度，不能合并成一个“已安装”状态。Runtime 不可用时说明列表是否来自缓存，不将静态候选当作当前能力证明。

结果先支持平台内置的文本、表格、文件、进度和操作结果组件。模型说明、工具结果和技术诊断各自保留来源；失败在原对话或操作卡片中持续可见，toast 不能替代结果记录。成果通过授权引用下载；动作按钮重新鉴权并绑定目标版本，不执行工具结果中任意传入的 URL 或脚本。

### 首个贯通样例与验收

选择平台已经支持的文件读取、生成或编辑能力，在原执行器上完成一次“发现 → 接入 → Agent 授权 → DSH 调用 → 表格/文件结果 → 失败说明”的样例，并提供有效及无效输入、期望结果与验证入口。

- 同一个定义用于目录描述、模型可见 Schema、执行校验和结果投影；普通工具接入不新增业务 Agent 专用分支。
- 未授权、Schema 错误、缺少依赖、超时、取消、输出超限均有不同的可观察结果；不再统一误报为包解析失败。
- 安装或发现工具不会扩大已有 Agent 权限；上游工具变化不会覆盖旧 Tool Version。
- 原有 Skill 安装、`activate_skill` 和 `python_execute` 保持相同授权语义和执行链路。
- 工具注册规范与样例由此阶段交付；员工 Tool 候选审核、发布规则随准入流水线另行设计，现阶段按[差异清单](../development/agent-design-gap-analysis.md)登记。

## 6. EX-02：跨轮上下文与成果延续

### 改进内容

先补全新一轮执行所需的业务上下文，不把常驻 Worker 或复用旧 Session 作为前置条件：

1. 在当前 Session 内关联已确认的用户要求、已提交回答、必要的工具结果摘要、来源版本和成果版本。
2. 后续修改文档时，将明确选中的旧成果作为只读输入准备到新 Attempt；新修改产生新成果版本，旧文件保持不变。
3. 上下文来源逐项复核当前身份与对象权限；跨用户、跨空间、已撤权或已失效内容不可因历史对话而重新进入模型。
4. 长对话需要裁剪时保留来源、用户约束和待处理问题。若生成语义摘要，由 DSH 在既有链路内完成；平台只负责筛选、预算和记录，不自行调用模型。
5. 历史中的“同意”“继续”仅作为历史内容，不作为新工具调用的授权。来源不完整或指代不唯一时，在对话中澄清。

同一 Session 沿用既有版本绑定规则；平台发布新 Agent 不得静默替换该 Session 的版本。用户明确选择升级后走版本和兼容性检查，旧上下文不能自动视为与新版本兼容。

### 验收与产物

- 第一轮生成 Markdown/CSV，第二轮要求修改指定部分，真实 DSH 能读取正确旧成果并输出新版本；下载两版能核对差异。
- 用户说“继续”时，助手能区分继续讨论、修改成果与重新执行失败任务，不谎称恢复了旧执行步骤。
- 两个用户使用相同 Agent 时，文件、摘要和上下文不串用；排队后撤权也无法继续读取旧内容。
- 长对话裁剪、文件移除、多版本文件指代和无法恢复的上下文都有可理解反馈。
- 此阶段的通过仅证明跨轮业务连续性，不标记为 checkpoint 恢复通过。

## 7. EX-03：受控检查点与人工审批

### 7.1 先固定“继续”的含义

| 动作 | 目标语义 | Attempt 与授权 |
| --- | --- | --- |
| 新一轮消息 | 用已授权上下文处理新的用户输入 | 新 Run/Attempt；按当前权限准备输入 |
| 重新执行 | 对失败或取消的任务再做一次 | 同一 Run 新建 Attempt；不冒充从旧步骤继续 |
| 存活 Worker 内审批后继续 | 对一个明确待批工具调用作出决定 | 仅非终态 Attempt 可继续；拒绝、撤权、超时和取消均终止对应等待 |
| Worker 中断后恢复 | 从已校验的安全检查点继续原任务 | 旧 Attempt 保留终态；新 Attempt 关联来源检查点并重新授权 |

表中后两项是目标行为。实施前必须同步设计运行状态机、API、Schema、Worker 回收和事件投影；不能因已有 `approval.required` 事件就直接增加“恢复”按钮。

### 7.2 EX-03A：限定场景的检查点恢复

先限定为已批准的只读查询和隔离工作区成果处理，验证 DSH 导出和恢复能力后再开放：

- 由 DSH 管理检查点内容和 Agent Loop 位置。平台记录租户、用户、空间、Session、来源 Attempt、运行内核/协议版本、能力与输入摘要、工具执行边界及状态文件引用。
- 状态文件使用受控存储键、内容摘要和原子写入；数据库只记录元数据。路径不可由模型或浏览器指定，原始状态不进入普通对话、前端响应或通用审计日志。
- 恢复前重新检查当前权限、Agent/Skill/Tool 版本、模型路由与配置、输入及成果引用、DSH 兼容性。检查点依赖范围不能完整确定、权限失效或配置发生不兼容变化时拒绝恢复，说明重新准备任务的路径。
- 对已完成工具调用关联稳定调用标识、结果引用和业务提交状态；工具执行成功但结果尚未确认的窗口必须可识别。副作用状态不明确时暂停并要求核验，不自动重复调用。
- 文件成果以提交记录及摘要判断是否完成；业务操作复用领域幂等机制。恢复不保证任意外部副作用恰好执行一次，也不开放 ERP/MES 写操作。
- 恢复请求使用幂等标识和事务认领，同一请求只创建一个恢复 Attempt。旧 Worker 的迟到事件和工具结果不能覆盖新 Attempt。
- 检查点需要保留期、访问审计和引用保护；备份恢复必须验证数据库引用与状态文件一致，仍被运行引用的文件不可清理。

验收至少注入四个中断点：工具调用前、工具提交后但结果确认前、结果确认后、最终回答提交前。检查取消、服务重启、重复恢复、版本变化、检查点损坏和撤权，证明不会串用状态、重复提交成果或产生虚假的“已继续”。

若当前锁定 DSH 不支持所需协议，交付能力缺口与同一 DSH 链路内的补齐方案；维持现有失败收敛，不解析日志拼装另一套 Agent 执行循环。

### 7.3 EX-03B：持久化人工工具审批

以一个确有人工确认需要的受控工具为先导，完成以下闭环后才开放：

- 审批记录绑定具体 Attempt、Tool Version、参数摘要、目标对象、风险范围、配置 revision 和有效期。批准一次操作不扩大后续工具权限。
- 审批资格和执行者当前权限分别校验；参数、目标或配置变化使旧批准失效。重复点击、取消与批准并发时只产生一个有效结果。
- 对长时间等待确定容量、超时和 Worker 回收规则：只有 DSH 证明能够安全挂起并恢复时才释放 Worker；否则设有界等待，超时给出明确结果。
- 服务重启、批准响应丢失、审批人失权和用户取消都有持久化结果；审批成功与工具执行成功分别展示。
- 业务负责人发布审核、管理助手操作计划确认与本节的 ACP 工具审批分别维护语义，不能互相充当批准依据。

验收包含批准、拒绝、过期、撤销、重复请求、重启、并发取消、权限变化以及工具执行失败。未经这些验证的工具继续显示不兼容，不降低审批策略以通过试运行。

## 8. EX-04：根据测量优化开销

优先优化已证明占比明显的阶段，不预先要求 Worker 池、常驻会话、外部队列或多节点。每次只验证一个有明确收益假设的改动。

| 测量结果 | 优先尝试 | 必须保留的边界 |
| --- | --- | --- |
| Skill 读取和准备占比高 | 缓存摘要锁定的不可变包内容，减少重复读取；结合完整性策略准备只读资源 | 当前权限每次检查；不能用可写硬链接把 Attempt 工作区连接到共享包 |
| Schema/目录构建重复开销明显 | 按精确 Runtime/Tool 版本缓存描述和编译结果 | 不复用其他用户的授权结论或凭据；版本变化可失效 |
| Worker 启动占比高 | 先减少初始化中重复工作，再评估预热 | 只有上下文、环境、连接、缓存和文件可彻底隔离及清理时才引入池；有资源上限和空闲回收 |
| 大部分等待来自排队 | 根据模型配额、CPU、RSS 和磁盘调整容量与准入 | 不以增大并发掩盖失败率、取消延迟或内存峰值 |
| 大部分等待来自模型或企业工具 | 优化上下文规模、工具查询范围、超时与结果大小 | 不把 Provider 延迟误归因于 ACP；不绕过授权或隐式切换执行引擎 |

验收使用 EX-00 相同的环境、输入、版本、样本量和冷热条件，对比约定指标及失败率。若收益未达到事先确定的预算，或隔离、取消、结果正确性退化，则不启用该优化。

多节点扩展单独评审租约、领取所有权、失联回收、事件归属和存储可达性，不作为本计划的默认后续阶段。新建多个 Node 实例不等于具备分布式运行能力。

## 9. 验证、发布与记录

每次只选择受影响的检查，命令以 [开发与测试](../development/development.md) 和 [package.json](../../package.json) 为准：

| 改动 | 验证入口与证据 |
| --- | --- |
| 文档与契约 | `pnpm verify project`；涉及 Schema 时补充 `pnpm verify contracts runtime`；架构改动执行 `pnpm check:architecture` |
| Runtime 与取消 | `pnpm test:m1`、`pnpm test:m5:faults`，按改动扩展真实 DSH 探针 |
| 工具、成果及权限 | 相应 Tool/File 集成套件、`pnpm test:m5:security`；使用专用可丢弃 PostgreSQL |
| 持久化恢复和容量 | `pnpm test:m5:faults:integration`、`pnpm test:m5:capacity:integration`，补充阶段专属故障注入 |
| 用户操作、等待与恢复页面 | 按 [项目工作规范](../../AGENTS.md) 先补 `e2e/TEST-CATALOG.md`，再执行 Spec → Code → Verify → Test → Green |
| macOS 真实执行 | 同一 Run/Attempt/DSH 链路、对应 Runtime Lock、受控身份和数据；模型、权限、取消、文件结果及必要重启演练留证 |

P0 原型、P1 受控集成、P2 真实验收分别记录。数据库测试不得使用开发业务库或生产库；真实模型运行记录次数与用量。一次模拟测试、版本探针或 UI 操作成功不能代表真实恢复已通过。

每阶段交付记录至少包含：任务编号、适用版本、实现与契约变更、验证层级、证据链接、失败及限制、回滚方式、实际部署状态。状态依次区分“待实施、开发中、验证中、代码已交付、真实环境已验收”；条件不满足则记录原因，不将待验证项勾为完成。

发布新增恢复能力前验证旧 Run/事件的读取和数据库迁移兼容性；回滚版本无法处理的等待记录必须先有明确处置方案。性能优化回滚应保留历史成果、Manifest 和运行证据。
