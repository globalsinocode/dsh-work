# 企业组织架构方案（第一期：本地维护）

**状态：** 待评审，尚未实施。本文所述能力在实施并通过第 8 节验收前均不可用。<br>
**更新日期：** 2026-10-31<br>
**依据：** 现有身份与授权模型（迁移 0001、0014、0015、0016；`server/src/modules/identity/`、`server/src/modules/authorization/`）、[功能规则](../development/feature-rules.md)。

## 1. 现状与目标

**现状：** 平台不支持组织架构树。

- `users.department_id` 是一个自由文本字段，没有部门表，也没有上下级关系。独立账号由管理员新建时手工填写部门（平台没有员工自助注册）；管理端运营统计用 `departmentLabel()` 写死了两个部门名。
- 授权只看三类对象：`user_roles`（角色），`data_scope_grants` 中 `subject_type` 为 `user` / `role` / `workspace` 的数据范围，以及项目空间成员角色。没有按部门授权，也没有向下级继承。
- 系统已有一个“部门负责人”角色（`role-department-manager`，角色代码 `department_manager`，迁移 0014）。员工持有该角色或 `workbench:manage` 权限时，员工端显示为“部门负责人”（`session-repository.ts` 中的 `primaryRole`）。这个角色没有绑定到具体部门。

**目标（第一期）：**

1. 管理员在管理端维护本企业的部门树，并把员工分配到部门；
2. 管理员可以把角色授给某个部门（可选包含下级部门），员工的部门变化后权限随之变化（ORG-S2 只授角色，见 OD7）。

钉钉通讯录同步放到后续阶段，见附录 A。

## 3. 边界

- **始终可用，部门只由组织架构维护。** 组织架构不随是否配置 AI Hub 而关闭（账号密码登录在任何配置下都可用）。AI Hub 账号登录与目录同步不再写入员工的显示部门，员工的“部门”只由组织架构维护（2026-11-03 调整，原“OIDC 模式下不可用”的规定作废）。
- **授权由平台管理员决定。** 部门树、成员关系和部门授权都只能由平台管理员修改，每次变更写审计。
- **手填的部门不产生权限。** 历史上手工填写的部门文本不会映射为部门成员关系，部门成员关系只能通过部门树分配。
- **不新增 Agent 执行路径。** 本方案只涉及目录和授权，不涉及 Agent 执行。

## 4. 数据模型

| 对象 | 说明 |
| --- | --- |
| `org_departments` | `tenant_id`、`id`、`parent_id`、`name`、`path`（从根到本部门的 ID 路径，用于查询子树）、`sort_order`、`status`（active / removed）、`created_at`、`updated_at`、`updated_by`。每个企业有且只有一个根部门，以企业名称命名，由数据库迁移为每个企业创建（新建企业时同时创建），打开页面不写入数据；唯一约束保证一个企业只有一个根部门。 |
| `org_department_members` | `tenant_id`、`department_id`、`user_id`、`is_primary`、`added_by`、`added_at`。员工可以属于多个部门，每个部门一行；员工属于任何部门时，必须恰好有一个主部门。 |
| `org_department_grants` | 部门授权（迁移 0114）：`department_id`、`role_id`、`include_descendants`、`status`（active / invalid）、`granted_by`、`created_at`、`invalidated_at`；同一部门同一角色只有一条有效授权。 |
| `users.department_id` | 继续作为显示文本，由平台写入主部门名称；没有主部门时为空，沿用现有“未分配部门”的显示。不考虑历史数据：上线迁移清空所有独立账号员工现有的部门文本（AI Hub 账号由目录同步维护，不清空）。现有按该字段显示、搜索和统计的代码可以继续使用。 |
| `user_roles.source_key` | 迁移 0016 的约束 `source_key = 'local'` 放宽为 `'local'` 或 `'department:%'`。 |

## 5. 部门树维护

管理端新增“组织架构”页，打开即进入部门树维护（没有首次使用的引导或导入步骤），只有平台管理员可以操作。不考虑历史数据：现有员工的部门文本在上线时清空，不转为部门，所有员工从“未分配部门”开始，由管理员新建部门并分配：

- **部门：** 新建、改名、调整排序、移动到其他上级部门（不能移动到自己或自己的下级之下）。删除部门要求该部门没有下级部门、也没有成员；部门上的授权随删除一起失效（6.3）。
- **成员：** 在部门中添加或移除员工（添加时可多选，可只看未分配部门的员工），指定主部门；也可以在员工详情中调整其所属部门。员工可以不属于任何部门，此时只有直接授予的权限。移除主部门时，如果员工还属于其他部门，要求管理员指定新的主部门。
- **员工账号：** 仍由管理员创建（平台没有员工自助注册；初始化首个管理员的命令不再写入部门文本）。管理员新建账号时，“部门”改为从部门树中选择（可以不选），选中的部门即为该员工的主部门，不再接受自由填写的部门文字。
- **显示字段：** 员工的主部门变化时，平台同步写入 `users.department_id`；该字段不再接受员工或管理员直接编辑。

移动或删除覆盖较多员工的部门时，确认框显示受影响的人数。部门移动、成员变化和删除都会按 6.2 触发权限重算。

## 6. 部门授权

### 6.1 生效方式：写入现有授权表

现有代码中有多处直接读取 `user_roles`（工作台授权、Runtime 授权、项目空间公共数据范围、管理员判断等）。部门授权按成员关系展开后写入这张表，这样读取点仍然只查 `user_roles`，不需要理解部门树和继承关系；但读取点中按 `source_key` 过滤的条件需要修改（6.4）。

- 角色：为覆盖到的每个员工写入 `user_roles`，`source_key = 'department:<grant_id>'`。
- “覆盖到的员工”指该部门的成员；授权包含下级时，还包括所有下级部门的成员。
- 管理端显示每条授权的来源（直接授予 / 来自某部门），部门来源的授权只能在部门授权中修改。

### 6.2 重新计算与权限版本

以下情况会触发对受影响员工的重新计算：部门授权的增删改、员工所属部门变化、部门在树中移动或被删除。重新计算在同一事务中对比计算前后的展开行，只写入差异，并写一条审计（原因：部门授权变更 / 部门调整 / 成员变化）。

迁移 0016 的触发器在 `user_roles` 每次增、改、删行时都会把 `local_authorization_version` 加 1，本方案不修改这个触发器。因此展开行有变化、但有效权限没变时，版本也会递增。例如员工从 A 部门调到 B 部门，两个部门授的是同一个角色，版本会加两次。版本递增在现有代码中只会让会话和执行按当前权限重新校验，不会让员工退出登录，所以接受这一行为。

### 6.3 风险与约束

部门授权意味着调整某人的部门就会间接改变其平台权限。约束如下：

- 部门、成员和部门授权的每次变更都写审计；
- 管理端可以查看任意员工的“有效权限及来源”，也可以查看“某条部门授权当前覆盖的员工”；
- 部门被删除时，其授权保留但标记为 `invalid`，不转移给上级部门，并在管理端提示处理。

### 6.4 现有代码需要修改的地方

- **角色读取点的来源过滤。** 计算有效权限的查询改为同时接受 `local` 和 `department:%`：`identity/session-repository.ts`（解析会话权限）、`authorization/postgres-authorization-service.ts`（身份、角色指纹与项目空间公共数据范围）、`workbench/application/postgres-workspace-member-service.ts`（员工端访问资格）、`identity/administration-service.ts`（已授权人数与角色人数）。
- **保持只认直接授予的地方。** 平台管理员与管理写权限的判定（`authorization/platform-admin-actor.ts`、`skill/admin-skill-installation-service.ts`、`admin/application/postgres-grant-reconciliation-service.ts`、`identity/local-auth-service.ts`、`administration-service.ts` 的最后一位管理员保护）仍只认 `local`：管理类角色不能授给部门（OD8），这里保持只认直接授予作为第二道防线。管理员直接授予和撤销角色仍然只操作 `local` 来源的行。
- **员工列表。** “员工与权限”的员工角色分为直接授予（`roles`，可移除）和来自部门（`departmentRoles`，注明部门，只能在组织架构中修改）。

## 7. 待评审确认的默认值

1. **主部门：** 只影响显示（`users.department_id` 和员工选择器），不影响授权：员工属于任一部门都会继承该部门的授权。
2. **项目空间：** 员工的部门授权发生变化后，所在项目空间的公共数据范围会随之变化。这与项目空间“空间不扩大员工权限”的规则一致，无需新增规则。

## 8. 验收

- **P0：** 冒烟服务提供测试身份和内存中的部门树，验证管理端组织架构页（部门编辑、成员分配、部门授权）可用；首次打开时直接进入维护页，只有根部门，员工都显示“未分配部门”。
- **P1：** 使用专用 PostgreSQL，覆盖以下场景：新建、改名、移动部门，并拒绝移动到自己的下级之下；删除有成员或下级的部门被拒绝；分配和移除成员、指定主部门后，显示字段随之变化；初始化管理员不写入部门文本；管理员新建账号时选择的部门成为主部门；上线迁移清空现有部门文本；添加成员时多选和“只看未分配”筛选正确；部门授权含与不含下级，并在会话权限、项目空间成员资格、平台管理员判定、Runtime 授权中实际生效；移动部门后整棵子树的成员权限重算；调岗后权限变化且权限版本递增；管理类角色不能授给部门、已授给部门的角色不能加入管理权限；撤销直接授予不影响来自部门的同名角色；删除部门后其授权失效；OIDC 模式下组织架构接口不可用。
- **P2：** 本方案不涉及外部系统；发布前在受控环境按发布流程验收部门授权在真实对话和定时任务中生效，并留证。

## 附录 A：后续阶段——钉钉通讯录同步（待单独设计）

本附录记录已确认的方向和已知的代码影响，供后续设计使用，**不属于第一期范围**。

**已确认的方向（2026-10-31）：**

- 部门树来源按企业二选一：本地维护或钉钉同步，两种来源不混用；钉钉同步的企业，部门树和成员关系在平台内只读。届时需要新增来源字段，以及部门和账号上的钉钉 ID；首版不支持在已有部门数据后切换来源。
- 同步即创建平台账号，并直接绑定该钉钉用户，不需要手机号匹配和验证码确认。
- 同步方式：首次全量 + 钉钉 Stream 通讯录事件增量 + 每日全量对账兜底；只有完整遍历成功后才停用账号；离职员工的账号自动停用；一次停用或移除超过阈值（建议在职员工的 10%）时暂停，由管理员确认。
- 只在钉钉客户端内免登，不做桌面扫码登录；管理员可以为钉钉来源的员工另设密码，供其在系统浏览器中登录。
- 钉钉侧的角色、群和主管身份不授予任何平台权限；部门授权沿用第 6 节。
- 与现有本地账号手机号相同时进入待处理，由管理员选择关联或新建；关联后原密码保留。

**已知需要修改的现有代码（PR #47 评审确认）：**

- 会话校验（`local-auth-service.ts`）要求会话来源为 `local-password`、账号有密码凭据、`identity_provider = 'local'`；迁移 0077 只允许 `ai-hub-oidc` 和 `local-password` 两种会话来源。免登需要新增 `dingtalk` 会话来源并调整校验。
- 管理端员工目录（`administration-service.ts`）只认 AI Hub 账号或有密码凭据的本地账号，没有密码的钉钉账号会查不到。
- 密码凭据只允许 `identity_provider = 'local'` 的账号使用。
- 定时任务按员工身份运行前的目录过期检查（`resolveAutomationSubject`）需要纳入钉钉来源的账号。

**需要修改的其他方案：** [钉钉接入方案](dingtalk-integration-plan.md)第 3 节“钉钉侧部门不授予平台权限”、4.3“不自动建账号”，以及 4.2、4.3 中验证码确认的适用范围；其 DT-S1（手机号与凭据配置）届时并入钉钉同步阶段。
