## 1. 背景与目标

协作模式（B）已有窄屏布局（820px 以下底部标签栏 + “列表 → 聊天”两级），也有 H5 接入规范，但移动协同仍不可用，原因有两个：

- **收不到提醒。** 通知仅站内（功能规则 3.7），员工不打开网页就不知道群里有新消息、有人 @ 了自己、任务完成或需要处理；
- **手机打不开。** 部署为内网 IP + 自签根证书，部署手册禁止公网转发，手机走蜂窝网络无法访问。

目标：以钉钉作为 dsh-work 的移动端——**钉钉工作通知负责提醒，员工端以 H5 微应用运行在钉钉内负责查看与操作**。员工收到通知后点击，直接在钉钉内进入对应群组或任务查看和回复；平台的身份、权限、业务状态与 Agent 执行链路保持不变，内容不搬到钉钉的聊天中。

## 3. 边界

- **钉钉只是渠道与容器，不是执行器。** 钉钉负责送达通知和承载 H5 页面；所有 Agent 交互都发生在 H5 页面（即员工端）内，经 Run/Attempt → Runtime Adapter → DSH 执行；不新增钉钉侧的消息入口，钉钉适配层不调用模型、不实现工具循环（[AGENTS.md](../../AGENTS.md)）。
- **内容留在平台。** 群聊消息、Agent 回复、文件与成果只在 H5 页面中由平台返回，不发送到钉钉会话；钉钉通知只含 4.1 规定的名称级信息。
- **权限仍由平台裁决。** 推送前、点击后都按现行规则检查可见权限；钉钉侧的群、部门或角色不授予任何平台权限。
- **管理端不上公网。** 公网入口只暴露员工端的页面、`/api/workbench/v1` 与 `/auth/workbench`；管理端（4180）、服务端口与数据库保持内网。
- **不改桌面端登录。** 账号密码登录保持原样；钉钉免登只在钉钉客户端内生效（4.3）。
- **不做机器人与群 Webhook。** 不做钉钉单聊机器人（DT21），不把平台群组同步成钉钉群，也不做群机器人 Webhook 推送（无法按人做权限检查）；所有提醒发给具体员工本人。

## 4. 方案

### 4.1 钉钉工作通知

**推送事件（DT16）：**

| 事件 | 接收人 | 来源 |
| --- | --- | --- |
| 项目任务指派给我 / 改派给我 | 被指派员工 | 站内通知 `task_assigned` |
| 我创建的项目任务被他人完成 | 任务创建人 | 站内通知 `task_completed` |
| 我的定时任务一次执行没有成功（失败、跳过、错过、未能开始） | 任务所有者 | 站内通知 `automation_failed`；成功不通知（站内通知方案 NC6） |
| 我设置的项目 Agent 任务定时执行被暂停或停止 | 规则设置人 | 站内通知 `task_schedule_stopped` |
| 对话或讨论中 @ 我 | 被 @ 的员工 | 站内通知 `mention` |
| 我所在的群组有新消息（含任务对话与 Agent 回复，DT26） | 群组现任成员（本人发送的消息不计） | 群组消息与未读状态（4.1.1），不新增站内通知 |

被加入项目、Skill 审核结论与长时间 Run 完成不推送钉钉。

**消息内容：** 使用钉钉工作通知的卡片或链接消息，只放“谁、在哪个项目/群组、做了什么”和一个跳转链接，例如“张三在『Q4 投放复盘』给你指派了任务『整理渠道数据』”“『Q4 投放复盘』有 3 条新消息（张三、项目助手）”。任务标题按 DT17、定时任务名称按 DT20 显示，超长截断。不放消息正文、Agent 回复、文件名与文件内容、成果摘要和对话标题。名称在发送时按接收人当前可见性读取，不使用事件发生时的快照。

**投递链路（站内通知类事件）：**

1. 业务事务内已写入站内通知 `user_notifications`（站内通知方案，已实现）；同一事务为已绑定且未关闭该类型的接收人写入投递记录 `external_notification_deliveries`（来源为通知 ID），状态 `pending`。不另建事件判断；
2. 单进程投递器（与定时任务一致，单一所有者）领取 `pending` 记录，**发送前复核**：接收人账号有效、仍有对象可见权限、未关闭该类事件、绑定有效，任务类事件还要求未静音该空间（`mention` 与站内一致，不受按空间静音影响，功能规则 3.7）；任一不满足记为 `skipped` 并写原因；
3. 调用钉钉工作通知接口发送，成功记 `sent` 并保存钉钉任务 ID；可重试错误按退避重试，超过上限记 `failed`（死信），不再重试；
4. 投递失败不影响业务结果，也不回滚站内通知（沿用 3.7“通知失败不把已成功的业务变更报成失败”）。

去重键为 `(tenant_id, channel, recipient_user_id, source_type, source_id)`，重放与重启不会重复发送。同一接收人短时间内的同类事件可合并为一条（例如 5 分钟内 3 个任务被指派给你），合并窗口为可配置项。

**与站内通知清扫的关系：** 站内通知每天删除 90 天前的记录（站内通知方案 NC-S4）。投递记录只保存来源 ID，**不对 `user_notifications` 设外键**，不随通知级联删除，自有保留期（建议 180 天，留作送达证据）；清扫跳过仍有 `pending` 投递记录的通知，投递器在通知已被删除时把投递记为 `skipped`（原因：通知已过期）。P1 验收覆盖这一点。

#### 4.1.1 群组新消息提醒（DT23）

站内没有“群组新消息”通知，群组只有按“账号 + 对话对象”计的未读（功能规则 2.2b，`conversation_read_states`）。钉钉提醒直接以未读为依据，不新增站内通知：

- **计入范围（DT26）：** 与群组未读的现行实现一致（`postgres-conversation-target-service.ts`）——群组下所有会话（含任务对话）中，已读位置与本人加入时间之后的消息：他人发送的 user 消息，以及**全部** Agent 回复（含员工本人 @Agent 得到的回复，这样发起人离开页面也能知道结果；这不是单独的“Run 完成”事件，DT16 不变）。本人发送的 user 消息不计；已归档的群不提醒。点开提醒进入该群组。
- **触发与展开：** 群组消息写入时，同一事务只登记一条群组消息事件（群组 ID、消息 ID、消息时间），不按成员展开。投递器按群组合并同一延迟窗口内的事件，每个群每个窗口只对现任成员计算一次，避免每条消息都遍历全体成员；消息越多，合并越多。
- **提醒轮次（每个“接收人 + 群组”一条状态）：** 记录本轮锚点（本轮第一条计入未读的消息时间）、计划发送时间、实际发送时间、结束时间。
  - **开启：** 没有进行中的轮次，且该接收人在锚点之后有计入未读的消息时开启一轮，计划发送时间 = 锚点 + **延迟窗口**（默认 1 分钟）；
  - **本轮内：** 后续消息只更新计数，不再发送；
  - **结束：** 平台没有“标记已读”的钩子，由投递器在处理该群下一个事件或到达发送时间时惰性判断——员工的已读位置不早于锚点即结束本轮；
  - **下一轮：** 本轮结束后，下一条计入未读的消息开启新一轮；本轮已发送但员工一直未读时，**冷却时间**（默认 30 分钟）后若出现发送时间之后的新未读，以第一条这样的消息为锚点开启新一轮；
  - **清理：** 接收人被移出群组、群组归档或删除、账号停用时，其未结束的轮次在下次处理时关闭并记 `skipped`；每日清扫关闭超过 7 天的残留轮次。
- **发送前复核：** 账号有效且属于该租户；仍为现任成员且可读该群；群未归档；群未被本人静音；未关闭“群组新消息”类型；绑定状态为已绑定；重新计算未读——已读则结束本轮不发送；当日平台计数未达群组提醒停发阈值（计数来源为投递记录中该接收人当日状态为 `sent` 的条数，8.1）。未读数与发言人在发送时读取，最多列 2～3 位发言人。
- **与 @ 我的关系：** 只有投递状态为 `sent` 的 `mention` 才视为已提醒；若本轮未读全部是已 `sent` 的 @ 我消息，则不再发群组提醒。`mention` 被跳过或失败时，群组提醒照常发送。
- **静音：** 已按空间静音的群不发群组提醒，但其中的 @ 我照常推送。
- **配额：** 群组提醒优先级最低；接收人当日平台计数达到 150 条时停发群组提醒，保留任务、定时任务与 @ 我（上限见 8.1）。文案带时间，避免同日同文案被钉钉丢弃。

**员工偏好：** 员工端个人设置增加“钉钉通知”开关与事件类型选择（含“群组新消息”），默认全部开启；按空间静音的群不推送任务类事件与群组新消息，@ 我照常推送，只能按事件类型关闭。

**跳转（DT22、DT24）：** 每条通知带一个指向公网员工端稳定路由的链接（项目空间方案已规定链接与 A/B 模式无关），群组提醒与 @ 我指向对应群组，任务类指向任务详情，定时任务指向该定时任务。链接以钉钉内打开的方式发送，点击后在钉钉容器内打开 H5 并经 4.3 免登直达目标页面；在系统浏览器打开时走现有登录。具体的钉钉内打开链接格式以钉钉官方文档为准。

### 4.2 账号绑定（DT27–DT29）

**状态：** 每个平台账号对一个钉钉账号，记录在 `external_account_bindings`（`channel = dingtalk`、`user_id`、`external_user_id`（钉钉 `userid`）、`external_union_id`、`bound_by`（`self` / `admin`）、`bound_by_admin_id`、`status`（`valid` / `invalid`）、`bound_at`、`revoked_at`、`revoke_reason`、`self_rebind_locked`），两侧在有效记录中各自唯一：部分唯一索引 `(tenant_id, channel, user_id) WHERE status = 'valid'` 与 `(tenant_id, channel, external_user_id) WHERE status = 'valid'`。“未绑定”即没有有效记录。状态三种：

| 状态 | 收钉钉通知 | 钉钉内免登 |
| --- | --- | --- |
| 未绑定（无有效记录） | 否 | 否，打开后显示账号密码登录 |
| 已绑定 | 是 | 是 |
| 已失效 | 否 | 否，打开后显示账号密码登录，登录即重新绑定（管理员锁定时除外） |

**方式一：钉钉内登录即绑定（员工）**

1. 员工在钉钉工作台打开 dsh-work，或点开钉钉中的链接；页面经免登码调用 `POST /auth/workbench/dingtalk/login`（4.3），服务端换取钉钉 `userid` 并核对属于本企业；
2. 该 `userid` 没有有效绑定时，服务端返回一个**待绑定凭证**：服务端签发、单次有效、约 5 分钟过期，内含 `userid`、企业 `corpId`、租户与请求来源；页面显示员工端账号密码登录页，并注明“登录后将绑定当前钉钉账号，之后在钉钉内无需再登录”。客户端不提交也不能指定 `userid`，只能回传该凭证；
3. 员工提交账号密码与待绑定凭证到 `POST /auth/workbench/dingtalk/bind-login`。服务端在**同一事务**中：按现有登录的顺序锁定 `users` 与 `local_user_credentials`，校验密码与 audience 权限，消费待绑定凭证（重复使用、过期、来源不符一律拒绝），写入绑定（`bound_by = self`），签发关联该绑定的 `dingtalk` 会话（会话保存 `binding_id`）；写审计。并发两次绑定撞上唯一索引时，后到者失败并提示重试；
4. 不允许绑定的情况（均只签发普通密码会话，或在要求改密时进入改密流程，并写审计）：
   - 账号需要先修改初始密码（`must_change_password`）：先完成改密，改密后才可绑定；
   - 该钉钉账号已绑定其他平台账号：提示“此钉钉账号已绑定其他员工，请联系管理员”；
   - 该平台账号已有另一个有效钉钉绑定：**不自动替换**，提示“你的账号已绑定另一个钉钉账号，请先在个人设置中解除绑定，或联系管理员”。只凭密码替换绑定会让泄露的密码变成长期的免登权限；
   - 该账号被管理员锁定了自行绑定（见“解绑与失效”）：提示联系管理员。
5. 本流程与密码登录共用登录限流（按 IP 与账号），并另按钉钉 `userid` 限流。

账号密码证明平台身份，钉钉客户端内的免登码证明钉钉身份，两者在同一次操作中完成，无需验证码或扫码。必须在钉钉内打开员工端才能自行绑定，因此依赖公网入口（DT24）。

**方式二：管理员代绑**

1. 管理端“员工与权限 › 员工详情 › 钉钉”点“绑定钉钉”，输入该员工手机号（预览接口）；
2. 平台调用钉钉“根据手机号查询用户”得到 `userid`，再查询该成员的钉钉姓名与部门，返回预览“将绑定钉钉用户：张三（销售部）”和一个**确认凭证**（服务端保存，单次有效、短时过期，固定目标员工、`userid` 与所展示的姓名）。钉钉姓名与平台员工姓名不一致时，界面醒目提示并要求再勾选一次“我已核实是本人”；
3. 管理员确认（只提交确认凭证，不提交 `userid`）后，在同一事务中写入绑定（`bound_by = admin`）；审计中手机号只记脱敏号码（后 4 位）与哈希，平台不保存手机号字段；
4. 该钉钉账号已绑定其他员工时提示冲突，管理员可选择“改绑到本员工”：原绑定失效、按原 `binding_id` 撤销其钉钉会话，与新绑定在同一事务中提交，并通知原员工；
5. 写审计，并给被绑定员工登记一条站内通知“管理员已为你绑定钉钉账号（张三）”，员工可在个人设置中查看并解除；
6. 限制：不能为拥有管理类角色（含 `admin:*`、`admin:write`、`admin:read`、`audit:read`）的账号代绑，这类账号只能本人在钉钉内登录绑定，避免管理员借代绑获得其他管理员的免登；单个管理员每日代绑次数设上限（默认 50，可配置）。

代绑同样允许免登（DT29）。代价：管理员输错号码时，对应钉钉账号的主人可免登进入该员工账号；第 2 步的姓名核对、第 5 步通知本人与审计用于尽早发现，第 6 步限制影响范围。

**解绑与失效：**

- 员工在个人设置中解除绑定，或管理员在员工详情中解绑：绑定置为失效，停止推送，按 `binding_id` 撤销其 `dingtalk` 会话，均在同一事务中；
- 管理员解绑时可勾选“**锁定自行绑定**”（`self_rebind_locked`，用于怀疑账号被盗用或绑错人）：锁定期间员工在钉钉内登录不会重新绑定，只有管理员解除锁定或重新代绑后才恢复；这是失效记录上的标记，不新增状态；
- 平台账号停用：绑定置为失效；
- 管理员重置员工密码：绑定置为失效（重置通常意味着密码可能泄露）；员工自己修改密码时绑定保留，但与现在一样撤销全部会话，钉钉内下次打开会自动免登重新签发；
- 员工离职：每日检查一次已绑定的钉钉账号是否仍为企业在职成员（按 `userid` 查询）。只有钉钉**明确返回“用户不存在”**才判为离职并失效；超时、限流、权限错误等记为检查失败、不改变绑定。一次检查中判为离职的超过有效绑定的 10% 时整批暂停，由管理员在“钉钉集成”页确认后再执行（与[组织架构方案](org-structure-plan.md)附录 A 的阈值一致）；
- 失效后恢复：员工在钉钉内重新登录一次（未被锁定时），或管理员重新代绑。所有变更写审计。

### 4.3 H5 微应用（钉钉内移动端）与免登

- **公网入口：** 员工端使用独立域名（例如 `m.<企业域名>`）+ 受信证书，经反向代理只转发员工端页面、`/api/workbench/`、`/auth/workbench/`；按[移动端接入规范](../development/mobile-integration-guide.md) §2 把该 origin 加入 `DSH_WORK_WORKBENCH_ORIGINS`。端口：`server/src/modules/identity/config.ts` 只在 OIDC 配置下要求所有 origin 与 `DSH_WORK_WORKBENCH_PORT` 同端口，账号密码模式（`localAudienceConfiguration`）不校验端口。注意：只要环境中配置了任一 `AI_HUB_*` 接入变量，启动就会尝试 OIDC 配置；公网 443 origin 校验不过时**不会报错，而是静默回退为本地模式并关闭 AI Hub 登录**（`loadStartupIdentityConfiguration`）。因此公网入口上线时部署环境应已不再配置 AI Hub（OD1 计划删除），或公网入口改用 4174 端口；部署手册写明此检查。反向代理对 `/auth/workbench/` 按路径**显式白名单**转发（登录、钉钉免登、退出、会话查询），不整段转发。上线前须落实 8.3 的安全基线。
- **钉钉应用：** 在钉钉开放平台创建企业内部应用，工作通知与 H5 微应用属于同一应用（通知显示在该应用名下）；H5 首页为公网入口的协作模式（B）首页。在钉钉容器内一律按协作模式（B）显示，不修改员工保存的模式偏好（DT25）；容器识别只用于界面，不作为安全依据；按 8.1 的“DT-S1 钉钉后台配置清单”申请最小权限并完成配置（权限清单只在 8.1 维护）。
- **免登：** 页面在钉钉容器内用 JSAPI 获取一次性授权码 → 新增 `POST /auth/workbench/dingtalk/login`，服务端用授权码换取钉钉 `userid`（授权码一次性，服务端不缓存、不重放），并核对授权码属于本企业应用（`corpId` 与配置一致），不属于则拒绝 → 查有效绑定 → 与密码登录相同地调用 `resolveAuthorization` 与 `assertAudienceAccess`、校验请求来源（`validateRequestOrigin`）→ 签发员工端 Session Cookie → 跳回通知链接的目标页面。免登只签发 workbench audience 的会话；跳转目标 `return_to` 只接受同源相对路径；免登接口按 IP 与钉钉 `userid` 限流。没有有效绑定时显示账号密码登录页，登录即绑定（4.2 方式一）；不自动建账号。
- **会话来源：** 免登签发的是同一平台账号的会话，不新增账号类型，但新增会话来源 `dingtalk`（与[组织架构方案](org-structure-plan.md)附录 A 的结论一致，届时共用）。需要改动：
  - **迁移：** 新迁移重建 0077 中的两处约束——`authentication_provider` 的列内取值检查（约束名为自动生成，迁移中按实际名称删除重建）与 `authentication_session_credentials` 中按来源约束凭据列的检查，加入 `dingtalk`（不带 OIDC 令牌列）；会话表新增可空的 `binding_id`（`dingtalk` 会话必填）；`IdentityProvider` 类型加值。同时核对按 `authentication_provider = 'ai-hub-oidc'` 过滤的会话读取（`session-repository.ts`）与 `main.ts` 中身份模式到来源标签的映射，确保出现第三种取值后仍正确。
  - **会话校验：** `local-auth-service.ts` 的 `loginSession` 目前写死 `local-password`、要求 `identity_provider = 'local'`、内连接 `local_user_credentials` 并按 `must_change_password` 返回 403。`dingtalk` 会话另走一条查询：账号为本地账号且有效、会话上的 `binding_id` 对应的绑定仍有效，不要求密码凭据；`must_change_password` 为真时同样拒绝（绑定前已要求先改密，此处兜底）。钉钉会话不能用于修改密码（改密仍需密码会话），与现状一致。`dingtalk` 会话有效期短于密码会话（默认 12 小时，可配置），过期后在钉钉内自动免登重新签发，使离职、收权的滞后不超过该时长。
  - **会话并存：** 现有密码登录会撤销同一账号同一 audience 的全部旧会话。改为按来源撤销：钉钉免登只撤销该账号此前的 `dingtalk` 会话，密码登录只撤销此前的 `local-password` 会话，手机钉钉与桌面浏览器的会话并存、互不踢下线。取舍：桌面重新登录不再结束手机钉钉中的会话；为此钉钉会话有效期较短（见上），且退出登录、解绑、改绑、收权、停用、管理员撤销、员工改密与管理员重置密码都撤销全部来源的会话。
  - **Cookie：** 沿用员工端本地会话 Cookie 名（`dsh_work_local_session`），钉钉容器有独立的 Cookie 存储，不与桌面浏览器冲突。不采用“以 `local-password` 签发、只在审计中记录钉钉”的做法，以免会话来源失真。登录方式写入审计；收权、停用、Session 撤销沿用现有机制。
- **钉钉容器适配：** 在钉钉 iOS 与 Android 客户端内实测并按需适配：导航栏标题随页面变化、返回键与“列表 → 聊天”两级一致（聊天页返回列表，列表页返回关闭微应用）、软键盘不遮挡输入框、选图与上传文件、文件预览与下载、安全区；需要 JSAPI 的能力（标题、关闭页面、预览文件等）封装为员工端的“容器能力”适配层，钉钉外运行时退回浏览器默认行为。适配层只做界面与容器交互，不承载业务逻辑。
- **功能范围：** H5 即协作模式员工端，群组（查看、回复、@ 同事、@Agent、任务）、与 AI 同事对话、知识库、定时任务等按现有规则全部可用，不另做精简版；未适配完成的能力在验收中列出。
- **移动端规范调整：** 现行规范写明“认证优先使用平台独立账号、不集成 AI Hub”。钉钉免登作为钉钉容器内的附加方式写入该规范，规范的其余约束不变。

### 4.4 不做的形态

- **钉钉单聊机器人（DT21）：** 曾在讨论中设计（Stream 模式单聊、按 Agent 开启外发回复），已撤销。原因：H5 已能完成与 AI 同事的对话，机器人会把 Agent 回复正文发送到钉钉侧且无法收回。若日后重启，须重新评审披露范围。
- **平台群组同步为钉钉群：** 钉钉群成员可在平台外变更，无法保证与项目空间成员一致，Agent 回复与群内容会外泄；消息双向同步的编辑、撤回、文件、未读也会形成两套消息源。不做。

## 8. 待评审确认的默认值与风险

1. **钉钉接口与配额（2026-11-04 按钉钉开放平台官方文档核对）：**
   - **发送工作通知** `POST https://oapi.dingtalk.com/topapi/message/corpconversation/asyncsend_v2`（创建应用时默认具备消息通知权限）：单次 `userid_list` 最多 100 人；消息体最长 2048 字节，支持 `link`、`markdown`、`action_card`、`oa` 等类型；返回异步任务 `task_id`。**企业内部应用每天给每个员工最多 500 条**；**给同一员工一天只能发送一条内容相同的消息**；每分钟最多 5000 人可收到消息。**超出限制时接口仍返回成功，但用户收不到**，需调用“获取工作通知消息的发送结果”核对。
   - **据此确定：** 投递器为每个接收人维护当日已发计数，建议默认每人每日上限 200 条（低于钉钉 500 条，留余量）、达到 150 条时停发群组提醒，均为可配置项（4.1.1）；每条通知文案带发生时间（如“10:42”），避免同日相同文案被钉钉静默丢弃（群组提醒尤其需要）；`sent` 只表示已受理，投递器按 `task_id` 抽查或批量查询发送结果，失败的标记为 `failed` 并在管理端列出；合并窗口沿用 4.1 的 5 分钟。
   - **根据手机号查询用户** `POST https://oapi.dingtalk.com/topapi/v2/user/getbymobile`（仅管理员代绑使用）：需在应用中开通“根据手机号获取成员基本信息权限”；只能查到在职员工；错误码 `60121` 未找到用户、`40104` 无效手机号，在代绑对话框中直接提示。
   - **查询用户详情** `POST https://oapi.dingtalk.com/topapi/v2/user/get`（参数 `userid`）：需“成员信息读权限”；返回姓名、`unionid`、所在部门 ID 等，用于代绑预览显示钉钉姓名与部门、每日离职检查。错误码 `33012` 为“无效的 userId”，离职检查把它（以及 `60121` 未找到用户）视为“明确不存在”，`-1` 系统繁忙等其他错误记为检查失败、不改变绑定；离职后实际返回哪个错误码在 P2 真实环境中确认，确认前若与文档不符，按“检查失败”处理而不失效。每次离职检查记录失败数与错误码分布；连续 3 天失败超过已绑定人数的 5% 时，“钉钉集成”页显示常驻“离职检查异常”提醒，避免因错误码不符而长期漏判离职。检查按官方限流分批限速调用，限流错误记为检查失败、次日重试。
   - **获取部门详情** `POST https://oapi.dingtalk.com/topapi/v2/department/get`（参数 `dept_id`）：需“通讯录部门信息读权限”；把用户详情中的部门 ID 转成部门名称，用于代绑预览：成员属于多个部门时最多显示 2 个、以“、”连接，根部门显示为企业名称；`60003`（未找到部门）或限流、超时等任何失败时只显示姓名，并把“我已核实是本人”改为必选。
   - **不需要的权限：** 不申请“企业员工手机号信息”与“邮箱等个人信息”（代绑只按手机号查人，不读取手机号）。
   - **DT-S1 钉钉后台配置清单：**
     - 应用凭据：CorpId、AgentId、AppKey / AppSecret，在管理端“钉钉集成 › 应用配置”填写（DT30；服务端经 `gettoken` 换取应用 access_token，缓存至过期前刷新）；
     - 权限：免登（企业内部应用默认）、工作通知（默认具备，含“获取工作通知消息的发送结果”）、根据手机号获取成员基本信息、成员信息读权限、通讯录部门信息读权限；
     - **通讯录权限范围设为“全部员工”**：范围不全时，范围外员工无法代绑，`user/get` 对其报权限错误；
     - 服务器出口 IP 白名单：在钉钉后台登记平台服务器的出口 IP（与第 2 项“放行出站域名”是两件事）；
     - H5 微应用：首页地址与可信域名设为公网员工端域名；
     - DT-S1 开始时先在开发者后台逐项核对上述权限的当前名称，名称与本文不同以后台为准并回写本文。
   - **权限或范围错误不当作员工检查失败：** 调用返回权限不足或不在通讯录范围内时，在“钉钉集成”页显示为“配置异常”，不计入单个员工的“检查失败”。
   - **免登**：微应用前端用 JSAPI `requestAuthCode` 取得授权码，服务端调用 `POST https://oapi.dingtalk.com/topapi/v2/user/getuserinfo` 换取 `userid`；授权码五分钟内有效且只能使用一次，服务端不缓存、不重放。
   - **消息链接打开方式**：官方文档说明 PC 端可指定在侧边栏、外部浏览器或工作台打开微应用链接（工作台方式需要企业 `corpid` 与 `0_<agentId>`）；移动端在钉钉内打开的表现以 DT-S1 真机验证为准。
   - 文档来源：钉钉开放平台“发送工作通知”“根据手机号查询用户”“通过免登码获取用户信息”“消息链接说明”“查询用户详情”“获取部门详情”页面（open.dingtalk.com/document/orgapp/…，2026-11-04、11-05 读取）；实施时以当时文档为准。
2. **服务器出站：** 投递器需要访问钉钉开放平台；若内网有出站白名单，需放行对应域名。
3. **公网暴露的安全基线（DT-S1 上线前必须确定）：** 员工端上公网后，账号密码登录接口同样对公网可达——服务端无法可靠识别请求是否来自钉钉容器（User-Agent 可伪造），所以“只允许钉钉内登录”只能靠网关或 IP 控制实现，不能靠应用判断。建议默认：登录与免登接口按 IP 和账号限流、连续失败锁定；访问日志与异常登录告警；反向代理按路径白名单只转发员工端。待确认：是否加 WAF 或网关 IP 控制。注意：员工在钉钉内首次绑定需要公网上的账号密码登录（4.2 方式一），网关不能按登录方式只放行免登，只能按来源 IP、频率等限制。
4. **群组提醒的窗口：** 延迟窗口默认 1 分钟、冷却时间默认 30 分钟，均为可配置项；上线后按实际打扰程度调整。
5. **绑定覆盖率与代绑风险：** 员工不在钉钉内登录、管理员也未代绑时收不到任何通知，上线时由管理员按“钉钉集成”页的未绑定名单代绑或通知员工；代绑输错号码会让他人可免登，靠代绑时显示钉钉姓名与部门、通知员工本人和审计控制。
6. **钉钉容器兼容性：** 文件上传下载、键盘与返回键在 iOS/Android 钉钉中的表现可能不同，DT-S1 以真机验收为准，未适配的能力明确列出，不宣称可用。
7. **任务标题外发：** 按 DT17、DT20 显示任务标题与定时任务名称，标题中的业务内容会随工作通知外发，需在功能规则 3.7 中写明。
