## 1. 背景与目标

协作模式（B）已有窄屏布局（820px 以下底部标签栏 + “列表 → 聊天”两级），也有 H5 接入规范，但移动协同仍不可用，原因有两个：

- **收不到提醒。** 通知仅站内（功能规则 3.7），员工不打开网页就不知道群里有新消息、有人 @ 了自己、任务完成或需要处理；
- **手机打不开。** 部署为内网 IP + 自签根证书，部署手册禁止公网转发，手机走蜂窝网络无法访问。

目标：以钉钉作为 dsh-work 的移动端——**钉钉工作通知负责提醒，员工端以 H5 微应用运行在钉钉内负责查看与操作**。员工收到通知后点击，直接在钉钉内进入对应群组或任务查看和回复；平台的身份、权限、业务状态与 Agent 执行链路保持不变，内容不搬到钉钉的聊天中。

## 3. 边界

- **钉钉只是渠道与容器，不是执行器。** 钉钉负责送达通知和承载 H5 页面；所有 Agent 交互都发生在 H5 页面（即员工端）内，经 Run/Attempt → Runtime Adapter → DSH 执行；不新增钉钉侧的消息入口，钉钉适配层不调用模型、不实现工具循环（[AGENTS.md](../../AGENTS.md)）。
- **内容留在平台。** 群聊消息、Agent 回复、文件与成果只在 H5 页面中由平台返回，不发送到钉钉会话；钉钉通知只含 4.1 规定的名称级信息。
- **权限仍由平台裁决。** 推送前、点击后都按现行规则检查可见权限；钉钉侧的群、部门或角色不授予任何平台权限。
- **管理端不上公网。** 公网入口只暴露员工端的页面、`/api/workbench/v1` 与 `/auth/workbench`；管理端（4180）、服务端口与数据库保持内网。
- **不改桌面端登录。** 账号密码登录保持原样；钉钉免登只在钉钉客户端内生效（4.3）。
- **不做机器人与群 Webhook。** 不做钉钉单聊机器人（DT21），不把平台群组同步成钉钉群，也不做群机器人 Webhook 推送（无法按人做权限检查）；所有提醒发给具体员工本人。

## 4. 方案

### 4.1 钉钉工作通知

**推送事件（DT16）：**

| 事件 | 接收人 | 来源 |
| --- | --- | --- |
| 项目任务指派给我 / 改派给我 | 被指派员工 | 站内通知 `task_assigned` |
| 我创建的项目任务被他人完成 | 任务创建人 | 站内通知 `task_completed` |
| 我的定时任务一次执行没有成功（失败、跳过、错过、未能开始） | 任务所有者 | 站内通知 `automation_failed`；成功不通知（站内通知方案 NC6） |
| 我设置的项目 Agent 任务定时执行被暂停或停止 | 规则设置人 | 站内通知 `task_schedule_stopped` |
| 对话或讨论中 @ 我 | 被 @ 的员工 | 站内通知 `mention` |
| 我所在的群组有新消息（含任务对话与 Agent 回复，DT26） | 群组现任成员（本人发送的消息不计） | 群组消息与未读状态（4.1.1），不新增站内通知 |

被加入项目、Skill 审核结论与长时间 Run 完成不推送钉钉。

**消息内容：** 使用钉钉工作通知的卡片或链接消息，只放“谁、在哪个项目/群组、做了什么”和一个跳转链接，例如“张三在『Q4 投放复盘』给你指派了任务『整理渠道数据』”“『Q4 投放复盘』有 3 条新消息（张三、项目助手）”。任务标题按 DT17、定时任务名称按 DT20 显示，超长截断。不放消息正文、Agent 回复、文件名与文件内容、成果摘要和对话标题。绑定确认用的一次性验证码（4.2）是工作通知中唯一的另一类内容，只含验证码与用途说明。名称在发送时按接收人当前可见性读取，不使用事件发生时的快照。

**投递链路（站内通知类事件）：**

1. 业务事务内已写入站内通知 `user_notifications`（站内通知方案，已实现）；同一事务为已绑定且未关闭该类型的接收人写入投递记录 `external_notification_deliveries`（来源为通知 ID），状态 `pending`。不另建事件判断；
2. 单进程投递器（与定时任务一致，单一所有者）领取 `pending` 记录，**发送前复核**：接收人账号有效、仍有对象可见权限、未关闭该类事件、绑定有效，任务类事件还要求未静音该空间（`mention` 与站内一致，不受按空间静音影响，功能规则 3.7）；任一不满足记为 `skipped` 并写原因；
3. 调用钉钉工作通知接口发送，成功记 `sent` 并保存钉钉任务 ID；可重试错误按退避重试，超过上限记 `failed`（死信），不再重试；
4. 投递失败不影响业务结果，也不回滚站内通知（沿用 3.7“通知失败不把已成功的业务变更报成失败”）。

去重键为 `(tenant_id, channel, recipient_user_id, source_type, source_id)`，重放与重启不会重复发送。同一接收人短时间内的同类事件可合并为一条（例如 5 分钟内 3 个任务被指派给你），合并窗口为可配置项。

**与站内通知清扫的关系：** 站内通知每天删除 90 天前的记录（站内通知方案 NC-S4）。投递记录只保存来源 ID，**不对 `user_notifications` 设外键**，不随通知级联删除，自有保留期（建议 180 天，留作送达证据）；清扫跳过仍有 `pending` 投递记录的通知，投递器在通知已被删除时把投递记为 `skipped`（原因：通知已过期）。P1 验收覆盖这一点。

#### 4.1.1 群组新消息提醒（DT23）

站内没有“群组新消息”通知，群组只有按“账号 + 对话对象”计的未读（功能规则 2.2b，`conversation_read_states`）。钉钉提醒直接以未读为依据，不新增站内通知：

- **计入范围（DT26）：** 与群组未读的现行实现一致（`postgres-conversation-target-service.ts`）——群组下所有会话（含任务对话）中，已读位置与本人加入时间之后的消息：他人发送的 user 消息，以及**全部** Agent 回复（含员工本人 @Agent 得到的回复，这样发起人离开页面也能知道结果；这不是单独的“Run 完成”事件，DT16 不变）。本人发送的 user 消息不计；已归档的群不提醒。点开提醒进入该群组。
- **触发与展开：** 群组消息写入时，同一事务只登记一条群组消息事件（群组 ID、消息 ID、消息时间），不按成员展开。投递器按群组合并同一延迟窗口内的事件，每个群每个窗口只对现任成员计算一次，避免每条消息都遍历全体成员；消息越多，合并越多。
- **提醒轮次（每个“接收人 + 群组”一条状态）：** 记录本轮锚点（本轮第一条计入未读的消息时间）、计划发送时间、实际发送时间、结束时间。
  - **开启：** 没有进行中的轮次，且该接收人在锚点之后有计入未读的消息时开启一轮，计划发送时间 = 锚点 + **延迟窗口**（默认 1 分钟）；
  - **本轮内：** 后续消息只更新计数，不再发送；
  - **结束：** 平台没有“标记已读”的钩子，由投递器在处理该群下一个事件或到达发送时间时惰性判断——员工的已读位置不早于锚点即结束本轮；
  - **下一轮：** 本轮结束后，下一条计入未读的消息开启新一轮；本轮已发送但员工一直未读时，**冷却时间**（默认 30 分钟）后若出现发送时间之后的新未读，以第一条这样的消息为锚点开启新一轮；
  - **清理：** 接收人被移出群组、群组归档或删除、账号停用时，其未结束的轮次在下次处理时关闭并记 `skipped`；每日清扫关闭超过 7 天的残留轮次。
- **发送前复核：** 账号有效且属于该租户；仍为现任成员且可读该群；群未归档；群未被本人静音；未关闭“群组新消息”类型；绑定状态为已匹配或已确认（通知只要求已匹配）；重新计算未读——已读则结束本轮不发送；当日平台计数未达群组提醒停发阈值（计数来源为投递记录中该接收人当日状态为 `sent` 的条数，8.1）。未读数与发言人在发送时读取，最多列 2～3 位发言人。
- **与 @ 我的关系：** 只有投递状态为 `sent` 的 `mention` 才视为已提醒；若本轮未读全部是已 `sent` 的 @ 我消息，则不再发群组提醒。`mention` 被跳过或失败时，群组提醒照常发送。
- **静音：** 已按空间静音的群不发群组提醒，但其中的 @ 我照常推送。
- **配额：** 群组提醒优先级最低；接收人当日平台计数达到 150 条时停发群组提醒，保留任务、定时任务与 @ 我（上限见 8.1）。文案带时间，避免同日同文案被钉钉丢弃。

**员工偏好：** 员工端个人设置增加“钉钉通知”开关与事件类型选择（含“群组新消息”），默认全部开启；按空间静音的群不推送任务类事件与群组新消息，@ 我照常推送，只能按事件类型关闭。

**跳转（DT22、DT24）：** 每条通知带一个指向公网员工端稳定路由的链接（项目空间方案已规定链接与 A/B 模式无关），群组提醒与 @ 我指向对应群组，任务类指向任务详情，定时任务指向该定时任务。链接以钉钉内打开的方式发送，点击后在钉钉容器内打开 H5 并经 4.3 免登直达目标页面；在系统浏览器打开时走现有登录。具体的钉钉内打开链接格式以钉钉官方文档为准。

### 4.2 账号匹配（手机号）

**现状：** `users` 表没有手机号字段；AI Hub 目录同步只带 `email`（AI Hub 登录计划删除，组织架构方案 OD1）；独立账号的登录标识可以是手机号，但它是登录名，不是经过核对的联系方式。

**方案：**

- `users` 新增 `mobile`（E.164 规范化存储，唯一约束为 `(tenant_id, mobile)`，允许为空）。来源为管理端“员工与权限”由管理员维护或批量导入。**员工不能自助修改手机号。**
- 匹配：管理员触发或定时任务调用钉钉“根据手机号查询用户”接口，得到钉钉 `userid`，写入 `external_account_bindings`（`channel = dingtalk`、`user_id`、`external_user_id`、`external_union_id`、`matched_mobile`、`status`、`matched_at`、`confirmed_at`），两侧各自唯一。
- 绑定分两级：
  - **已匹配：** 手机号查到唯一钉钉用户即可接收工作通知；
  - **已确认：** 员工在桌面端员工设置中点击“绑定钉钉”，服务端经工作通知向已匹配的钉钉用户发送一次性验证码（短时有效、限次尝试），员工在桌面端输入后确认。该过程同时证明平台身份（已登录桌面端）与钉钉身份（收到验证码）。只有已确认的绑定才允许免登（4.3）。
- 失效：平台手机号变更、账号停用、钉钉侧查不到该手机号（离职后接口不再返回）或返回的 `userid` 变化时，绑定置为失效，停止推送、撤销该账号的 `dingtalk` 会话并要求重新确认；每次变更写审计。
- 冲突：同一手机号对应多个平台账号（唯一约束阻止写入）或钉钉返回异常时不绑定，在管理端列出待处理项。

**为什么要“已确认”：** 手机号录错时，已匹配只会让对方收到少量名称级提醒；若直接允许免登，录错就等于把整个账号交给他人。

### 4.3 H5 微应用（钉钉内移动端）与免登

- **公网入口：** 员工端使用独立域名（例如 `m.<企业域名>`）+ 受信证书，经反向代理只转发员工端页面、`/api/workbench/`、`/auth/workbench/`；按[移动端接入规范](../development/mobile-integration-guide.md) §2 把该 origin 加入 `DSH_WORK_WORKBENCH_ORIGINS`。端口：`server/src/modules/identity/config.ts` 只在 OIDC 配置下要求所有 origin 与 `DSH_WORK_WORKBENCH_PORT` 同端口，账号密码模式（`localAudienceConfiguration`）不校验端口。注意：只要环境中配置了任一 `AI_HUB_*` 接入变量，启动就会尝试 OIDC 配置；公网 443 origin 校验不过时**不会报错，而是静默回退为本地模式并关闭 AI Hub 登录**（`loadStartupIdentityConfiguration`）。因此公网入口上线时部署环境应已不再配置 AI Hub（OD1 计划删除），或公网入口改用 4174 端口；部署手册写明此检查。反向代理对 `/auth/workbench/` 按路径**显式白名单**转发（登录、钉钉免登、退出、会话查询），不整段转发。上线前须落实 8.3 的安全基线。
- **钉钉应用：** 在钉钉开放平台创建企业内部应用，工作通知与 H5 微应用属于同一应用（通知显示在该应用名下）；H5 首页为公网入口的协作模式（B）首页。在钉钉容器内一律按协作模式（B）显示，不修改员工保存的模式偏好（DT25）；容器识别只用于界面，不作为安全依据；申请通讯录手机号查询、工作通知、免登等最小权限。
- **免登：** 页面在钉钉容器内用 JSAPI 获取一次性授权码 → 新增 `POST /auth/workbench/dingtalk/login`，服务端用授权码换取钉钉 `userid` → 查已确认绑定 → 签发员工端 Session Cookie → 跳回通知链接的目标页面。免登只签发 workbench audience 的会话；跳转目标 `return_to` 只接受同源相对路径。绑定未确认时提示先在桌面端完成 4.2 的确认（也可在钉钉内直接用账号密码登录）；不存在绑定时提示联系管理员，不自动建账号。
- **会话来源：** 免登签发的是同一平台账号的会话，不新增账号类型，但新增会话来源 `dingtalk`（与[组织架构方案](org-structure-plan.md)附录 A 的结论一致，届时共用）。需要改动：
  - **迁移：** 新迁移重建 0077 中的两处约束——`authentication_provider` 的取值检查与 `authentication_session_credentials` 中按来源约束凭据列的检查，加入 `dingtalk`（不带 OIDC 令牌列）；`IdentityProvider` 类型加值。
  - **会话校验：** `local-auth-service.ts` 目前写死 `local-password`、要求 `identity_provider = 'local'`、关联 `local_user_credentials` 并按 `must_change_password` 返回 403。`dingtalk` 会话改为：账号为本地账号且有效、绑定仍为已确认，不要求密码凭据；`must_change_password` 只约束密码登录，不阻止钉钉会话（钉钉会话不使用密码）。
  - **会话并存：** 现有密码登录会撤销同一账号同一 audience 的全部旧会话。改为按来源撤销：钉钉免登只撤销该账号此前的 `dingtalk` 会话，密码登录只撤销此前的 `local-password` 会话，手机钉钉与桌面浏览器的会话并存、互不踢下线；收权、停用、管理员撤销仍作用于全部来源。
  - **Cookie：** 沿用员工端本地会话 Cookie 名（`dsh_work_local_session`），钉钉容器有独立的 Cookie 存储，不与桌面浏览器冲突。不采用“以 `local-password` 签发、只在审计中记录钉钉”的做法，以免会话来源失真。登录方式写入审计；收权、停用、Session 撤销沿用现有机制。
- **钉钉容器适配：** 在钉钉 iOS 与 Android 客户端内实测并按需适配：导航栏标题随页面变化、返回键与“列表 → 聊天”两级一致（聊天页返回列表，列表页返回关闭微应用）、软键盘不遮挡输入框、选图与上传文件、文件预览与下载、安全区；需要 JSAPI 的能力（标题、关闭页面、预览文件等）封装为员工端的“容器能力”适配层，钉钉外运行时退回浏览器默认行为。适配层只做界面与容器交互，不承载业务逻辑。
- **功能范围：** H5 即协作模式员工端，群组（查看、回复、@ 同事、@Agent、任务）、与 AI 同事对话、知识库、定时任务等按现有规则全部可用，不另做精简版；未适配完成的能力在验收中列出。
- **移动端规范调整：** 现行规范写明“认证优先使用平台独立账号、不集成 AI Hub”。钉钉免登作为钉钉容器内的附加方式写入该规范，规范的其余约束不变。

### 4.4 不做的形态

- **钉钉单聊机器人（DT21）：** 曾在讨论中设计（Stream 模式单聊、按 Agent 开启外发回复），已撤销。原因：H5 已能完成与 AI 同事的对话，机器人会把 Agent 回复正文发送到钉钉侧且无法收回。若日后重启，须重新评审披露范围。
- **平台群组同步为钉钉群：** 钉钉群成员可在平台外变更，无法保证与项目空间成员一致，Agent 回复与群内容会外泄；消息双向同步的编辑、撤回、文件、未读也会形成两套消息源。不做。

## 8. 待评审确认的默认值与风险

1. **钉钉接口与配额（2026-11-04 按钉钉开放平台官方文档核对）：**
   - **发送工作通知** `POST https://oapi.dingtalk.com/topapi/message/corpconversation/asyncsend_v2`（创建应用时默认具备消息通知权限）：单次 `userid_list` 最多 100 人；消息体最长 2048 字节，支持 `link`、`markdown`、`action_card`、`oa` 等类型；返回异步任务 `task_id`。**企业内部应用每天给每个员工最多 500 条**；**给同一员工一天只能发送一条内容相同的消息**；每分钟最多 5000 人可收到消息。**超出限制时接口仍返回成功，但用户收不到**，需调用“获取工作通知消息的发送结果”核对。
   - **据此确定：** 投递器为每个接收人维护当日已发计数，建议默认每人每日上限 200 条（低于钉钉 500 条，留余量）、达到 150 条时停发群组提醒，均为可配置项（4.1.1）；每条通知文案带发生时间（如“10:42”），避免同日相同文案被钉钉静默丢弃（群组提醒与验证码尤其需要）；`sent` 只表示已受理，投递器按 `task_id` 抽查或批量查询发送结果，失败的标记为 `failed` 并在管理端列出；合并窗口沿用 4.1 的 5 分钟。
   - **根据手机号查询用户** `POST https://oapi.dingtalk.com/topapi/v2/user/getbymobile`：需在应用中开通“根据手机号获取成员基本信息权限”；只能查到在职员工，离职后查不到；错误码 `60121` 未找到用户、`40104` 无效手机号，分别记为待处理项。
   - **免登**：微应用前端用 JSAPI `requestAuthCode` 取得授权码，服务端调用 `POST https://oapi.dingtalk.com/topapi/v2/user/getuserinfo` 换取 `userid`；授权码五分钟内有效且只能使用一次，服务端不缓存、不重放。
   - **消息链接打开方式**：官方文档说明 PC 端可指定在侧边栏、外部浏览器或工作台打开微应用链接（工作台方式需要企业 `corpid` 与 `0_<agentId>`）；移动端在钉钉内打开的表现以 DT-S3 真机验证为准。
   - 文档来源：钉钉开放平台“发送工作通知”“根据手机号查询用户”“通过免登码获取用户信息”“消息链接说明”页面（open.dingtalk.com/document/orgapp/…，2026-11-04 读取）；实施时以当时文档为准。
2. **服务器出站：** 投递器需要访问钉钉开放平台；若内网有出站白名单，需放行对应域名。
3. **公网暴露的安全基线（DT-S3 上线前必须确定）：** 员工端上公网后，账号密码登录接口同样对公网可达——服务端无法可靠识别请求是否来自钉钉容器（User-Agent 可伪造），所以“只允许钉钉内登录”只能靠网关或 IP 控制实现，不能靠应用判断。建议默认：登录与免登接口按 IP 和账号限流、连续失败锁定；访问日志与异常登录告警；反向代理按路径白名单只转发员工端。待确认：是否在网关层限制公网的账号密码登录（例如只放行免登），是否加 WAF 或网关 IP 控制。
4. **群组提醒的窗口：** 延迟窗口默认 1 分钟、冷却时间默认 30 分钟，均为可配置项；上线后按实际打扰程度调整。
5. **手机号来源：** 首次启用需要管理员批量导入手机号；导入错误的影响由 4.2 的两级绑定控制。
6. **钉钉容器兼容性：** 文件上传下载、键盘与返回键在 iOS/Android 钉钉中的表现可能不同，DT-S3 以真机验收为准，未适配的能力明确列出，不宣称可用。
7. **任务标题外发：** 按 DT17、DT20 显示任务标题与定时任务名称，标题中的业务内容会随工作通知外发，需在功能规则 3.7 中写明。
