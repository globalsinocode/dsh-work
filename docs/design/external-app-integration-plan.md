## 1. 背景与目标

2026-11-17 确定分工：业务规则、业务状态与主动发现由外部业务应用承担，经 MCP 提供给 dsh-work；dsh-work 的 Agent 作为员工与外部系统之间的中介（查询、解释、比较方案、起草，以及经外部应用授权的写入），平台不保存外部业务事实。Agent 只做协调，不作为业务记录方。

按这个分工接入外部应用，dsh-work 缺一项通用能力：**调用上下文**。MCP 只用 Connector 的共享凭据，外部应用不知道这次是哪位员工、结果给谁看，无法按人过滤数据，也无法判断能否写入。

目标是把它做成通用机制：任何外部应用只需遵守第 6 节的约定即可接入，dsh-work 不为具体业务场景增加对象、页面或计算。

## 2. 边界

- **数据权限以外部应用为准（2026-11-18 确认）：** 外部应用按员工在它自己系统中的数据权限返回数据，dsh-work 不把自己的数据范围传给外部应用（EA2）。因此 Agent 在 dsh-work 中被授予的数据范围不限制它经 MCP 读到的数据（与设计规范 6.4 的现状一致）；要限制某个 Agent 能接触的外部数据，靠是否为它选定该 Connector，以及外部应用提供哪些工具。
- **写入的授权由外部应用负责（2026-11-17 确认）：** 外部应用凭调用上下文（5.1）判断操作人与结果可见类型，决定是否允许写入，并且只提供愿意让 Agent 调用的工具。dsh-work 不区分工具读写，不设写入准入，沿用现有的“新增或 Schema 变化的工具须管理员确认能力变更”。不认调用上下文的第三方 MCP 服务若带有不愿开放的写工具，不接入，或按 PF-07 手册只使用只读凭据。员工本人确认后才执行的写入（依赖持久化等待的验收与 DSH 按工具请求权限）不在本文，出现需要时另行设计。
- **不提供外部推送入口（2026-11-17 确认）：** 外部应用不经 dsh-work 推送消息。需要提醒员工的场景，由 dsh-work 中的 Agent 按计划经 MCP 查询外部应用的消息状态，把结果交给员工（5.2）。
- **不保存外部业务事实：** 业务数据留在外部应用，Agent 需要时经 MCP 读取。
- **不新增执行路径：** 调用上下文不调用模型，不改变 Run/Attempt → Runtime Adapter → DSH 的执行链路。
- **不建连接器网关：** MCP 调用仍由 DSH 直连外部应用，平台只在每个 Attempt 的配置中多下发一个请求头（与设计规范 6.4 一致）。

| EA1 | 令牌中给外部应用哪些员工标识 | (a) 只给平台用户 ID，外部应用自行维护对应；(b) 平台用户 ID 与登录账号（手机号或邮箱）；(c) 再加钉钉 userid（已绑定时） | **已确认（2026-11-18）：** (c)。外部应用优先按手机号识别员工，也支持钉钉 userid 等。令牌给出平台用户 ID、手机号（登录账号为手机号时）、邮箱（登录账号为邮箱时）与钉钉 userid（已绑定时），不给显示名；只在 Connector 开启调用上下文时发送（EA4） |
| EA2 | 外部应用按什么过滤数据，结果对多人可见的运行怎么办 | (a) 传 dsh-work 的披露数据范围，外部应用按它过滤；(b) 项目空间的运行传全体成员的标识，由外部应用求交集；(c) 不传数据范围，项目空间的运行也不传员工标识 | **已确认（2026-11-18）：** (c)。数据权限以外部应用自己的权限为准：员工本人的运行按 `viewer` 在外部应用中的权限返回；项目空间的运行没有 `viewer`，外部应用只返回本系统中对所有员工可见的数据。项目空间因此拿不到按人限制的数据（如应收明细），需要时员工在个人对话中查询；以后确有项目空间使用这类数据的场景再考虑 (b) |
| EA3 | 令牌的签名方式 | (a) Ed25519 非对称签名，外部应用用平台公钥验证；(b) 每个 Connector 一个共享密钥（HMAC-SHA256）；(c) 令牌只是随机值，外部应用每次回调平台校验 | **已确认（2026-11-18）：** (b)。令牌按 `aud` 绑定 Connector，外部应用持有的密钥只能给自己签令牌，与 (a) 的安全差别很小；HS256 几乎所有 JWT 库都支持，EdDSA 在较老的 Java、.NET 库中支持不全；不需要对外发布公钥地址，也不用改反向代理。代价是平台要新增“密钥只显示一次”的流程（现有凭据都是录入 dsh-work，没有从 dsh-work 给出的）。(c) 每次调用多一跳，并要求外部应用能访问 dsh-work |
| EA4 | 调用上下文是否默认发送 | (a) 按 Connector 开启，默认关闭；(b) 全部 Connector 都发送 | **已确认（2026-11-18）：** (a)。令牌含员工标识，不应发给不需要它的 MCP 服务；现有 Connector 不受影响 |

| 工具清单 | 管理端“MCP 连接器”页登记时读出的工具直接生效；之后新增或 Schema 变化的工具标为待确认，管理员“确认能力变更”后生效；不区分读写 |

| 运行与结果受众 | 授权按工作空间类型分支：项目空间中的运行（讨论与任务对话、项目任务定时执行、他人重试，以及结果归属空间选为项目空间的定时任务）经 `authorizeTeamRunExecution` 授权，结果对全体成员可见（`run-orchestration-service.ts`、`automation-service.ts`）；无 Session 的 Task 执行接口（`/api/workbench/v1/task-executions`，前端未调用）在项目空间中同样经它授权，结果只给发起人读取。个人空间中的运行经 `authorizeRuntime` 授权，结果只给本人。Agent 主动任务经 `authorizeAgentRoutine` 授权，可以放在项目空间，结果只给接收人。发布验证经 `authorizeReleaseTrial` 授权，Attempt 仍装载选定的 MCP（`attempt-dispatcher.ts`），工具调用由 DSH 策略返回 `trial_only`（`dsh-acp-runtime-adapter.ts`） |

| 写入 | 真实 Agent 的 `approvalMode` 固定为 `never`（`postgres-agent-service.ts`），Adapter 对权限请求直接放行，选定 Connector 中的写工具不经审批即可调用；每次调用写 `mcp_invocation_audits`，结果未知的调用经管理端对账 |
| 定时任务与主动任务 | 员工本人的定时任务（结果归属空间可选个人空间或项目空间）按每天或每周（`HH:mm`）或手动运行，每次在该空间新建 Session，结果留在该次 Session；成功不发通知，执行失败、被跳过（所有者本人造成的除外）、停机错过或受理后未能开始时以站内通知告知所有者（功能规则第 7 节）。Agent 主动任务只有一个接收人，结果留在该次 Task，只给接收人看 |

## 5. 方案

### 5.1 调用上下文（EA-S1）

**做法：** Connector 开启“发送调用上下文”后，平台在每个 Attempt 启动时（发布验证除外）签发一个上下文令牌，作为该 Connector 的额外请求头 `X-DSH-Work-Context` 下发给 DSH（与现有 Bearer 凭据同样经环境变量注入，不写入 patch 文件正文）。DSH 对该 Connector 的每次 MCP 请求都带上它，外部应用验证后据此识别员工、过滤数据并判断能否写入。

**令牌内容（JWS，HS256，EA3）：**

| 字段 | 内容 |
| --- | --- |
| `iss` | dsh-work 实例标识 |
| `aud` | Connector ID；外部应用只接受发给自己的令牌 |
| `iat`、`exp` | 签发时间；有效期覆盖 Attempt 启动与执行时限（与模型网关 Attempt 令牌的有效期算法相同） |
| `jti` | Attempt ID，只用于审计关联：同一令牌在该 Attempt 中随每次请求重复发送，不是一次性标识 |
| `run_id`、`agent_id` | 本次运行与执行的 Agent，供外部应用审计 |
| `visibility` | 结果可见类型，按结果实际给谁看判定（第 4 节“运行与结果受众”）：`shared`——项目空间中经 `authorizeTeamRunExecution` 授权的运行，包括讨论与任务对话、项目任务定时执行、他人重试、结果归属空间为项目空间的定时任务，以及无 Session 的 Task 执行接口（结果只给发起人，但数据范围按项目空间计算，从严按 `shared`）；`personal`——个人空间中的运行（员工本人的对话与定时任务），以及 Agent 主动任务（不论放在哪个空间，结果只给接收人） |
| `viewer` | 仅 `personal` 时出现，为披露用户（`disclosure_user_id`，主动任务为接收人）的标识（EA1）：`user_id`（平台用户 ID）、`mobile`（登录账号为手机号时，统一为去掉 `+86` 的 11 位号码，判定与 `normalizeLoginAccount` 相同）、`email`（登录账号为邮箱时）、`dingtalk_userid`（已绑定时） |

- **识别与过滤（EA2）：** 外部应用优先按 `mobile` 对应本系统员工，没有时依次用 `dingtalk_userid`、`email`；都对应不上的按无权限处理。`personal` 按该员工在外部应用中的数据权限返回，写入同样按其业务权限判断；`shared` 没有 `viewer`，只返回外部应用中对所有员工可见的数据，不允许写入。
- **签名密钥（EA3）：** 管理员为 Connector 开启调用上下文时，平台生成该 Connector 的随机密钥（256 位），以 `DSH_CREDENTIAL_MASTER_KEY` 加密入库（与 Bearer 凭据同一存储），只在生成时显示一次，由管理员复制到外部应用。“重新生成”后新 Attempt 立即使用新密钥；令牌头带 `kid`（密钥版本），外部应用在切换期间可同时接受新旧版本，以免正在执行的 Attempt 失败。管理员把新密钥配到外部应用之前，新运行对该 Connector 的调用会被拒绝；这段空窗作为重新生成的代价接受，不做两步切换，宜在低峰时操作。关闭调用上下文或删除 Connector 时销毁密钥。没有主密钥时不能开启。
- **不能吊销：** 令牌到期前有效，Attempt 提前结束不吊销；DSH Worker 随 Attempt 结束退出，令牌只出现在发往该 Connector 的请求中，`aud` 限定了它的用途。
- **发现与连通检查：** 管理端的连通测试、登记与发现清单不属于任何运行（登记前的测试也还没有 Connector ID），不带令牌；外部应用列出工具（`tools/list`）不要求令牌，调用工具时才要求（第 6 节）。
- **发布验证：** 发布验证的 Attempt 仍装载选定的 MCP，但工具调用由 DSH 策略返回 `trial_only`，不实际执行（功能规则第 9 节）。平台不为发布验证签发调用上下文，以免把发起验证的管理员标识发给外部应用；`tools/list` 不要求令牌，验证不受影响。
- **审计：** `mcp_invocation_audits` 记录调用时是否带调用上下文与 `visibility`。

### 5.2 需要提醒员工的场景（沿用现有能力）

员工为自己创建定时任务并把结果归属空间选为个人空间（或管理员为接收人配置 Agent 主动任务），选用已选定该外部应用 Connector 的 Agent，由 Agent 按计划经 MCP 查询外部应用中与本人相关的消息状态，整理后交给员工。开启调用上下文后，这类运行的 `visibility` 为 `personal`，`viewer` 是任务所有者（主动任务为接收人），外部应用据此只返回本人的消息。结果归属空间选为项目空间的定时任务是 `shared`，外部应用只返回对所有员工可见的数据，不能用于按本人查询的提醒。本文不改变定时任务与主动任务的规则，现有规则带来以下限制：

- **频率：** 最短为每天一次，不能按小时查询；
- **送达：** 运行成功不发通知，结果只在该次 Session（主动任务在该次 Task）中，员工要打开 dsh-work 查看；钉钉工作通知（DT-S2）规划中与定时任务相关的推送只有执行未成功与定时执行被暂停或停止（钉钉方案 4.1，DT16），成功不推送，主动任务的结果也不推送；
- **成本：** 每次运行都唤醒模型，没有新消息时也运行一次。

需要“有结果时通知员工”或更短的周期时，另行修改功能规则第 7 节，不在本文。

## 6. 外部应用的接入约定

外部应用由客户 IT 或其他团队按以下约定实现，作为接入前的检查清单：

- **MCP 服务：** Streamable HTTP；只提供愿意让 Agent 调用的工具；工具输入 Schema 稳定，变化须通知平台管理员确认能力变更；在 `annotations` 中如实标注只读与破坏性。
- **调用上下文：** 开启后验证 `X-DSH-Work-Context`：用管理员配置的密钥（按 `kid`）校验签名、`aud` 等于本 Connector、未过期；列出工具不要求令牌，调用工具时缺少或无效的令牌一律拒绝；`jti` 只用于审计关联，同一令牌会在一次 Attempt 中重复出现，不要用它防重放；不记录令牌原文。
- **识别员工与数据权限：** 优先按 `viewer.mobile`（去掉 `+86` 的 11 位号码）对应本系统员工，其次 `dingtalk_userid`、`email`，都对应不上按无权限处理；按该员工在本系统中的数据权限返回；`shared` 只返回本系统中对所有员工可见的数据。
- **写入工具：** 只在 `personal` 且有 `viewer` 时允许，按 `viewer` 在本系统中的业务权限判断能否执行；只写外部应用自身的记录（如跟进状态、录入的交期），不直接写 ERP 等权威系统；在写工具的输入参数中定义幂等键并按它去重（如 PF-07 靶场的 `operationKey`），dsh-work 不向 MCP 传递逐次调用 ID；结果中返回可核对的回执；记录 `viewer` 为操作人。
- **供定期查询的工具：** 需要提醒员工的场景，提供按 `viewer` 返回待处理消息的只读工具，供定时任务中的 Agent 调用（5.2）。

## 8. 风险

| 事项 | 处理 |
| --- | --- |
| 外部应用不验证令牌、识别或过滤错误、不按令牌授权写入 | 平台无法强制，列入第 6 节约定并在接入验收中检查；数据敏感或有写入的场景以通过该检查为接入条件 |
| 第三方 MCP 服务不认调用上下文且带写工具 | 不接入，或按 PF-07 手册只使用只读凭据 |
| 模型误解员工意思而调用写工具 | 外部应用只提供低风险写入（只改自身记录、可撤销）并记录操作人；需要员工本人确认时另行设计 |
| 运行的可见类型判错（如项目空间的定时任务按个人处理） | 按第 4 节“运行与结果受众”的授权分支判定，P1 覆盖项目空间的定时任务与主动任务 |
| 员工在 dsh-work 中没有手机号（登录账号为邮箱或旧账号） | 外部应用改用 `dingtalk_userid` 或 `email`，都对应不上按无权限处理；dsh-work 不为此新增手机号字段，需要时另行设计 |
| Agent 在 dsh-work 中的数据范围不限制 MCP 数据 | 与现状一致（设计规范 6.4）；按需为 Agent 选定 Connector，外部应用只提供愿意让 Agent 调用的工具 |
| 令牌在外部应用日志中泄露 | 有效期限于 Attempt，`aud` 限于一个 Connector；约定外部应用不记录令牌原文 |
| 密钥在外部应用泄露 | 影响限于该 Connector（`aud`），管理员重新生成密钥 |
| 定期查询的时效与成本 | 现有定时任务最短每天一次、成功不通知、每次唤醒模型（5.2）；不满足时另行修改功能规则第 7 节 |

## 9. 分期

只有一个阶段：**EA-S1 调用上下文**——Connector 开关与密钥、令牌签发与下发、审计字段、管理端展示。
