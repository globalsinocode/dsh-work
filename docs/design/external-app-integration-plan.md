## 1. 背景与目标

2026-11-17 确定分工：业务规则、业务状态与主动发现由外部业务应用承担，经 MCP 提供给 dsh-work；dsh-work 的 Agent 作为员工与外部系统之间的中介（查询、解释、比较方案、起草，以及经外部应用授权的写入），平台不保存外部业务事实。Agent 只做协调，不作为业务记录方。

按这个分工接入外部应用，dsh-work 缺一项通用能力：**调用上下文**。MCP 只用 Connector 的共享凭据，外部应用不知道这次是哪位员工、结果给谁看，无法按人过滤数据，也无法判断能否写入。

目标是把它做成通用机制：任何外部应用只需遵守第 6 节的约定即可接入，dsh-work 不为具体业务场景增加对象、页面或计算。

## 2. 边界

- **数据权限以外部应用为准（2026-11-18 确认）：** 外部应用按员工在它自己系统中的数据权限返回数据，dsh-work 不把自己的数据范围传给外部应用（EA2）。因此 Agent 在 dsh-work 中被授予的数据范围不限制它经 MCP 读到的数据（与设计规范 6.4 的现状一致）；要限制某个 Agent 能接触的外部数据，靠是否为它选定该 Connector，以及外部应用提供哪些工具。
- **写入的授权由外部应用负责（2026-11-17 确认）：** 外部应用凭调用上下文（5.1）判断操作人与结果可见类型，决定是否允许写入，并且只提供愿意让 Agent 调用的工具。dsh-work 不区分工具读写，不设写入准入，沿用现有的“新增或 Schema 变化的工具须管理员确认能力变更”。不认调用上下文的第三方 MCP 服务若带有不愿开放的写工具，不接入，或按 PF-07 手册只使用只读凭据。员工本人确认后才执行的写入（依赖持久化等待的验收与 DSH 按工具请求权限）不在本文，出现需要时另行设计。
- **不提供外部推送入口（2026-11-17 确认）：** 外部应用不经 dsh-work 推送消息。需要提醒员工的场景，由 dsh-work 中的 Agent 按计划经 MCP 查询外部应用的消息状态，把结果交给员工（5.2）。
- **不保存外部业务事实：** 业务数据留在外部应用，Agent 需要时经 MCP 读取。
- **不新增执行路径：** 调用上下文不调用模型，不改变 Run/Attempt → Runtime Adapter → DSH 的执行链路。
- **不建连接器网关：** MCP 调用仍由 DSH 直连外部应用，平台只在每个 Attempt 的配置中多下发几个请求头（与设计规范 6.4 一致）。

## 5. 方案

### 5.1 调用上下文（EA-S1）

**做法：** 管理员为 Connector 开启“发送员工身份”后，平台在每个 Attempt 启动时（发布验证除外）计算本次的调用上下文，作为该 Connector 的额外请求头下发给 DSH（与现有 Bearer 凭据同样经环境变量注入，不写入 patch 文件正文）。DSH 对该 Connector 的每次 MCP 请求都带上这些请求头；外部应用先按 Bearer 凭据确认请求来自 dsh-work，再据请求头识别员工、过滤数据并判断能否写入。

**请求头（明文，EA3）：** 下文的 `viewer`（员工标识）指 `X-DSH-Work-Viewer-*` 这组请求头所代表的员工：`personal` 运行中的披露用户（`disclosure_user_id`，主动任务为接收人）；`shared` 运行没有 `viewer`。

| 请求头 | 内容 |
| --- | --- |
| `X-DSH-Work-Visibility` | 结果可见类型，按结果实际给谁看判定（第 4 节“运行与结果受众”）：`shared`——项目空间中经 `authorizeTeamRunExecution` 授权的运行，包括讨论与任务对话、项目任务定时执行、他人重试、结果归属空间为项目空间的定时任务，以及无 Session 的 Task 执行接口（结果只给发起人，但数据范围按项目空间计算，从严按 `shared`）；`personal`——个人空间中的运行（员工本人的对话与定时任务），以及 Agent 主动任务（不论放在哪个空间，结果只给接收人） |
| `X-DSH-Work-Viewer-User-Id` | 仅 `personal` 时出现：披露用户（`disclosure_user_id`，主动任务为接收人）的平台用户 ID |
| `X-DSH-Work-Viewer-Mobile` | 仅 `personal` 且登录账号为手机号时出现：去掉 `+86` 的 11 位号码（判定与 `normalizeLoginAccount` 相同） |
| `X-DSH-Work-Viewer-Email` | 仅 `personal` 且登录账号为邮箱时出现；含非 ASCII 字符的邮箱在计算请求头时略去（请求头只能是 ASCII；现有下发校验只拒绝换行，交给它会使整个 Attempt 失败） |
| `X-DSH-Work-Viewer-Dingtalk-Userid` | 仅 `personal` 且已绑定钉钉时出现 |
| `X-DSH-Work-Run-Id`、`X-DSH-Work-Attempt-Id`、`X-DSH-Work-Agent-Id` | 本次运行、Attempt 与执行的 Agent，供外部应用审计关联；同一 Attempt 中的每次请求相同，不是逐次调用标识 |

- **识别与过滤（EA2）：** 外部应用优先按 `X-DSH-Work-Viewer-Mobile` 对应本系统员工，没有时依次用钉钉 userid、邮箱；都对应不上的按无权限处理。`personal` 按该员工在外部应用中的数据权限返回，写入同样按其业务权限判断；`shared` 没有员工标识，只返回外部应用中对所有员工可见的数据，不允许写入。
- **开启条件：** 由平台检查：认证方式为 Bearer（没有凭据的 Connector 任何人都能伪造这些请求头），且该凭据为本 Connector 独占（平台中可能有共用一份凭据的旧 Connector，共用时另一个 MCP 服务也会拿到这份凭据，从而能冒充员工；须先“更换凭据”拆开）；凭据被共用后不能再开启，已开启的 Connector 在凭据变为共用时自动关闭并在管理端提示。由管理员与外部应用保证、平台无法检查：该凭据只配置在 dsh-work 与这个外部应用中，不与其他调用方共用；跨网络访问的外部应用使用 HTTPS（凭据与员工标识都在请求中明文传输）。
- **开关与界面：** 开关在管理端“MCP 连接器”的 Connector 详情中，名称“发送员工身份”，默认关闭。说明文字：“开启后，结果只给一个人看的调用——员工本人的对话和个人定时任务，以及 Agent 主动任务（包括放在项目空间中的，员工身份为接收人）——会附带该员工的平台用户 ID、手机号、邮箱和钉钉账号，由应用按该员工的权限返回数据、判断能否写入；项目空间中结果多人可见的调用只告知‘结果多人可见’，不附带员工身份。仅在应用已按接入约定改造、且 Bearer 凭据只给 dsh-work 使用时开启。”开关变化只影响此后新启动的 Attempt。连接器列表标出哪些 Connector 在发送员工身份。
- **更换凭据：** 沿用现有“更换 Bearer 凭据”。怀疑凭据泄露时更换凭据，旧凭据在外部应用中作废后，持有者不能再冒充员工。
- **发现与连通检查：** 管理端的连通测试、登记与发现清单不属于任何运行，不带调用上下文；外部应用列出工具（`tools/list`）不要求调用上下文，调用工具时才要求（第 6 节）。
- **发布验证：** 发布验证的 Attempt 仍装载选定的 MCP，但工具调用由 DSH 策略返回 `trial_only`，不实际执行（功能规则第 9 节）。平台不为发布验证发送调用上下文，以免把发起验证的管理员标识发给外部应用；`tools/list` 不要求调用上下文，验证不受影响。
- **审计：** `mcp_invocation_audits` 记录调用时是否带调用上下文与 `visibility`。

### 5.2 需要提醒员工的场景（沿用现有能力）

员工为自己创建定时任务并把结果归属空间选为个人空间（或管理员为接收人配置 Agent 主动任务），选用已选定该外部应用 Connector 的 Agent，由 Agent 按计划经 MCP 查询外部应用中与本人相关的消息状态，整理后交给员工。开启“发送员工身份”后，这类运行的 `visibility` 为 `personal`，`viewer` 是任务所有者（主动任务为接收人），外部应用据此只返回本人的消息。结果归属空间选为项目空间的定时任务是 `shared`，外部应用只返回对所有员工可见的数据，不能用于按本人查询的提醒。本文不改变定时任务与主动任务的规则，现有规则带来以下限制：

- **频率：** 最短为每天一次，不能按小时查询；
- **送达：** 运行成功不发通知，结果只在该次 Session（主动任务在该次 Task）中，员工要打开 dsh-work 查看；钉钉工作通知（DT-S2）规划中与定时任务相关的推送只有执行未成功与定时执行被暂停或停止（钉钉方案 4.1，DT16），成功不推送，主动任务的结果也不推送；
- **成本：** 每次运行都唤醒模型，没有新消息时也运行一次。

需要“有结果时通知员工”或更短的周期时，另行修改功能规则第 7 节，不在本文。

## 6. 外部应用的接入约定

外部应用由客户 IT 或其他团队按以下约定实现，作为接入前的检查清单：

- **MCP 服务：** Streamable HTTP；只提供愿意让 Agent 调用的工具；工具输入 Schema 稳定，变化须通知平台管理员确认能力变更；在 `annotations` 中如实标注只读与破坏性。
- **认证与调用上下文：** 使用只发给 dsh-work 的 Bearer 凭据认证每个请求，凭据无效的请求一律拒绝；跨网络访问时提供 HTTPS。开启“发送员工身份”后，只信任凭据有效的请求中的 `X-DSH-Work-*` 请求头；列出工具不要求调用上下文；调用工具时，以下请求一律拒绝：缺少 `X-DSH-Work-Visibility` 或取值不是 `personal`、`shared`；`personal` 却没有任何 `X-DSH-Work-Viewer-*`；`shared` 却带有 `X-DSH-Work-Viewer-*`。`X-DSH-Work-Attempt-Id` 只用于审计关联，同一 Attempt 的请求会重复携带，不要用它防重放。请求头含员工手机号与邮箱，按个人信息处理，不在访问日志中原样记录。
- **识别员工与数据权限：** 优先按 `X-DSH-Work-Viewer-Mobile`（去掉 `+86` 的 11 位号码）对应本系统员工，其次钉钉 userid、邮箱，都对应不上按无权限处理；按该员工在本系统中的数据权限返回；`shared` 只返回本系统中对所有员工可见的数据。
- **写入工具：** 只在 `personal` 且有员工标识时允许，按该员工在本系统中的业务权限判断能否执行；只写外部应用自身的记录（如跟进状态、录入的交期），不直接写 ERP 等权威系统；在写工具的输入参数中定义幂等键并按它去重（如 PF-07 靶场的 `operationKey`），dsh-work 不向 MCP 传递逐次调用 ID；结果中返回可核对的回执；记录该员工为操作人。
- **供定期查询的工具：** 需要提醒员工的场景，提供按员工返回待处理消息的只读工具，供定时任务中的 Agent 调用（5.2）。

## 8. 风险

| 事项 | 处理 |
| --- | --- |
| 外部应用不校验凭据、识别或过滤错误、不按调用上下文授权写入 | 平台无法强制，列入第 6 节约定并在接入验收中检查；数据敏感或有写入的场景以通过该检查为接入条件 |
| Bearer 凭据泄露，持有者冒充任意员工调用外部应用 | 明文请求头的主要代价（EA3）。凭据只发给 dsh-work、不与其他调用方共用；跨网络使用 HTTPS；外部应用不在日志中记录凭据；怀疑泄露时更换凭据。接入由客户 IT 或第三方开发、或数据更敏感（如薪资）的外部应用时，评估升级为签名令牌（请求头字段不变，外部应用增加验签） |
| 请求头中的手机号、邮箱进入外部应用或中间代理的日志 | 约定外部应用按个人信息处理，不原样记录；只为开启开关的 Connector 发送（EA4） |
| 第三方 MCP 服务不认调用上下文且带写工具 | 不接入，或按 PF-07 手册只使用只读凭据 |
| 模型误解员工意思而调用写工具 | 外部应用只提供低风险写入（只改自身记录、可撤销）并记录操作人；需要员工本人确认时另行设计 |
| 运行的可见类型判错（如项目空间的定时任务按个人处理） | 按第 4 节“运行与结果受众”的授权分支判定，P1 覆盖项目空间的定时任务与主动任务 |
| 员工在 dsh-work 中没有手机号（登录账号为邮箱或旧账号） | 外部应用改用钉钉 userid 或邮箱，都对应不上按无权限处理；dsh-work 不为此新增手机号字段，需要时另行设计 |
| Agent 在 dsh-work 中的数据范围不限制 MCP 数据 | 与现状一致（设计规范 6.4）；按需为 Agent 选定 Connector，外部应用只提供愿意让 Agent 调用的工具 |
| 定期查询的时效与成本 | 现有定时任务最短每天一次、成功不通知、每次唤醒模型（5.2）；不满足时另行修改功能规则第 7 节 |

## 9. 分期

只有一个阶段：**EA-S1 调用上下文**——Connector 的“发送员工身份”开关（仅 Bearer 认证且凭据独占）、调用上下文请求头的计算与下发、审计字段、管理端展示。签名令牌不在本阶段，需要时另立阶段（EA3）。
