## 1. 产品目标与交付边界

团队负责人能够组建由员工成员与 Agent 成员组成的团队；员工能够选择团队中的 Agent，使用共同资料开展对话，并在自己的历史对话中找到、恢复和继续这些对话。Agent 成员来自平台已发布的 Agent，通过空间关联加入，不复制 Agent 配置。工作空间同时承担内容归属、协作发现和访问边界，空间角色不能扩大员工的企业数据权限。

首版完整用户流程：

1. 负责人创建空间，从企业员工目录添加成员。
2. 从平台允许范围内添加 Agent 成员，确认员工可以使用它发起分析。
3. 成员上传共享资料，另一名成员引用该资料开始自己的对话。
4. 成员能找到、恢复和继续自己的历史对话，同一会话只出现一条记录。
5. 管理员调整成员资格或角色后，页面、接口、下载和执行权限随之收敛。

范围划分：

- P0 为本次团队协作交付的必需项，由批次 1A（成员、Agent 与授权基础）与批次 1B（团队资料与本人对话）共同构成；1A 完成不代表全部 P0 完成。
- P1 完善空间生命周期、资料维护和团队动态。
- P2 根据真实使用反馈安排，不纳入首版承诺。
- 首版不包含多人同时续写同一会话、在线共同编辑文件、跨企业邀请、内容分享与派生、跨空间访问、匿名公开链接和外部系统写入。
- 个人空间完全保持现状：保留默认个人空间、现有 Agent／Skill 入口、版本解析与执行授权；不添加员工或 Agent 成员，不接入团队内容共享、来源依赖、归档和通知功能，不调整个人文件、成果或会话模型。
- 本文的“空间”“成员”等新增规则均指团队空间。个人空间现有接口不要求提交团队 Agent 关联 ID，也不因未加入 Agent 而阻止原有对话。

| --- | --- | --- |

个人空间当前不检查 `workspace_capability_grants`，该检查仅在团队空间分支执行；员工身份、Agent、Skill、Tool 与数据范围校验仍保留，见[授权分支](../../server/src/modules/authorization/postgres-authorization-service.ts)。本方案不修改这一区分。

## 3. 界面方案：保留现有布局

### 3.1 必须保留的页面基准

- 复用现有 `EmployeeShell` 应用壳层、导航、最近对话区域和账户入口。
- 工作空间列表继续使用现有空间卡片、搜索栏和创建弹窗。
- 空间详情保留“对话／共享文件／成果”三个顶部页签，不新增六页签主布局。
- 右侧继续使用 `WorkspaceInfoPanel`，保留折叠能力；小屏继续使用现有空间信息抽屉。
- 复用现有组件、图标、[Design Token](../../packages/design-tokens/src/tokens.css)、字体、配色、间距与按钮样式，不新增独立主题。
- 页面级标题保持一次；已有空间信息栏负责空间身份与说明，不再在主内容区域叠加重复的大标题和统计卡。
- 复用组件增加团队专用分支，不改变个人空间现有渲染和交互；个人空间不显示 Agent 成员、成员管理或归档入口。

### 3.2 新增入口的落点

| 功能 | 入口与呈现 | 布局约束 |
| --- | --- | --- |
| 历史对话 | 对话页签内提供“历史对话”切换；历史视图可返回“新对话” | 复用原有新对话组件，历史列表占据同一内容区域 |
| 成员管理 | 右侧成员区同时展示员工与 Agent，增加“管理成员”；弹窗内区分“员工／Agent” | 保留原成员摘要和头像展示；Agent 使用图标与文字标识，不混入员工人数 |
| Agent 成员 | 成员弹窗内提供“添加员工／添加 Agent”；Agent 条目提供“开始对话”和有权限的管理操作 | 不再另设“可用能力”入口；能力说明、版本与状态放入 Agent 成员详情 |
| 空间设置 | 右侧信息栏操作入口打开设置弹窗 | 修改说明、转交、退出、归档按权限呈现 |
| 共享文件 | 沿用现有文件页签列表，增加紧凑搜索和稳定行操作 | 类型、状态、版本、操作按密度安排；宽度使用可用内容区 |
| 动态 | 右侧“最近动态”摘要和“查看全部”抽屉，随 P1 开放 | 动态不占用第四个主内容页签 |

列表使用项目现有列表或数据表格组件。表格场景不得以原生 `<table>` 取代已有组件。新增筛选靠左、主要操作靠右；正文列表与内容面板使用可用宽度。

### 3.3 通用状态与反馈

| 状态 | 呈现与交互 |
| --- | --- |
| 加载 | 在对应区域显示骨架或加载态；不闪现“空间不存在” |
| 空数据 | 区分空间尚无内容、本人尚无内容与筛选无结果；提供有权限的下一步 |
| 错误 | 保留输入与已加载内容；说明失败对象、原因、重试方式 |
| 无权限 | 写操作不渲染；无读取权限时不返回名称、摘要、数量或下载信息 |
| 不可用 | 区分尚未加入 Agent、Agent 停用、能力未授权、Runtime 不可用与文件解析失败 |
| 成功 | 更新对应条目、数量和操作状态；反馈实际完成的业务动作 |
| 归档 | 空间级只读提示；隐藏新增、续写、上传动作，保留有权限的查看与下载 |

弹窗使用现有表单与 footer 顺序；删除、移除、转交、归档进行二次确认。所有字段有 label，图标按钮有可访问名称，支持键盘和焦点恢复。清空可选说明时 API 显式传递 `null`，由服务端归一化为存储约定的空值，不用 `undefined` 表示清空。

## 4. 功能清单与产品规则

### TW-01 员工成员与角色管理 · P0

- 从当前企业内有效业务员工目录搜索选择成员；仅返回成员选择所需的姓名、部门等最小信息，不能把管理端全量身份数据直接开放给员工端。
- 添加已有成员保持幂等，不生成重复关系；离职、停用、无应用访问资格的账户不能添加为有效成员。
- 支持负责人、管理员、成员、只读成员。管理员只能管理成员与只读成员；只有负责人能任免管理员、转交负责人。
- 唯一负责人不可直接移除或退出。转交采用事务，任何时刻保留一个有效负责人；不改写内容最初创建者。
- 移除成员后立即撤销其后续空间访问，保留其已上传共享文件及作者归属；原有下载链接仍需重新鉴权。
- 主动退出与被移除采用相同的权限、在途执行和内容保留规则；退出不转移业务内容或作者归属。失去成员资格后也不能继续访问该团队空间。
- 负责人停用等异常交由有明确治理权限的平台管理员处理，不默认开放空间私有对话正文。
- 成员界面统一展示两种成员类型；本节的企业员工目录和负责人／管理员／成员／只读成员角色只适用于员工。Agent 成员按 TW-02 管理，不具有员工登录身份或空间管理角色。

### TW-02 添加与使用 Agent 成员 · P0

- **适用空间：** Agent 成员仅用于团队空间。个人空间的现有 Agent／Skill 使用方式与执行授权保持不变，不迁移为成员模式。
- **成员呈现：** 例如“林岚 · 负责人”“陈默 · 员工成员”“订单分析助手 · Agent”。摘要显示“4 位员工 · 2 个 Agent”，Agent 条目展示名称、职责与可用状态；版本放入详情，避免混入普通员工角色选择。
- **加入流程：** 负责人在现有成员区域选择“添加 Agent”，从平台已发布且允许加入该空间的 Agent 中搜索选择，查看职责、关联技能、所需工具与数据范围后确认加入。普通管理员首版不获授添加或管理 Agent 的权限。
- **关联模型：** 加入操作建立空间与平台 Agent 的引用关系，固定当前启用版本。同一空间内同一 Agent 不重复加入，不允许在空间中另建一份 Agent 定义或修改其模型、凭据、Skill、Tool 配置。
- **授权生效：** 添加时复用现有精确版本授权，校验 Agent、Skill 及 Tool 依赖。只有关联及授权事务成功后才成为可用成员；Skill 不能间接扩大 Agent 的 Tool Allowlist。
- **状态与管理：** Agent 成员支持可用、已停用、不可用及移出状态。负责人可添加、停用、重新启用、升级和移出；成员详情显示平台未授权、版本失效或 Runtime 不可用的具体原因。
- **空态：** 新空间显示“尚未加入 Agent”。负责人可以添加 Agent，普通员工看到联系负责人提示；加入可用 Agent 后开放相应对话入口。
- **发起对话：** 点击 Agent 成员的“开始对话”，进入现有新对话区域并预选该 Agent；也可在新对话输入区选择团队中的 Agent。只有一个可用 Agent 时可默认选中，但必须明确显示身份；多个 Agent 时由用户选择。
- **单一会话绑定：** 首版每个产品 Session 固定一个 Agent 版本，后续消息继续由它处理。需要换 Agent 时新建对话，可带入明确获准共享的内容；不在原 Session 内静默切换 Agent。
- **执行身份：** Agent 为 AI 成员，没有独立员工账户。每次执行记录实际发起员工及 Agent 版本，权限取发起员工权限、空间授权与 Agent 允许能力的交集。
- **内容边界：** 加入空间不会使 Agent 自动读取所有共享文件、成员对话或成果；仅在用户发起任务时访问显式引用或受控工具获准返回的内容。成果保留发起员工归属，同时展示由哪个 Agent 生成，读取范围不因 Agent 加入空间而扩大。
- **版本升级：** 平台发布新版本时提示负责人显式升级，新会话使用升级后的版本；既有 Session、Run、Attempt 保持原快照。旧版本仍获授权时可以继续使用，失效或撤权时明确阻止并引导使用新 Agent 会话。
- **停用与移出：** 阻止该关联的后续启动、续写和重试；排队与活动任务通过既有调度和取消链路收敛。历史消息、成果与 Agent 版本来源保留，不删除平台 Agent，也不撤销其他 Agent 仍需要的共享工具授权。
- **首版触发边界：** Agent 由员工显式发起任务；不自动监听团队消息，不自动发言，不触发 Agent 之间的循环调用。未来若增加 `@Agent`，先作为新对话的选择快捷方式，与已有 `@Skill` 明确区分；群聊多 Agent 协作需另行定义产品与执行契约。
- 所有 Agent 执行继续走既有 Run/Attempt → Runtime Adapter → DSH。DSH 不可用时报告不可用，禁止另建模型调用循环或自动直连模型回退。

### TW-03 空间历史对话 · P0

- 提供本空间“我的对话”：搜索标题、按最近活动排序、服务端分页。
- 历史列表固定为发起人本人的范围，服务端按当前登录员工强制过滤，不接受由前端传入的范围参数；空间内的会话列表不向其他成员展示标题、摘要或数量。
- 首版标题沿用现有确定性规则：以首条输入去除首尾空白后作为标题，超过 40 个字符时截取前 40 个并加省略号；后续发送不自动改名。本方案不引入模型生成标题，也不调整个人空间标题行为。
- 列表一条对应一个产品 Session，显示标题、发起人、最近活动时间与最新运行状态。Run/Attempt 留在详情中追溯。
- 服务端在会话汇总后再分页和计算数量，不能先限制 Run 数量后由前端去重。
- 继续发送消息只创建新 Run、更新原 Session 的活动时间和列表位置；旧 Run 的延迟事件不能覆盖最新运行状态。
- 团队空间内新对话默认仅发起人可读。负责人、管理员不能因为管理角色自动读取其他人的私有对话。
- 内容分享、来源快照与派生（原“共享快照”部分）已随 2A／2B 放弃，见 §9.1。

### TW-05 共享文件使用闭环 · P0

- 复用现有上传、解析与引用链路，补齐列表下载、名称搜索、上传人、时间和状态信息。
- 保留 PDF、DOCX、XLSX、CSV、TXT、Markdown 与单文件 20 MB 上限；继续遵守当前运行的文件数量和解析文本预算，不因空间共享扩大限额。
- 区分上传中、检查中、解析中、可引用、失败和已移除。只有通过适用安全检查且解析成功的不可变文件对象可进入 Run。
- 正常成员可上传、下载、引用，并移除自己上传的空间文件；负责人和管理员可移除空间共享文件。只读成员仅查看和下载。
- P0 引用时固定不可变文件对象 ID、解析结果 ID 及既有内容快照，不仅把文件名拼入提示词。用户可管理的逻辑文件、版本号和升级入口属于 P1 的 TW-07，P0 不依赖这些入口。
- 空间共享文件与私有对话附件保持区分。附件不自动成为团队文件，文件名、大小和数量也遵循读取权限。
- 移除属于逻辑移除：不再出现在有效列表，不允许新引用；已使用版本仍按历史运行权限保留。后台物理清理由独立保留策略控制。
- 文件的逻辑移除属于目录维护，不等同于来源权限撤销。若同时发生成员收权或来源数据访问撤销，历史读取仍按当前授权拒绝，不能以保留快照绕过权限。

### TW-06 空间设置与生命周期 · P1

- 修改名称与说明；负责人可转交、归档和恢复。普通成员可主动退出，负责人必须先转交；该不变量从 TW-01 开始生效。
- 主动退出后已有共享文件与成果保持原状态和作者归属；退出者的空间访问和在途运行按 TW-01 收敛。
- 首版管理闭环以归档代替永久删除。复用已有 `status` 和 `archived_at` 字段：归档写入时间，恢复清空当前归档时间，历史归档／恢复动作由审计记录保留。
- 团队列表支持活动／归档筛选，默认活动；归档筛选只查当前用户仍有权访问的团队空间。个人空间列表、状态和入口保持现状。
- 归档阻止新对话、续写、重试和上传，保留有权限的只读访问与下载。
- 为避免运行结果落入归档状态的歧义，有排队或活动运行时暂不允许归档；提示先等待完成或通过现有取消链路停止运行。
- 恢复不自动恢复已经移除的成员，不扩大能力授权；继续检查员工与依赖当前是否有效。
- 归档空间仍允许必要的访问撤销与负责人治理，不能以只读状态阻止紧急收权。

### TW-07 文件更新与版本 · P1

- 在同一逻辑文件下上传新版本，记录上传人、时间和更新说明；不通过同名覆盖修改既有文件对象。
- 新版本检查、解析成功前，旧的有效版本继续可用；新版本失败不破坏旧版引用。
- 新引用默认使用最新有效版本；已加入对话的文件固定到所选版本，升级需要显式重新选择。
- 历史对话、成果和 Run 可以追溯实际输入版本。版本读取和下载同样重新鉴权。
- 并发上传采用明确版本分配或冲突反馈，避免不同上传覆盖为同一版本。

### TW-08 团队动态与通知 · P1

- 展示成员变动、文件上传与移除等有协作价值的事件。
- 普通发送消息与未共享对话活动不进入团队动态；审计日志与团队动态使用不同的可见投影。
- 首版采用站内通知，支持未读标记及按空间关闭提醒，不接入邮件、短信或外部聊天发送。
- 通知接收时与点击时均检查可见权限；失去权限后不能通过旧通知读取正文或敏感名称。
- 业务成功后通过持久化事件生成通知，同一事件幂等去重；通知失败不能把已成功的业务变更伪装为失败。

### TW-10 空间共享讨论与 @Agent 触发 · 已交付（实时推送待补）

**范围决定（2026-09-17，产品确认）：** 团队空间对话区由「发起人私有的 Agent 会话」改为「全部成员可见的共享讨论」。本节取代 TW-02「首版触发边界」中关于 `@Agent` 的预留口径，以及 TW-03「历史列表固定为本人范围」的过滤规则；个人空间行为不变（AC-23 红线继续成立）。

- **讨论模型：** 团队会话仍是「一条 = 一个话题」的消息流，但读取与发言范围由发起人扩大为全部空间成员。普通消息是成员间讨论，**不产生 Run**（`messages.run_id` 可空，无需新表）；会话标题沿用首条输入的确定性截断。
- **@Agent 触发：** 消息中 @ 某个当前可发起的 Agent 成员时才创建 Run：绑定该成员加入时的固定版本（复用 `workspaceAgentMemberId` 与 `resolveTeamSessionAgentVersion` 的服务端校验），执行身份仍为发起员工，权限取发起员工 ∩ 空间授权 ∩ Agent 能力的交集。不 @ 不触发；Agent 不监听讨论、不自动发言、不发生 Agent 之间的循环调用（TW-02 触发边界其余部分不变）。
- **回复可见性（已决策）：** Agent 回复进入共享消息流，对全部空间成员可见。即显式接受「发起者数据范围产出的内容广播给空间成员」的泄露面；回复必须标注发起人（`requestedBy`）与执行 Agent 成员及版本，行内展示「由 X 发起」标记，使广播行为可审计、可归因。
- **权限：** 发讨论消息与 @ 触发要求当前成员资格且非只读；只读成员可读讨论流。成员移除、空间归档后停止向其投递新消息与运行事件（沿用 §6.5 收权链路）。
- **实施前收敛项：** ① `sessions.agent_version_id` 现为 NOT NULL，纯讨论会话无 Agent——需放开可空或引入讨论会话类型；② 成员间消息可见需要新的拉取/推送通道，现有 SSE 只面向 Run 发起者；③ Run 的 `conversation_history` 会混入他人讨论消息，需定带入窗口与归属口径；④ 会话删除、通知、「使用中」预选语义随共享重新定义。
- **实施口径（2026-09-18 交付，收敛项逐条落定）：** ① 迁移 0041 放开 `agent_version_id` 可空，无新表；② 消息可见经 `GET /sessions/:sessionId` 共享线程拉取（含 `currentUserRole`、发送者/触发人/Agent 归因、Run 状态列表），成员级实时推送未实现——当前靠刷新/重开会话拉取，SSE 仍只覆盖 Run 事件，推送通道与收权断流列为后续项；③ 团队会话的 `conversation_history` 纳入全部讨论消息（`run_id` 为空者同样带入），用户消息统一加「发送者：」前缀，个人会话不加以保持契约不变；④ 会话删除沿用创建者独占（`archiveSession` 按 `created_by`）——首版明确：创建者可删除含其他成员消息的讨论串，删除即全员不可见，如需成员级删除/管理员介入另行立项；「使用中」预选语义调整为唯一可发起成员自动预选 + 显式选择不被覆盖；Run 详情与续写接口返回 `currentUserRole`，前端据此对只读成员隐藏输入框与停止/重试入口。

## 5. 权限矩阵与内容边界

以下为团队空间活动状态下员工角色的拟定权限，不用于调整个人空间现有权限；所有“允许”仍须满足员工有效身份、应用权限、数据范围与对象读取条件。Agent 不作为第五种员工角色，不拥有管理成员、邀请员工或扩大授权的自主权限。

| 操作 | 负责人 | 管理员 | 成员 | 只读成员 |
| --- | --- | --- | --- | --- |
| 查看空间资料、成员摘要 | 允许 | 允许 | 允许 | 允许 |
| 新建或继续自己的对话 | 允许 | 允许 | 允许 | 不允许 |
| 查看他人私有对话与未发布成果 | 不允许 | 不允许 | 不允许 | 不允许 |
| 上传或引用共享文件 | 允许 | 允许 | 允许 | 不允许 |
| 移除共享文件 | 全部 | 全部 | 自己上传的 | 不允许 |
| 添加或管理普通成员、只读成员 | 允许 | 允许 | 不允许 | 不允许 |
| 任免管理员 | 允许 | 不允许 | 不允许 | 不允许 |
| 添加、停用、升级、移出 Agent 成员 | 允许 | 不允许 | 不允许 | 不允许 |
| 修改空间设置 | 允许 | 不允许 | 不允许 | 不允许 |
| 转交、归档、恢复 | 允许 | 不允许 | 不允许 | 不允许 |
| 退出 | 先转交 | 允许 | 允许 | 允许 |

执行原则：

1. **管理权与内容读取权分离。** 成员与 Agent 关联可治理，私有正文不可因管理身份而开放。
2. **企业权限与空间权限取交集。** 团队资格、内容可见范围、来源数据约束都必须满足，空间授权不能越过平台授权上限。
3. **内容读取校验当前身份。** 团队文件等共享对象的快照不可变不意味着永久可访问；企业权限或来源数据访问收回后，后续读取必须被拒绝。
4. **不自动公开既有内容。** 历史私有对话、成果与附件迁移后保持原访问范围；不因加入团队空间而互相可见。
5. **收权覆盖整个链路。** 列表、详情、搜索、计数、文件下载、SSE 续传、Run 启动、重试与工具读取都重新检查；不能只隐藏按钮。
6. **在途运行收敛。** 成员被移除后阻止新请求与排队任务启动，对活动运行使用既有取消链路；撤销订阅，不再向失权者交付后续内容，终态和竞态必须可审计。

以上收权机制是本次团队功能需要补齐的工程能力，不能视为现有链路已经具备。现有 SSE 在建连时鉴权，循环推送未持续检查团队权限；现有调度在领取任务后直接执行，尚需增加执行前的团队授权复核，具体工作见第 6.5 节。

## 6. 服务端与数据实施方案

### 6.1 模块职责

| 模块 | 实施责任 |
| --- | --- |
| 员工端页面、Store、API Client | 承接原页面入口，展示服务端允许的动作、分页结果和错误状态 |
| Workbench API | 员工侧空间、成员、会话与文件接口；从请求身份取得操作人 |
| Admin API 与治理页面 | 配置平台能力允许范围、处理负责人失效等有明确权限的治理操作 |
| Workspace / Content 应用服务 | 员工与 Agent 成员关联、生命周期事务、文件版本和按本人范围的内容查询 |
| Authorization | 团队角色、平台能力上限、对象和来源范围校验，统一团队执行与读取边界；个人空间原有授权分支不变 |
| Run / Runtime Adapter | 复用原有执行、取消、重试、事件与不可变 Manifest；增加团队撤权通知、执行前复核及事件交付拦截，不另建 Agent 引擎 |
| Audit / 通知投影 | 记录业务变更事实，生成按权限过滤的团队动态 |

共享 UI 包保持无业务状态。共享对话或成果访问通过独立团队投影实现，不直接删除既有查询中的 `created_by` 或 `requested_by` 条件来开放全部 Run 数据。团队专用参数和拦截逻辑按服务端解析的空间类型生效，不能要求个人空间补成员关联或团队授权数据。

新增团队历史会话入口使用稳定 Session 身份；现有以 Run ID 打开的团队链接保留兼容解析并先鉴权，不能通过跳转暴露无权访问的空间或会话。个人空间的入口与链接行为保持现状。保存成员与能力等关键动作支持幂等及版本冲突处理。

### 6.3 数据对象与不变量

| 对象 | 复用或新增方向 | 不变量 |
| --- | --- | --- |
| 工作空间与员工成员 | 复用 `workspaces`、`workspace_members` 与四种角色枚举；团队负责人取 `member_role = owner` 的成员关系 | 创建者与当前负责人分离；补团队恰有一个负责人的事务及数据库约束，不要求新增重复 owner 列 |
| Agent 成员关联 | 新增空间与 Agent 的关联实体，记录版本、状态、加入人和时间 | 不伪造 `users` 记录；同一空间同一 Agent 唯一；成员 DTO 显式区分 employee 与 agent |
| 能力授权 | 复用 `workspace_capability_grants` 作为有效授权集合，新增授权与来源之间的多对多关系 | 一个工具授权可有多个 Agent 或既有人工来源；撤销单个来源不误删其他有效来源 |
| Session 查询 | 复用 `sessions`、`runs`，增加必要查询索引与摘要投影 | 按 Session 去重且稳定排序；Run 事实不丢失 |
| 文件版本 | 在现有不可变 `file_objects` 外增加逻辑文件与版本关系 | 旧存储对象、解析结果、`run_input_files` 不被覆盖 |
| 生命周期、审计与事件 | 复用 `status`、`archived_at`，补团队授权修订标识、持久化撤权事件与通知消费状态 | 提交成功才生成有效事件；归档字段不重复增加；不存私有正文、凭据或隐藏推理 |

重点修正：当前空间摘要使用创建者展示负责人，并直接统计空间关联的会话和成果。转交负责人后应按当前 owner 展示；统计应按用户可见范围计算，并与分页列表口径一致，排除已移除、不可见和不应计入的版本。

团队负责人以成员关系为单一事实来源。转交锁定空间行，在同一事务更新旧、新负责人的角色，提交时必须恰有一个 owner。数据库约束只针对团队空间检查，可使用团队限定的可延迟约束触发器；不改写个人空间已有唯一索引、成员保护触发器和创建者规则。

授权来源属于批次 1A 的独立交付物：区分 Agent 关联版本、已有明确人工授权与待对账旧授权。有效集合由仍有效的来源汇总，并始终受平台授权上限约束；添加、升级、停用和移出在同一事务维护来源与有效集合。升级需保留仍允许既有 Session 使用的旧版本来源；平台撤权、明确停用或移出时再关闭相应调用资格。来源不明的存量授权不能猜测为某个 Agent 所有，更不能因移出一个 Agent 顺带删除；对账完成前阻止涉及歧义来源的破坏性授权调整。

原批次 1B 的“来源限制采集”随 2A／2B 一并取消：不再为团队输入文件、知识或工具返回数据记录来源标识与访问限制。若将来需要追溯内容来源，必须重新立项，且无法补记已发生运行的来源事实。

### 6.4 迁移与兼容策略

- 使用新的顺序 SQL 迁移，不改写已应用迁移；准确表结构、索引和约束在实施阶段落到 SQL。
- 以完整迁移链为前置条件，核对 `0013` 已应用及其个人空间唯一索引、空间回填、非空约束有效。若目标环境仍有空空间归属或缺约束，停止本次升级并按既有迁移／数据恢复流程处理，不另建一套个人空间回填逻辑。
- 先扩展模型与 API，再切换前端；保持上一版本运行、下载和私有会话兼容。
- 新关联、回填、负责人约束及发布规则只作用于团队空间。不得给个人空间添加 Agent 关联、逻辑文件版本、发布记录或团队能力授权；个人空间业务记录不做本方案数据转换。
- 既有共享文件仍为共享文件，既有会话和成果不因为空间属性被自动公开。
- 既有团队成员角色保持；负责人以 owner 成员关系为准，创建者不同不单独认定为异常。团队缺 owner 或存在多个 owner 时报告并对账，约束通过前不执行转交，不静默覆盖归属。
- P1 仅将团队共享文件回填为逻辑文件的初始版本，历史 Run 继续指向原不可变对象；个人文件不回填，P0 不依赖此迁移。
- 新建团队空间默认没有 Agent 成员；既有有效能力授权按精确版本保留，仅在可确定 Agent 对应关系时回填关联，歧义项输出对账清单；不自动扩大授权范围。
- 在独立测试库验证全新安装、已有数据升级、重复运行、约束冲突与应用回滚兼容；迁移失败不得留下半个负责人转交或半个发布事实。
- 归档后仍需读取的接口将“活动成员可执行”与“获准成员可读”分开；不能继续用统一 `status = active` 把历史空间完全屏蔽。
- **归档语义已定（2026-09-11 产品确认）：只读保留。** 归档后现任成员仍可按权限查看会话、文件、成果与历史运行并下载；新对话、续写、重试、上传、成员与 Agent 变更、空间设置修改一律拒绝；失去成员资格者仍拒绝；归档空间仍允许必要的访问撤销与负责人治理。读/执行两条口径在实现上必须显式分开（方案 §6.5、批次 3 任务 3-T1）。

### 6.5 团队运行中收权与事件交付 · 批次 1A／1B

1. 成员移除、退出、角色降级、Agent 停用／移出等变更在提交业务状态时同步更新团队授权修订标识并写入持久化撤权事件。基础机制在 1A 完成，不等到共享功能上线。
2. Run 启动、重试及队列领取后、调用 Runtime 前，重新校验当前员工、团队成员角色、Agent 关联和平台授权；执行前复核只决定是否执行，不覆盖既有不可变 Manifest。
3. SSE 建连、断线续传与每批内容写出前校验团队授权，使用可失效的授权缓存或等价机制。收到撤权事件时关闭相关订阅、丢弃待交付内容；通知丢失时仍由当前授权检查拒绝发送。团队文件下载与结果读取采用相同授权边界。
4. 撤权处理通过平台内部的系统取消入口调用既有 Runtime Adapter，对排队、运行、终态分别幂等收敛；不能依赖已经失权的员工再次调用取消 API。撤权事件可重放，进程重启后继续处理。
5. 撤权提交后新发起的授权决策必须拒绝；取消实际执行可异步完成，但结果不得因此继续对失权用户交付。已经交付或已经开始写出的内容无法回收；验收需覆盖检查与写出、领取与执行、取消与完成之间的竞态。
7. 以上新增机制限定团队对象。个人空间继续使用现有执行、订阅与授权路径，回归测试验证两条分支互不串用。
8. **读取轨与执行轨分开判定空间状态**（批次 3）：执行轨要求团队空间处于活动状态；读取轨只要求调用者是现任成员，允许已归档空间的历史内容按权限读取与下载。读路径不得复用仅认活动状态的空间类型解析，写路径不得被读取轨的放宽影响。

### 6.6 团队可见统计与查询性能 · 批次 1B

- 团队列表、页签数量、搜索和内容列表使用同一可见条件；不先取空间全部数量再在前端隐藏不可见条目。
- 优先用服务端可授权查询、按租户／空间／作者／状态的索引和聚合后关联，避免会话、文件、版本多表展开导致重复计数。
- 在 1B 建立包含多成员、多会话、一个会话超过 50 个 Run、共享文件与成员数据的基线。记录查询计划、延迟分位数、数据量和并发，实施评审时确定目标环境预算。
- 在测量确认必要前不预设物化方案。若使用缓存或异步投影，必须能按当前身份过滤，且在收权后失效；性能优化不能返回已失权对象的名称、数量或摘要。
