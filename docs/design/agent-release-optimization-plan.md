# Agent 配置与发布简化方案

**状态：** 设计已确认（2026-10-16），按第 11 节分阶段实施；S1、S2、S3、S4 已完成。本文替代原“Agent 新建与发布流程优化方案”（AR-00～AR-08）；原方案中已交付的修复（`96e797d`）保留在代码中，其余阶段不再按原设计实施。<br>
**更新日期：** 2026-10-16<br>
**范围：** 管理端 Agent 的配置、权限、工作数据、主动任务、经验、验证、发布、回滚与停用。员工端执行入口、团队空间加入 Agent 的方式不变。

**定位：** Agent 是独立的 AI 员工，不是某位人类员工的助手。它有自己的身份、职责与人格、岗位权限、工作数据、主动任务和经验；员工向它请求工作，它也可以在批准范围内按时间或事件主动工作。本方案的简化以这个定位为前提：去掉重复的机制，不去掉 AI 员工应有的能力。

## 1. 为什么要改

管理员反馈：配置和发布流程太复杂，功能权限的配置不清晰。核对代码后，复杂度主要来自同一件事被多套机制重复表达：

| 问题 | 现状 |
| --- | --- |
| 权限分散在四处、名字相近 | 发布工作台配“可见角色”和“平台数据范围”（版本上限），管理页抽屉配“业务执行角色”和“平台数据范围”（执行身份授权）；工具另有角色与数据范围要求，缺了要到发布前检查才报错，再离开发布页去补 |
| 版本与候选两套对象 | 草稿本身是一条版本记录，发布时又另建候选（`agent_release_submissions`），带修订号、草稿指纹、封存修订号、案例、检查、计划；草稿一改候选要重新绑定或推进修订，页面读取也会触发同步 |
| 判断“测过的东西变没变”有三套机制 | 草稿指纹、候选修订/封存修订、工具绑定 pin |
| 验证结论散在五处 | 试运行记录（步骤 JSON 内嵌案例运行）、版本证据表、发布记录表、候选上的检查与计划、早期结构校验表 |
| 试运行是服务器上的分步向导 | 固定 6 个步骤，每次只跑一个案例：开始、继续、确认循环 5 次，每步是同步长请求；一轮约 22 次点击、5 次串行等待 |
| 通用案例价值低 | 5 条固定模板，除“正常任务”取第一条示例问题外，其余 4 条是与业务无关的通用句子；机器只检查“有运行记录、执行成功、回答非空” |
| 不再使用的流程和字段 | 提交审核、退回修改、撤回；ZIP 导入相关字段；Agent 委派配置 |
| 页面分散 | 三步编辑弹窗、Agent 管理页抽屉、发布工作台三处 |

规模参考：发布服务 2,025 行、Agent 服务 1,368 行；管理端发布工作台 880 行、管理页 601 行、编辑弹窗 571 行；发布与 Agent 管理接口约 26 个；发布治理相关表 7 张。

## 2. 已确定的决策（2026-10-16）

1. 不需要审核流程：配置的管理员自己验证、自己发布。删除提交审核、退回修改、撤回，以及写入型 Agent 双人审核的设想。
2. 不需要 ZIP 导入与导出。
3. 可见范围只设“哪些角色可用”，不做灰度。
4. 删除 Agent 委派（PF-06，AI 员工之间分工协作）：先删除，以后有需要时按 AI 员工定位重新设计后再加（2026-10-16 确认）。管理助手的“委派确认”是另一回事，保留。
5. 验证案例 = 员工端示例问题（至少 1 条）+ 管理员自定义的测试问题；取消 4 条通用模板案例。
6. 权限按 AI 员工设计：Agent 像员工一样持有岗位角色和数据范围（同一套角色体系），可随时调整；版本上不再另设数据范围上限。
7. Agent 是独立 AI 员工（2026-10-16 确认）。工作数据（原“Agent 数据平面”）、主动任务、经验迭代与持久化审批全部保留，并纳入 Agent 详情页统一配置。

## 3. 目标模型

```text
Agent（名称、负责人、启停状态、可见角色、当前版本指针）
  ├─ 草稿版本（唯一，可随时编辑，自动保存）
  ├─ 待发布版本（点「验证」时由草稿冻结而来，不可变）
  │     └─ 验证：每个案例一行结果（Run、机器检查、管理员判定、原因）
  ├─ 已发布版本（不可变；当前版本指针指向其中一个）
  ├─ 自定义测试问题（随 Agent 保存，跨版本复用）
  ├─ 岗位权限（岗位角色、数据范围；随时可改，立即生效）
  ├─ 工作数据（被授权的记录集合与私有状态）
  ├─ 主动任务（按时间或事件唤醒的工作规则，结果交给接收人）
  └─ 经验（运行中提出、经审核发布的经验版本）
```

- **版本状态：** `draft`（可编辑，每个 Agent 最多一条）→ `candidate`（验证时冻结的副本，不可变）→ `published`（曾被发布）。冻结后再改草稿不影响正在验证的版本，页面提示“草稿与待发布版本不同”，可“以当前草稿重新验证”。
- **发布：** 当前版本指针指向通过验证的待发布版本。**回滚：** 指针指回任一曾发布的版本。**停用/启用：** Agent 级状态，不动版本。
- **内容是否变化：** 只用待发布版本本身判断——版本不可变，验证结果绑定版本 ID 与内容摘要；不再有候选修订、草稿指纹和封存修订。工具绑定 pin 仍随版本固定（执行期复核撤权所需），但不再参与“是否需要重新验证”的判断以外的流程。
- **已有会话：** 继续固定原版本（现行行为不变）。

## 4. 权限模型

Agent 作为 AI 员工，权限与人类员工同构：持有岗位角色（决定能用哪些工具）和数据范围（决定能读写哪些数据），由管理员像给员工授权一样分配。权限在详情页“岗位权限”一节集中配置，回答三个问题：

| 问题 | 配置 | 生效方式 |
| --- | --- | --- |
| 谁可以向它请求工作 | 可见角色（Agent 级属性，不随版本） | 改了立即生效，不需要重新验证 |
| 它能做什么 | 能力（Skill、MCP 范围）+ 岗位角色 | 能力属于版本内容，改了要重新验证；岗位角色随时可改、立即生效 |
| 它能接触哪些数据 | 数据范围（对 Agent 身份的授权）+ 工作数据集合的动作授权 | 改了立即生效，不需要重新验证 |

- **岗位角色与能力对齐：** 页面列出每项能力需要的角色（工具允许多个角色时任选其一），缺少时标出“该能力因缺少角色 X 不可用”，可一键补齐；不再到发布前才报错，也不再单独打开“执行身份”抽屉。
- **取消版本上的数据范围上限**（`agent_versions.data_scopes`）：数据权限只有 Agent 身份授权这一组。放宽授权立即生效且记入审计，不触发重新验证。
- **结果交给谁、能看到多少：** 员工请求时，Agent 用自己的权限工作，交给该员工的结果不超过该员工本人可见的范围；主动任务用 Agent 自己的权限工作，结果按接收人的可见范围交付。这条执行期规则保持现状。
- **权限总览：** 详情页常驻一张卡片，例如“财务部、采购部可以请求；持有采购分析员角色；可访问华东区订单数据；可写入缺料台账；每天 8:00 向采购主管推送异常汇总”。
- 执行期的权限复核（撤权即停、工具策略、审批）保持不变。

## 5. Agent 详情页

一个页面完成全部操作，取代三步弹窗、管理页抽屉、发布工作台，以及分散在各处的主动任务面板和经验审核页（按 Agent 进入）：

| 分区 | 内容 | 是否属于版本 |
| --- | --- | --- |
| 职责与人格 | 名称、说明、欢迎语、SOUL.md、AGENTS.md（选填）、员工端示例问题 | 是（草稿自动保存） |
| 能力 | Skill、MCP 范围；运行限制（超时、工具调用上限）默认折叠 | 是 |
| 岗位权限 | 可见角色、岗位角色、数据范围、权限总览 | 否，立即生效 |
| 工作数据 | 声明需要的记录集合与私有状态；集合的动作授权（查询、提议、新增、修改、改状态） | 声明属于版本；授权立即生效 |
| 主动任务 | 规则列表（时间或事件、提示词、接收人、预算）、启停、执行记录 | 否；规则启用时固定当时的发布版本 |
| 经验 | 本 Agent 的经验申请审核、已发布经验版本 | 否 |
| 验证与发布 | 案例、验证进度与判定、发布、版本历史、回滚、停用/启用 | — |
| 运行记录 | 近期 Run 与结果 | — |

集合本身（Schema、作用域、保留期）是平台级对象，可被多个 Agent 共享，在独立的“工作数据集合”管理页维护；详情页只管本 Agent 的声明与授权。技术标识（版本 ID、Run/Attempt、绑定修订）收进“技术详情”。

## 6. 验证的执行

- **案例：** 示例问题至少 1 条；已配置的主动任务提示词自动列入；自定义测试问题可选（如业务上的越权请求）。案例在验证开始时快照进验证记录，之后修改示例问题不影响本次验证。
- **机器检查：** 固定三项——留下运行记录、执行成功、回答非空，不需要配置；不通过时管理员不能判为通过。
- **与生产一致：** 试运行与员工执行共用一个 Manifest 构造函数，只覆盖三处：执行身份上限（以可见角色的权限作为员工侧上限）、外部效果隔离、无工作空间输入。知识、经验、工具集、审批、写入策略与限额与生产一致。
- **外部效果隔离：** 平台写工具、数据平面写入返回 `trial_only`；MCP 调用在试运行中一律不执行（现行 fail-closed），发布页对使用 MCP 的 Agent 注明“MCP 能力未在试运行中执行”。MCP 只读/写入标注留待有需要时再做。
- **后台并行与容量：** 验证受理即返回，前端轮询进度。试运行设独立并发上限 2，并始终为员工交互任务保留 1 个执行位（与自动任务、对话摘要一致）。
- **重启收敛：** 服务重启时未完成的案例标为“服务重启中断”，可单独重跑。

## 7. 接口

| 接口 | 用途 |
| --- | --- |
| `GET /agents`、`GET /agents/:id` | 列表与详情（含草稿、当前版本、权限总览、最近验证） |
| `POST /agents` | 新建（生成草稿与执行身份） |
| `PATCH /agents/:id/draft` | 保存草稿（带修订号，防并发覆盖） |
| `PATCH /agents/:id/access` | 可见角色、数据范围、执行角色（立即生效，记审计） |
| `PUT /agents/:id/test-cases` | 自定义测试问题 |
| `POST /agents/:id/validations` | 前置检查 + 冻结 + 后台运行全部案例 |
| `GET /agents/:id/validations/:validationId` | 进度与结果 |
| `POST /agents/:id/validations/:validationId/cases/:caseId/rerun` | 重跑单个案例 |
| `POST /agents/:id/validations/:validationId/cases/:caseId/verdict` | 判定通过/不通过（不通过须带原因） |
| `POST /agents/:id/publish` | 发布通过验证的待发布版本 |
| `POST /agents/:id/rollback`、`PATCH /agents/:id/status` | 回滚、停用/启用 |
| `GET /agents/:id/versions` | 版本历史 |

## 9. 删除 Agent 委派

委派（PF-06）让一个 AI 员工在执行中把子任务交给另一个指定的 AI 员工。先删除，以后需要 AI 员工之间协作时重新设计。删除范围：

- 运行：委派服务、`delegate_agent` 平台工具、Manifest 的 `delegation_policy`/`delegation_context`、调度器为子任务预留执行位的逻辑、取消时级联子任务、任务结果合并子任务回执、执行能力检查中的委派项。
- 数据：委派表 `task_delegations` 与版本上的委派策略列（迁移删除，不保留兼容）。
- 界面：编辑页“权限与运行限制”中的委派设置、发布检查中的委派项。
- 测试与文档：PF-06 相关测试、PF-07 能力矩阵中的委派项、功能规则与架构总览中的委派描述。

## 12. 风险与取舍

- 改动面大，基本是重写发布模块和管理端 Agent 页面；发布治理的旧集成测试需要按新模型重写。
- 详情页分区较多（职责、能力、权限、工作数据、主动任务、经验、验证发布、运行记录），需要在页面设计中控制信息密度：未启用的能力默认收起，不让简单 Agent 的配置变复杂。
- 放宽数据授权或可见角色不触发重新验证，依靠审计和“员工权限为上限”控制风险。
- 案例减少到示例问题与自定义问题，验证质量更依赖管理员认真写示例问题；平台层的越权与注入防护由权限交集和工具策略保证，不再通过每次发布跑通用句子。
- MCP 能力在试运行中不执行，依赖 MCP 的 Agent 的验证只能覆盖非 MCP 部分；页面会明确提示。
