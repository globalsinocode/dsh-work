## 1. 背景与目标

平台已有三种“提醒”，各管一块，员工没有一个地方能看到“与我有关、需要我知道的事”：

| 现有能力 | 范围 | 局限 |
| --- | --- | --- |
| 项目空间动态与通知未读（`workspace_activity_events`、`workspace_notification_states`） | 单个项目空间内的协作事件，按空间计未读、可静音 | 要进入空间才看得到；不区分“与我有关”与“空间里发生了什么” |
| 协作模式对话未读（`conversation_read_states`） | B 模式对话列表的未读数 | 只覆盖消息；A 模式没有 |
| @ 成员提醒（`message_mentions`） | 群聊与共享讨论中 @ 我 | 只在 B 模式对话列表显示“[有人@我]”与导航圆点 |

而以下结果目前完全没有提醒，员工不回到原页面就不知道：

- 我提交的 Skill 审核通过或未通过（[Skill 创建专家方案 4.7](skill-creator-plan.md)：“审核结论只体现在草稿卡片上”）；
- 我设置的项目 Agent 任务定时执行被暂停或停止（功能规则 3.12：“暂停与停止不发站内提醒”）；
- 我的定时任务执行失败或被跳过（功能规则第 7 节：结果只进入该次 Session）；
- 项目任务指派或改派给我、我创建的任务被完成。

**目标：** 两种模式都有一个统一的“通知”入口，集中列出与本人相关的事件，点一条直达对应页面；未读有醒目但克制的提示。钉钉工作通知（钉钉方案 DT-S2）以后从同一份通知记录投递，不再各自从业务表取数。

## 2. 边界

- **不新增执行链路。** 通知只记录已发生的业务事实，不触发 Run，不调用模型；Agent 的执行仍经 Run/Attempt → Runtime Adapter → DSH。
- **不替代项目空间动态。** 动态仍在空间内展示全部协作事件；通知只收“与我本人相关”的事件（第 4 节），两者是不同投影。
- **不新增推送通道。** 沿用协作模式未读的刷新方式（2.2b）：每分钟、页面重新可见、回到对话页时刷新；不做 WebSocket/SSE。
- **只披露名称级信息。** 通知文案只含“谁、在哪个项目/对象、做了什么”，不含消息正文、Agent 回复、文件内容或成果摘要；名称在读取时按接收人当前权限解析。
- **不做管理端通知。** 管理端“待审核”页签已承担管理员待办；管理员审核类提醒另行评估。
- **不改主导航。** A 模式五个入口、B 模式四个入口保持不变（AGENTS.md 壳层导航约束），通知入口放在壳层的固定位置（第 5 节）。

| NC5 | 静音 | 沿用按空间静音：静音空间的任务类通知照常列在“全部”中，但不计未读、不进“未读”页签；@ 我不受静音影响（现有规则）。第一期不做按类型的个人开关，随钉钉“通知设置”一起做 |

## 4. 首批事件

| 类型 | 接收人 | 文案示例 | 点击去向 | 事件来源 |
| --- | --- | --- | --- | --- |
| `mention` @ 我 | 被 @ 的现任成员 | 张三在「Q4 投放复盘」中 @ 了你 | 该群组/共享讨论，定位到消息 | `message_mentions`（已有，同事务补写通知） |
| `task_assigned` 任务指派给我 | 新负责人（员工） | 李四把任务「整理竞品报价」指派给你 | 项目任务详情 | 项目任务创建或 `project_task_events.reassigned` |
| `task_completed` 我创建的任务完成 | 任务创建人（不是完成者本人时） | 王五完成了你创建的任务「汇总周会纪要」 | 项目任务详情 | `project_task_events.completed` |
| `task_schedule_stopped` 定时执行暂停或停止 | 规则设置人 `schedule_set_by` | 任务「每日舆情汇总」连续 3 次执行失败，定时执行已暂停 | 项目任务详情 | 定时执行状态变化（原因：连续失败、设置人失权、Agent 不可用、空间归档、过截止日期、任务完成） |
| `automation_failed` 定时任务未成功 | 定时任务所有者 | 定时任务「周一销售周报」本次执行失败 | 该次执行的对话；无对话时到定时任务页 | 定时任务执行记录（失败、跳过、遗漏区间） |
| `skill_review_result` Skill 审核结论 | 提交人 | 你提交的 Skill「销售周报整理」已发布到 Skill 广场 / 未通过审核 | 提交草稿所在的对话 | `skill_submissions` 状态变为 approved / rejected |
| `workspace_member_added` 被加入项目 | 被加入的员工 | 张三把你加入了项目「Q4 投放复盘」 | 项目空间（A）/ 群组（B） | `workspace_activity_events.member_added` |

**NC-S3 实施说明（2026-10-31）：**
- 定时执行：自动暂停（连续失败、设置人失权）与停止（Agent 不可用、项目归档、过截止日期）通知设置人；因任务完成而停止不另发（创建人已有“任务完成”通知）。系统动作没有触发人。
- 定时任务：只为所有者无从知晓的情况通知——执行失败（含服务重启后丢失的执行）、被跳过（重叠、主体或授权无效、待处理数超限）、停机错过、受理后未能开始；所有者自己暂停、停用、改计划而作废的时间点与“立即运行”当场被拒不通知。去重键按“执行 + 结果”；同一定时任务同一结果已有未读通知时不新增，只把那一条更新为最新一次（长时间重叠或权限失效不刷屏），读过之后再发生才另起一条。受理中断的通知与 Run 落为失败在同一事务中写入。
- Skill 审核：通过与拒绝都通知提交人，只带结论代码，拒绝原因留在草稿卡片上；文案只写“未通过审核”，不写“原因见草稿卡片”（之后修改再提交通过后，卡片已显示新结论）；管理员审核自己的提交不通知。
- 接口新增 `detail`，只返回 `state`、`reason`、`outcome`、`result` 四个代码键。通知写入函数放在独立的 `modules/notification`，供工作台、定时任务、Run 与 Skill 模块共用，不引入模块循环。

**暂不纳入：** 长时间 Run 完成提醒（需要判断发起人是否在页面上；钉钉方案 DT16 已定不推送钉钉，群组中 Agent 的回复由钉钉群组提醒覆盖）；被移出项目（移出后不再可见该项目，文案只能写“你已不是某项目成员”，价值低，现有页面已有提示）；管理员审核待办。

## 5. 交互

- **入口：** 导航栏左下角、头像上方的铃铛按钮（A、B 两种模式位置一致），可访问名称“通知”或“通知，3 条未读”。未读数为 0 时不显示角标。
- **面板：** 点铃铛打开紧贴导航栏的面板（宽屏 400px 并遮罩其余区域，点遮罩关闭；窄屏全屏），标题“通知”，右上角“全部标为已读”。顶部两个页签：“全部”“未读”。
- **条目：** 左侧类型图标，正文一句话（人名与对象名加粗），下方相对时间与所属项目；未读条目左侧有圆点、背景略深。点击条目标为已读并跳转；目标已不可见时就地提示“该内容已不可见”，不跳转。
- **空与错误：** 无通知时显示“暂时没有通知”；加载失败显示重试按钮，不影响页面其他部分。
- **分页：** 按时间倒序，滚动到底加载更早的通知；90 天前的不再显示。

## 6. 数据与接口

新增表 `user_notifications`（迁移号实施时确定）：

| 字段 | 说明 |
| --- | --- |
| `tenant_id`、`id` | 主键 |
| `recipient_user_id` | 接收人 |
| `kind` | 第 4 节七类之一（check 约束） |
| `workspace_id` | 所属项目空间，可空（定时任务、Skill 审核无空间） |
| `object_type`、`object_id` | 跳转目标的安全引用（只存 ID） |
| `actor_user_id` | 触发人，可空（系统暂停等） |
| `safe_metadata` | 最少的附加信息：暂停原因代码、失败状态、审核结论；不含名称和正文 |
| `dedupe_key` | 业务发生的唯一标识，`unique (tenant_id, recipient_user_id, dedupe_key)` |
| `created_at`、`read_at` | 产生时间、本人已读时间 |

- **写入：** 与产生它的业务变更在同一事务中写入（沿用 `workspace_activity_events` 的做法），重复写入因唯一键成为空操作。写入只依据服务端事实，不取客户端提交的名称。
- **读取：** `GET /api/workbench/v1/me/notifications?status=all|unread&cursor=&limit=` 返回本人通知，每条读取时重新解析对象名称并检查可见权限，失权的条目不返回名称与跳转目标（`visible=false`，显示“该内容已不可见”），也不计未读、不出现在“未读”筛选中；`GET /me/notifications/unread-count`；`POST /me/notifications/:id/read`；`POST /me/notifications/read-all`。
- **保留：** 服务启动后与每天清扫一次，按产生时间分批删除 90 天前的记录（迁移 0112 按时间建索引），与已读未读无关、可重复执行；只删通知，不动 @ 提醒等业务数据。
- **与现有表的关系：** `message_mentions` 保留（群组“[有人@我]”标记仍用它），@ 通知是同事务另写的一行；`workspace_notification_states` 的静音状态在计未读时读取。钉钉投递记录 `external_notification_deliveries` 的来源为 `user_notifications.id`（钉钉方案 4.1 已于 2026-10-31 同步）。

### 6.1 移动端与外部推送：复用同一份通知

`user_notifications` 是“该告诉谁什么”的唯一事实来源，移动端和以后任何推送渠道都不另建事件判断：

- **移动端站内列表：** 移动端 H5 是 Workbench API 的独立消费方（[移动端接入规范](../development/mobile-integration-guide.md)），直接调用第 6 节的 `/notifications` 接口，把这些端点收进 `openapi-mobile-h5.json` 即可，不新增服务端逻辑。
- **推送到手机（应用未打开时）：** 推送只是“投递渠道”，每个渠道一张投递记录，以 `user_notifications.id` 为来源、`(tenant_id, channel, recipient_user_id, source_type, source_id)` 去重（`source_type = notification`；钉钉群组提醒以提醒轮次为来源，见钉钉方案 4.1.1）；单进程投递器领取后做发送前复核（账号有效、仍有可见权限、未静音、渠道绑定有效），失败重试与死信不影响业务和站内通知。钉钉工作通知（钉钉方案 DT-S2）是第一个渠道；投递记录不对通知设外键、自有保留期，清扫跳过仍有待投递记录的通知（钉钉方案 4.1）；以后若有原生 App 推送或浏览器 Web Push，按同一结构增加渠道。
- **为此本方案预留：** 通知类型 `kind` 与 `safe_metadata` 足以生成名称级推送文案；跳转目标用稳定路由表达（与 A/B 模式无关），移动端与钉钉内打开都能定位；第一期不做的按类型开关，随第一个推送渠道一起做成“按渠道 × 类型”的个人设置。
- **渠道的约束：** H5 页面自身收不到系统推送，需要钉钉等宿主或原生外壳；内网部署时 APNs/FCM 需要出网，Web Push 需要 HTTPS 且 iOS 只支持添加到主屏幕的网页。选哪种渠道在做移动端时按部署条件定，不影响本方案的数据结构。

## 7. 安全与权限

- 跨空间输入与执行前复核等约束不变；通知不是授权依据，点击后仍按目标页面自己的权限判断。
- 接收与读取两次检查：写入时接收人必须对对象有可见权限；读取时再查，失权后不能经旧通知看到名称。
- `safe_metadata` 只放代码值；审核拒绝原因不进入通知，员工点开草稿卡片看。

## 9. 验收

- **P0：** 冒烟服务提供测试身份和内存通知，验证铃铛、面板、页签、已读、跳转与空状态在 A、B 两种模式和窄屏下可用。
- **P1：** 一次性 PostgreSQL 与合成 Runtime：七类事件各自产生且只产生一条通知；重放不重复；失权后读取不返回名称；静音空间不计未读、@ 不受影响；打开群组后 @ 通知已读。验收目录新建分册 `e2e/catalog/notifications.md` 记录旅程。
- **P2：** 真实 DSH 下定时任务失败与项目任务定时暂停各走一次，确认通知产生与跳转；按发布流程留证。P0/P1 绿灯不能代替 P2。
