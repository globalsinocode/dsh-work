## 1. 背景与目标

企业里有一类反复出现的工作：按固定周期从业务系统取数，按确定的规则算出需要处理的事项，分给具体的人，并跟踪处理结果。欠料风险预警是第一个例子，来料检验异常、价格协议到期、应收逾期属于同一类。

现在的平台做这类工作有三个缺口：外部数据只能由模型调用 MCP 取得；每次触发都会创建 Run 并唤醒模型；结果停留在该次 Task 中，主动任务只有一个接收人。若为每个场景单独建业务应用，又无法复制，也用不上 Agent 的配置组合能力。

目标：

- **新场景只靠场景包和配置上线：** 写一个场景包（场景声明、计算脚本、给 AI 同事的任务说明），必要时在共享数据服务中增加查询，再配置一条主动任务。不新建服务，不新做页面。
- **程序做确定的事，模型做判断：** 取数、计算、条件判断与交付由平台程序执行；说明与方案排序由 AI 同事经 DSH 执行。
- **结果变成有人负责的跟进项：** 按人分发，与上一次结果对账，标出新增、变差与持续，接收反馈，处理完或不再出现时关闭。
- **欠料风险预警作为首个场景走通，**分期见第 10 节。

## 2. 已确认事项（2026-11-10）

| 事项 | 内容 |
| --- | --- |
| 方向 | 不按场景建业务应用。一个场景 = 场景包（当时定为 Skill，SP14 改为独立对象）+ 共享数据服务中的查询 + 一条主动任务（部署）；固定步骤由程序编排（规范 1.1，PR #113） |
| 名称 | 按人交付、可反馈的对象叫“跟进项”，不与项目任务的“待办”状态混用 |
| 欠料一期范围 | 预警采购员；替代方案四类（分批催交、换或加供应商、替代料、调拨），挪用其他订单的库存放二期；采购员反馈必须做（误报、已跟进录入新交期、采用方案）；只用站内通知；与供应商协同（SRM 交期确认请求）、联动排产放二期 |
| 欠料数据口径 | 按订单交货日期倒推排产；ERP `SUGGESTION_PLAN` 表已有最终计算结果，每天刷新一次、不保留历史；ERP 中每个物料有对应采购员；ERP 有货源清单、BOM 替代关系与多仓可用库存；ERP 与 SRM 都提供 API；计算参数需要维护 |

## 3. 已确认决策（2026-11-10）

以下决策均按“确认的做法”一列拍板，可选做法保留作记录。SP2、SP3、SP4、SP7 在同日评审后调整；SP10～SP13 是同日简化评审后新增的决策，它们改掉的原做法写在该行，SP3、SP4、SP9 随之收窄。SP14～SP16 是同日从平台整体规划讨论后新增的决策，SP6 随之调整。

| 编号 | 决策 | 可选做法 | 确认的做法 |
| --- | --- | --- | --- |
| SP1 | 员工端跟进项的入口 | (a) A、B 两种模式主导航各加“跟进项”，只在本人有跟进项或在某条规则的接收范围内时显示；(b) 不加导航，从头像菜单与通知进入；(c) A 模式“新对话”首页上方显示今日跟进项摘要，点开进入列表 | (a)。跟进项是每天要看的工作清单，放进头像菜单太深；只对相关的人显示（规则负责人也显示，6.10），不影响其他员工。主导航“固定入口”的规则要同步修改：`AGENTS.md` 浏览器 E2E 一节、功能规则第 2 节与项目空间方案第 12 节 |
| SP2 | 采购员录入的交期在预计到货日来源中的位置 | (a) 等同“供应商确认”：排在 SRM 预计到货之后、PO 承诺之前，之后 SRM 出现新的预计到货时以 SRM 为准；(b) 优先于全部来源，直到采购员撤销 | (a)。SRM 发货数据比口头答复更可靠；采购员录入只填补 SRM 还没有数据的空档。**评审后补充：** 原方案中录入的交期没有进入计算的通道；现由平台按去重键保存声明的反馈值，作为计算的只读输入（6.6），不随跟进项关闭而失效，由下一次运行使用（SP10）；录入的交期与 SRM 中的供应商确认交期取确认时间较晚的一个 |
| SP3 | ERP 采购员代码与员工账号的对应 | (a) 复用 `external_account_bindings` 增加 ERP 渠道，管理员在组织架构中维护（支持 CSV 导入）；(b) 新建专用对应表 | (a)。**简化评审后收窄：** 第一期只做一个 `erp` 渠道，沿用“每人每渠道一个有效绑定”的约束。评审时补充的“渠道按 ERP 实例区分”和“一人多个代码”是为多套 ERP 准备的，目前没有这样的客户，第一期不做；采购员是否一人多个代码在欠料-0 向客户确认，确有时再放开约束。ERP 绑定在账号停用（与 `invalidateUserBindings` 同一事务）和钉钉离职检查确认离职（与 `invalidateDeparted` 同一事务）时失效，没有钉钉绑定的员工只能等账号停用；重置密码、钉钉解绑不影响它（`invalidateUserBindings` 现在只处理钉钉，且在重置密码与解绑时也会调用，不能直接扩大它的范围）。现有读取绑定的代码都按 `channel` 过滤或按绑定 ID 读取，实施时放宽 `channel` 的 check 约束。数据服务可另提供“采购员代码—工号”查询用于核对，但不自动绑定 |
| SP4 | “问 AI”时的数据可见范围（MCP 不带员工身份） | (a) 第一期接受：数据服务不按人过滤，设计记录写明过滤层为“无”及理由；(b) 先由平台为每次执行向 MCP 传递员工身份（参照模型网关的 Attempt 令牌，另立项）；(c) 第一期不提供“问 AI” | 欠料场景选 (a)：采购数据在采购部内部本就互相可见。涉及敏感数据的场景按 (b) 或 (c)。**简化评审后调整**（原做法是员工以该 Agent 发起任何 Run 时按接收范围并集复核，校验项目空间全体成员，并在规则停用后保留边界）：数据边界就是该 Agent 的可见角色。任何选用了 Connector 的 Agent，能与它对话的人都能经 MCP 查到数据，这不是场景包带来的新问题，不为它另建运行时机制。改为配置时校验：保存工作规则或修改该 Agent 的可见角色时，持有可见角色的员工须都在“引用该 Agent 的全部未停用 SP4 (a) 规则的接收范围并集”内（规则负责人计入），否则拒绝保存并列出超出的员工；第一期不允许把这类 Agent 加入规则 Workspace 以外的项目空间（含 B 模式群组），已加入时拒绝保存规则。此后的人员调动不触发复核，可见角色由管理员维护，与其他选用 Connector 的 Agent 一致；规则全部停用后限制随之解除。设计记录写明过滤层为“无”，数据边界是 Agent 的可见角色 |
| SP5 | 保留期 | 跟进项关闭后保留时长；取数结果与计算输出的保留时长 | 跟进项关闭后保留 180 天；取数结果与计算输出只存交付与审计所需字段，保留 30 天，触发记录中的阶段、原因与摘要照常保留；通知沿用 NC4 的 90 天。规则停用后的处理见 6.9 |
| SP6 | 谁能发布场景包 | (a) 只有管理员在管理端上传并发布；(b) 员工起草、管理员审核后发布 | (a)。场景包含会被平台执行的声明与脚本，第一期不开放员工起草。**SP14 后调整：** 场景包不再是 Skill，员工端没有任何入口，不需要让 `skill_draft_save` 识别并拒绝它；发布权限第一期沿用 Skill 发布权限，不新增权限点 |
| SP7 | 计算段的并发 | (a) 与成果解析共用执行器槽位，排队超时记为“计算失败”；(b) 为计算段单独建执行器实例与槽位 | (b)，**评审后调整**（原选 (a)，并误写成“共用 4 个槽位”）。成果解析用的是单独的 `ContainerExecutor` 实例，只有 2 个槽位（`main.ts`），而且它的 60 秒超时包含等槽位的时间；计算一次最长要占几分钟，共用会让员工上传文件后的成果解析超时失败。新建一个实例的代码成本低。计算段实例默认 2 个槽位；等槽位超过 10 分钟记为“计算失败”（原因“排队超时”），与运行超时分开记录。触发处在取数、计算阶段时计入主动任务的重叠检查与待处理名额（6.4），不占用 Worker 与后台车道 |
| SP8 | 跟进项通知的合并方式 | (a) 每人每次运行合并为一条（标题写紧急条数，正文写新增与变差条数），只在有新增或变差时发送；(b) 新增紧急项另发一条 | (a)。按 NC1 只收与本人相关的事件，按 NC6 不为“无变化”发通知 |
| SP9 | AI 同事输出不合格时 | (a) 跟进项照常交付，不带说明与排序，运行记录标注原因；(b) 整次交付失败 | (a)。事实与候选方案来自程序，AI 说明缺失不影响跟进项的正确性。**简化评审后由 SP12 扩大：** 交付改在 Agent 段之前，Run 未能创建、失败或超时也不影响跟进项送达，只影响是否带说明与排序（6.8）。原做法是 Run 未能创建或失败时整次不交付 |
| SP10 | 接收人反馈后何时重算 | (a) 反馈后立即发起只针对这一条的触发，重新取数并对账；(b) 保存反馈值，由下一次运行重算 | (b)（原为 (a)）。`SUGGESTION_PLAN` 每天只刷新一次，立即重新取数拿到的还是同一批数据，变化的只有刚录入的值；而单条触发要新增触发类型、独立的受理路径、互斥与节流、计算槽位预留、按键的取数时间守卫和按物料过滤的查询参数。反馈后跟进项进入“处理中”并标“已录入，下次运行重算”。确有即时重算的需要时再评审 |
| SP11 | 放权阶段能否退回 | (a) 可以从通知相关人退回影子运行（含更换 Agent Version 后自动退回），已分发的项冻结，再次放权时接续；(b) 只能前进 | (b)（原为 (a)）。退回只有“更换 Agent Version”一个来源，却要引入交付代次、冻结只读、超时关闭、接续与反馈值按代次回落。改为：更换场景包版本时（SP14 后由规则直接固定），管理员查看新版本的发布证据并确认后继续通知；口径有实质变化时停用旧规则、新建规则从影子运行开始（6.3、6.9） |
| SP12 | 交付与 Agent 段的先后 | (a) Agent 段结束后交付，Run 未成功则不交付；(b) 计算后立即交付事实与候选，Agent 段随后补充说明与排序 | (b)（原为 (a)）。事实与候选全部来自程序，模型服务故障不应让采购员收不到当天的紧急欠料；原做法在“Run 成功但输出不合格”时照常交付、“Run 失败”时不交付，两者对采购员没有区别。固定形态相应改为“取数 → 计算 → 条件判断 → 交付 → Agent 执行”，规范 1.1 与 AS-03 在同一 PR 修改 |
| SP13 | 对账的比较规则与反馈值过期 | (a) 场景声明逐字段声明“变差”“重新打开”的比较方式和反馈值的失效条件，由平台求值；(b) 计算脚本输出严重度分值并自行忽略过期的反馈值，平台只比较分值大小 | (b)（原为 (a)）。这些判断本来就是场景口径的一部分，放在脚本里与其他计算一起版本化、一起用样例验证；平台不必为每种比较方式增加声明能力 |
| SP14 | 场景包的载体与版本 | (a) 场景包是附带声明与脚本的 Skill，版本随 Agent Version；(b) 场景包是独立对象，有自己的版本，由工作规则直接固定 | (b)（原为 (a)）。口径校准期间脚本会频繁修改，而 Agent Version 固定了 Skill 版本（`agent_version_skills`），按 (a) 每改一次脚本都要发布新的 Agent Version，并重做与脚本无关的 Agent 发布验证。(a) 还要给 Skill 开五条例外（不进广场、不装配 `python_execute`、拒绝员工起草、另一套发布证据、加载时声明不生效），都落在安全敏感的路径上；拆开后“平台执行的代码”与“给模型看的方法”在存储上就是两类对象，功能规则第 5、6 节不用修改。代价是新增场景包的存储、版本与管理页面（6.2、6.3） |
| SP15 | Agent 段的方法放在哪里；规则是否必须有 AI 同事 | (a) 方法放在 AI 同事选用的普通 Skill 中；(b) 场景包自带任务说明，执行时作为该次 Run 的任务输入 | (b)。交给模型的字段、输出约定与写法要一起变，放在同一个场景包版本里（规范 1.1 原则 8）；AI 同事不必为每个场景选用专用 Skill。任务说明只是任务输入，不能增加工具或权限。Agent 段是可选的（场景包不声明 `agent` 一节即不执行），但规则始终属于一个 AI 同事：执行身份、Connector 与“问 AI”都来自它，不出现无主的系统管道（6.3、6.8） |
| SP16 | 跟进项与取数、计算管道的关系 | (a) 交付逻辑写在管道内；(b) 两者之间定一个内部快照接口 | (b)。跟进项可以先做、单独测试；计算下推到数据服务的场景只少一段，接口不变（6.9）。第一期只做平台内部接口，不对外开放 |

## 4. 边界

- 不建设通用工作流引擎：固定“取数 → 计算 → 条件判断 → 交付 → Agent 执行”五段，每段只执行一次，没有任意分支、循环或多 Agent 编排（规范 1.1）。Agent 段只在条件满足时执行，只为已交付的跟进项补充说明与排序；条件不满足时不创建 Run、不调用模型（6.7）。
- 不写外部业务系统：程序步骤只调用标记为“可供程序步骤调用”的只读工具；对外部系统的写操作只在 DSH 中经授权执行，且真实 Agent 审批固定为 `never`，第一期不开放。
- 第一期只在管理员配置的 Agent 主动任务中提供；员工本人的定时任务不支持场景包。
- 不新增钉钉推送；钉钉工作通知随[钉钉接入方案](dingtalk-integration-plan.md) DT-S2 另行规划。
- 欠料二期事项（供应商协同、联动排产、挪用其他订单库存）不在本文范围。

## 6. 方案

### 6.1 总体结构

```
场景包（独立对象，管理员发布）         共享数据服务（只读 MCP Server，按业务系统建设）
  scene.yaml 场景声明                     erp：建议计划、采购单、货源清单与库存……
  compute/   计算脚本                     srm：确认交期、发货与到货、供应商表现……
  agent/     给 AI 同事的任务说明（可选）
         │ 版本由规则直接固定                        │ 由 Connector 登记，工具逐个标记
         ▼                                          ▼
主动任务（部署）：场景包版本 · AI 同事（固定 Agent Version）· 逻辑名绑定 · 参数 · 接收范围 · 放权阶段 · 日程
         │ 触发
         ▼
受理（授权复核并冻结）→ 取数（MCP 客户端）→ 计算（一次性容器）→ 条件 → 交付（提交快照）
                                                                        │
                              跟进项（对账、按人分发、通知、反馈、问 AI）◄─┤
                                                                        │ 条件满足
                                                                        ▼
                                        Run/Attempt → DSH → 为已交付的跟进项补充说明与排序
```

### 6.2 场景包格式

场景包是独立于 Skill 的平台对象（SP14），有自己的不可变版本，由工作规则直接固定。包内有三部分：

```
scene.yaml        场景声明，平台读取
compute/          计算脚本与样例输入（可省略，见下）
  risk.py
  samples/        样例输入与期望的输出字段
agent/            可选；Agent 段的任务说明
  instructions.md
```

`scene.yaml` 的内容（字段名在 SP-B 定稿）：

| 部分 | 内容 |
| --- | --- |
| `data` | 用到的数据工具逻辑名与查询参数，如 `erp.suggestion_plan_open`；参数只能引用 `params` 与触发信息，不能引用其他查询或计算的结果；每个查询的数据刷新时间字段与新鲜度要求（6.5）。不写 Connector ID、地址或凭据 |
| `compute` | 入口（`compute/` 下登记的单个 `.py` 文件）、需要读取的反馈值、输出字段定义、样例输入位置。可省略，见表后“可省略的段” |
| `condition` | 从平台固定的判断方式中选择，只引用输出字段，如“风险行数大于 0” |
| `agent` | 可选。交给 AI 同事的字段子集、每次最多条数与排序依据、任务说明文件（`agent/instructions.md`，SP15）、输出文件的约定（6.8）；不声明这一节的场景不执行 Agent 段 |
| `follow_up` | 跟进项模板：标题、事实字段及类型（文本、数量、日期、日期对比、表格、候选方案）、分组字段；去重键；接收人字段；严重度分值字段（数值，由计算脚本给出，平台只比较大小，用于判定变差与误报后重新打开，6.9）；跟踪字段（少量关键事实，变化时在历史中记录前后值）；敏感字段（管理端与审计不显示其值） |
| `actions` | 反馈动作：类型（填写字段、选择候选、带原因关闭）、字段、结果状态、字段是否作为计算输入；作为计算输入的字段可以改写与撤销 |
| `params` | 可调参数的名称、类型、默认值与允许范围 |

**可省略的段：** 规范 1.1 允许取数、计算与条件判断各段省略，本方案按以下规则落地：

- **省略计算（计算下推到数据服务，SP16）：** `data` 只能声明一个查询，并在该查询上声明输出字段定义；平台把查询结果按字段定义校验后直接作为计算输出，交给条件与交付。发布证据改为用声明附带的样例取数结果做字段校验。没有计算脚本就无法读取反馈值，`actions` 中不能有“作为计算输入”的字段。
- **省略取数：** 计算只使用参数、触发信息与反馈值。
- **省略条件：** 视为条件恒满足，计算输出通过校验即交付；声明了 `agent` 一节时每次都执行 Agent 段。
- 取数与计算不能同时省略。省略的段不进入对应的 `stage`，也不产生对应的失败结果（6.4）。

**计算脚本的目录约定：** 沿用一次性容器的固定挂载，与 `python_execute` 经环境变量给出路径的约定不同。`/skill` 是场景包目录（只读、工作目录；挂载点名称沿用执行器的固定约定，与 Skill 无关）；`/input` 下有 `fetch/<逻辑名>.json`（取数结果）、`params.json`（参数取值）、`trigger.json`（触发时间、规则时区）与 `feedback.json`（声明需要的反馈值）；结果写入 `/output/result.json`。样例运行使用同一布局。

**单文件入口：** 第一期计算入口必须是单个文件，不能导入 `compute/` 下的其他模块。执行镜像为 Python 3.12，`python -I` 同时去掉脚本所在目录与当前目录（`-m` 方式也一样），并忽略 `PYTHONPATH`，同目录的辅助模块无法导入。需要拆分模块时，另行评审由平台提供固定的启动器设置导入路径。

校验分两处：上传与发布时检查声明结构、段的省略符合上文规则、声明了计算时入口在 `compute/` 中、依赖在执行镜像中（沿用依赖登记）、`data` 参数只引用 `params` 与触发信息、样例运行输出符合字段定义；保存主动任务时检查逻辑名绑定与工具标记（6.3）。

场景包只能由管理员在管理端上传并发布（SP6），员工端没有任何入口。它不是 Skill：不进入 Skill 广场，不被 Agent Version 选用，模型加载不到它，计算脚本也不是模型可调用的入口；Skill 的现有规则（功能规则第 5、6 节）不变。上传时复用 Skill 包的解包与安全检查和依赖登记；内容保存在数据目录的内容寻址文件夹，数据库保存引用与校验索引，与 Skill 的做法一致，须与数据库成组备份。

发布证据是平台用样例输入运行计算脚本的结果（退出码、输出字段校验、镜像摘要）；任务说明在发布时做密钥预检。已发布的版本不可修改，修改即发布新版本。场景包可以停用；停用或被标为“依赖缺失”后，引用它的触发不予受理（6.4）。

### 6.3 部署：扩展主动任务

不新增部署对象，在 `agent_routines` 上增加场景包部署。主动任务因此有两种，共用一张表：只有输入模板的是模型编排（现状），引用了场景包的是程序编排。

| 字段 | 内容 |
| --- | --- |
| 场景包 | 场景包的一个已发布版本，由规则直接固定（SP14）；更换版本的处理见表后 |
| AI 同事 | 沿用主动任务固定的 Agent Version：提供执行身份、授权上限与可绑定的 Connector；场景包声明了 `agent` 一节时由它执行 Agent 段，员工“问 AI”时也是它。规则不能没有 AI 同事（SP15） |
| 数据工具绑定 | 每个逻辑名对应该 Agent Version 已选定 Connector 中的一个工具；工具须带“可供程序步骤调用”标记 |
| 参数取值 | 在声明的允许范围内设置，未设置的用默认值 |
| 接收范围 | 部门或员工列表；接收人字段映射出的员工必须落在范围内；按 SP4 (a) 运行时，保存规则时据此校验该 Agent 的可见角色（SP4） |
| 放权阶段 | 影子运行、通知相关人（第一期只开放这两级，只能从影子运行进入通知相关人，不能退回，SP11）；影子运行时全部跟进项只交给规则负责人。切换是单独的操作，不属于修改部署字段：启用状态下即可进行（锁住规则行，处理见 6.9），记审计，不清空确认的配置修订（不改变执行身份、授权与接收范围） |
| Agent 段预算 | 每次 Agent 段 Run 的时长、工具次数与输出大小，沿用输入模板中的预算（`input_template.budget`）；场景包没有 `agent` 一节时不使用 |
| 规则负责人 | 沿用 `recipient_user_id`：影子运行的接收人、告警通知的接收人（6.12），在员工端的负责人视图查看该规则（6.10） |

日程、时区与 Workspace 沿用主动任务现有字段；引用场景包的规则不使用输入模板中的提示词，Agent 段的任务说明来自场景包（6.8）。输入模板在现有代码中还承载两件事，改为：

- **预算：** 保留在 `input_template.budget`（见上表“Agent 段预算”），提示词留空；`input_template` 列仍然非空，SP-B 只对引用场景包的规则放宽 `normalizeInput` 对提示词非空的要求。
- **受理时的提示词预检：** 现有主动任务在受理时对提示词做数据防护预检，拦截时记 `skipped`（`data_policy_blocked`）。引用场景包的规则没有提示词，不做这项预检：任务说明在场景包发布时已做密钥预检（6.2），交给 Agent 的字段按工具结果遮盖、不拦截（6.8 与数据防护方案）。

规则时区同时用于数据新鲜度检查与计算中的“今天”。引用场景包的主动任务必须固定 Agent Version，不使用升级策略；引用场景包的规则不允许触发重叠，与现有主动任务一致（现有代码对重叠一律拒绝，记 `skipped`（`overlap`），没有可配置的重叠策略），只是重叠检查扩展到 Run 之前的阶段（6.4）。

场景包版本与 Agent Version 分别固定、互不带动：更换场景包版本不需要发布新的 Agent Version；更换 Agent Version 时重新校验数据工具绑定。更换场景包版本时，已在通知相关人阶段的规则不自动退回：重新启用前，管理员须查看新版本的发布证据（样例运行）并确认继续通知，确认记审计；口径有实质变化、需要重新校准时，停用旧规则、新建规则从影子运行开始（SP11）。

除放权阶段的切换外，修改部署字段与修改日程一样，只能在草稿或暂停状态进行，并清空确认的配置修订。停用是终态，停用时按 6.9 关闭全部未关闭跟进项。员工本人的定时任务不提供这些字段。

### 6.4 触发与受理

`agent_routine_executions` 增加阶段与结果，受理规则修订如下（实施前写入功能规则第 7、8 节）：

```
受理（去重、规则状态、重叠与名额、场景包状态、授权复核并冻结）
  → 取数 → 计算 → 条件 → 交付（对账、跟进项、通知，一个事务）
       ├─ 条件不满足：no_work（本次结果中不再出现的项已在交付中关闭）
       ├─ 条件满足、场景包没有 agent 一节：delivered
       └─ 条件满足、声明了 agent 一节：原子创建 Task/Run → Agent → 写入说明与排序 → delivered
失败：fetch_failed / compute_failed / delivery_failed（不交付，记原因，告警规则负责人）
Agent 段没有产出合格的说明：delivered_no_notes（事实已交付，记原因；Run 未创建或失败时告警）
规则不再启用：交付前收敛为 skipped（routine_inactive），交付后记 delivered_no_notes，都不告警
进程中断：取数、计算、条件、交付阶段收敛为 interrupted；Agent 阶段由调度周期按 Run 终态收敛
```

**触发类型：** 沿用现有的 `scheduled`、`manual`、`event`、`missed`，不新增。接收人的反馈不发起触发，录入的值由下一次运行使用（SP10）。

**状态的存储：**

- `admission_status` 保持 `accepted`、`skipped`、`interrupted` 三个取值不变，原因沿用 `reason_code`。
- 新增 `stage`，记录当前或最后所处的阶段：`fetch`、`compute`、`condition`、`delivery`、`agent`；未引用场景包的主动任务为空。
- 新增 `outcome`：进行中为空；结束时取 `no_work`、`fetch_failed`、`compute_failed`、`delivery_failed`、`delivered`、`delivered_no_notes`，或与 `admission_status` 一致的 `skipped`、`interrupted`。引用场景包的触发只有进行中时 `outcome` 为空。
- `accepted` 的约束（拟议，SP-B 定稿）：未引用场景包（`stage` 为空）的触发仍须有 `task_id` 与 `run_id`，与现行一致；引用场景包的触发不要求 `task_id` 与 `run_id`，只有 `stage = 'agent'` 时可以有。

**受理：**

- 顺序为：同一触发去重（沿用 `(routine_id, trigger_id)` 唯一键）→ 规则状态 → 重叠与待处理名额 → 场景包状态 → 执行身份与授权复核（与现有 `authorizeAgentRoutine` 同一规则）。全部通过后，把执行身份、授权上限、数据工具绑定与参数取值冻结到触发记录，再进入取数；任一项不通过都记为 `skipped` 并写明原因，不取数。
- 规则固定的场景包被停用或被标为“依赖缺失”时不予受理（原因“场景包不可用”），同时告警规则负责人，不降级继续。
- 重叠检查与按 Agent、全局的待处理名额都按“`admission_status = 'accepted'` 且 `outcome` 为空”计入，覆盖 Run 之前的阶段与 Agent 阶段；未引用场景包的触发照旧按 Run 状态计入。引用场景包的规则固定不允许重叠，所以同一规则任何时候最多只有一个触发在进行。
- 创建 Run 时按现行规则再复核一次授权。

**规则状态的检查：**

- 取数、计算、条件与交付开始前都检查规则状态；规则已暂停或停用时收敛为 `skipped`（`routine_inactive`），不告警。
- 交付之后规则不再启用的（Run 未能创建、没有 Attempt 的 Run 按功能规则第 7 节被清理、创建 Task 时数据库触发器报错、已有 Attempt 的 Run 被实时授权闸门拒绝），事实已经送达，触发记 `delivered_no_notes`（`routine_inactive`），不告警。
- 实施时让实时授权闸门的拒绝区分“规则不再启用”与“执行配置已变化”：两者都记 `delivered_no_notes`，后者按 Run 失败告警。

**交付：**

- **时机：** 计算输出通过校验、条件求值之后立即交付，不等 Agent 段（SP12）。交付段把计算输出组装成一份快照，经 6.9 的快照接口交给跟进项模块（SP16）。
- **一个事务：** 先以 `for update` 锁住规则行（与受理、停用、放权阶段切换同一把锁），在事务内再检查一次规则状态；对账结果、跟进项、通知与阶段推进（条件不满足写 `outcome = 'no_work'`；条件满足但场景包没有 `agent` 一节写 `outcome = 'delivered'`；条件满足且声明了 `agent` 一节写 `stage = 'agent'`）在同一事务写入，提交即完成，失败或中断时整体回滚、不留部分结果。
- **失败：** 记 `delivery_failed` 并告警，不自动重试；跟进项保持上一次运行的状态，由下一次运行（或管理员手动触发）重新对账。
- **不需要并发保护：** 同一规则同时只有一个触发在进行，交付不会并发，也不存在较早的结果晚交付、覆盖较新结果的情况。

**Agent 段的收尾：**

- Run 进入终态后，在终态迁移提交之后由同一处收尾（现有代码在同一位置为员工定时任务写失败通知）：Run 成功且输出通过校验的，把说明与排序写入本次触发交付的、仍未关闭的跟进项，记 `delivered`；其余情况记 `delivered_no_notes` 并写明原因（6.8）。
- 写入说明是幂等的（按触发覆盖），不设尝试次数。主动任务的调度周期补做 `stage = 'agent'`、`outcome` 为空、且 Run 已到终态或超过 10 分钟仍没有 `run_id` 的记录，保证一次没接上不会让这条规则之后的触发一直被判为重叠。

**进程中断与启动恢复：**

- `stage` 处在取数、计算、条件、交付且 `outcome` 为空的触发，收敛为 `interrupted`，不续办、不补跑，名额随之释放；交付事务没有提交即没有任何结果。
- `stage = 'agent'` 的触发，启动时执行一次与调度周期相同的补做：没有 `run_id` 的记 `delivered_no_notes`（`run_not_created`）；派发中断的记 `delivered_no_notes`（`dispatch_interrupted`），`admission_status` 保持 `accepted`（现有 `recoverInterruptedPreparations` 把派发中断写成 `interrupted`，对引用场景包的触发要分开处理）；Run 已到终态的按收尾规则处理。其余沿用现有 Run 的恢复语义。

**DSH 不可用时：** 取数、计算、条件与交付照常完成，跟进项带程序给出的事实与候选送达；Agent 段记 `delivered_no_notes` 并告警，跟进项显示“说明暂缺”，不以程序结果冒充 Agent 结论（规范 AS-03）。

### 6.5 取数

- 新建服务端 MCP 客户端（Streamable HTTP，`tools/call`），复用 Connector 的加密凭据、生效清单摘要、健康与停用检查。
- 按受理时冻结的执行身份、授权上限与数据工具绑定调用；每次调用前再检查 Connector 状态与工具标记，不通过记 `fetch_failed`。
- 只调用绑定且带标记的工具；标记与 Tool 名称和输入 Schema 摘要绑定，Schema 变化后自动失效（规范 AS-05）。
- 各次调用只使用参数取值与触发信息，互不传递结果。
- **数据新鲜度：** 声明了刷新时间字段的查询，平台在取数结束后检查返回的刷新时间不早于声明的要求（如“规则时区的触发当日 0 点”）；不满足记 `fetch_failed`（原因“数据未刷新”）并告警，不进入计算。
- 每次调用设超时与返回大小上限；失败、超时、超限都记为取数失败，不当作“没有数据”。
- 每次调用写入与 DSH 调用同等的 Tool 级审计。

**数据服务约定：** 数据服务由客户 IT 按业务系统建设，后续场景只增加查询。供程序步骤调用的工具须满足以下要求，作为双方的接口约定；标记工具前由管理员对照检查。

- **完整快照：** 一次调用返回符合条件的全部结果，不分页、不静默截断；同时返回行数，平台核对行数与实际收到的一致，不一致或超过大小上限时记取数失败。跟进项“不再出现即关闭”依赖这一条。
- **刷新时间：** 数据有刷新周期的查询返回刷新时间，供新鲜度检查。
- **稳定标识：** 用作去重键的字段不随每次刷新变化。
- **只按参数过滤：** 不接受其他查询的结果；参数只缩小返回范围，不改变统计口径。
- **Schema 变更走流程：** 输入 Schema 变化会使“可供程序步骤调用”的标记自动失效，正在运行的规则随即取数失败；改接口前须通知平台管理员，变更后重新确认标记。

平台与数据服务并行建设：先定稿工具契约（参数与返回字段），平台按契约用假数据服务开发和测试，客户 IT 按同一契约实现；同一个数据服务同时供员工在对话中查询，目标环境的企业 MCP 验收（PF-07）借首个数据服务一并完成。

### 6.6 计算

- 经单独的 `ContainerExecutor` 实例（SP7）调用 `runPythonSandbox`，在一次性容器中运行声明的入口；隔离方式沿用成果解析的路径，目录与单文件入口按 6.2 的约定。
- 资源另设计算段档位：内存、CPU、单文件与输出合计大小、运行时长。现有 `runPythonSandbox` 的资源固定为 256 MB、0.5 CPU、单文件 10 MB，SP-B 要让执行器支持按请求的档位设置，数值用欠料样例实测后定稿。
- 等槽位与运行分别计时：等槽位超过 10 分钟记 `compute_failed`（原因“排队超时”），运行超过档位时长记 `compute_failed`（原因“运行超时”）。
- 输入目录放本次取数结果、参数取值、触发信息与反馈值（JSON 文件），输出目录收结果文件；运行结束后无论成败删除两个目录。
- **反馈值：** 声明为“作为计算输入”的反馈字段，平台按（规则、去重键、字段）保存最后一次录入的值，不随跟进项关闭而失效；接收人可以改写或撤销，每次变更记入跟进项历史（6.9）。例如录入的交期使风险消除、跟进项自动关闭后，下一次运行仍读到这个交期，同一风险不会作为“新增”重新出现。平台不判断反馈值是否过期：`feedback.json` 带录入人与录入时间，是否仍然采用由计算脚本决定（如所录入的交期已过则忽略，SP13）；最后一次录入满 180 天后清理（SP5）。影子运行切换到通知相关人时清除全部反馈值（6.9）。只读，审计记录条数与摘要。
- 输出按声明的字段校验；不合格记为计算失败。stdout 与 stderr 不保存正文。

### 6.7 条件

只提供固定判断方式：计数比较、布尔字段为真、字段存在。不在服务进程中解释表达式。数据是否新鲜不由条件判断（6.5）。

条件只决定是否执行 Agent 段，不影响交付：计算输出通过校验后，无论条件是否满足都按 6.9 对账，风险全部消除时这次交付就关闭全部未关闭项。条件不满足时不创建 Run、不调用模型（规范 1.1 原则 4），交付完成后记 `no_work` 并写明原因。场景包没有声明 `agent` 一节时同样不执行 Agent 段，交付完成后记 `delivered`。

**批量关闭保护：** 一次交付要自动关闭的项超过该规则未关闭项的一半、且不少于 10 条时，本次暂不执行自动关闭：其余对账照常，待关闭的项在跟进项上做标记、记入运行记录并告警负责人；下一次运行仍得出同样结果时才关闭。数据服务异常返回空结果而刷新时间正常时，就会出现这种情况；代价是风险真的全部消除时，关闭要晚一次运行。

### 6.8 Agent 段

- 交付完成、条件满足且场景包声明了 `agent` 一节时，原子创建 Task 与 Run（与现有主动任务一致：Run 不关联 Session，`sessionId` 为空；Workspace 沿用主动任务）。这次 Run 的任务输入是场景包自带的任务说明（`agent/instructions.md`，SP15），加上声明选定的字段作为只读输入（每次最多条数按声明，紧急优先），按工具结果经过数据防护遮盖。
- **任务说明的边界：** 它只是这一次任务的文字输入，不能声明工具、Skill 或权限；AI 同事能用什么仍由它的 Agent Version 与当前授权决定。交给模型的字段、输出约定与任务说明同在一个场景包版本里，一起变更。领域通用知识可以另做成普通 Skill 由 AI 同事选用（供“问 AI”时使用），不是必需。
- **只补充说明与排序：** 跟进项与通知在此之前已经送达。说明写入之前，本次新增的跟进项显示“说明生成中”；此前已有说明的项保留上一次的说明并标注“说明基于 {时间} 的运行”，直到被新的说明覆盖。Agent 段没有产出合格的说明时显示“说明暂缺”。
- **输出（结构化输出接通前的过渡做法）：** AI 同事按任务说明把结果写成 `output/` 下两份约定文件名的 CSV：说明（去重键、说明）与排序（去重键、候选编号、名次、一句理由）。现行成果登记接受 CSV、不接受 JSON，这两份文件因此登记为该 Run 的成果；平台在 Run 结束后读取并按声明校验：去重键须在本次计算输出中，候选编号须来自该键的可行候选，数量与日期不取自 AI 输出。说明与排序只用于展示和决定显示顺序，不驱动任何动作（规范 1.1）。主动任务的 Run 若不适用现行成果登记，SP-D 把它列入功能规则第 1 节的修订。结构化输出约束（AS-02、AS-10）接通后改用结构化结果。
- **各种结果：** 跟进项在所有情况下都已送达，区别只在说明与排序。

| 情况 | 记录 | 告警 |
| --- | --- | --- |
| Run 成功，输出通过校验 | `delivered` | 否 |
| Run 成功，但输出文件缺失、格式不符或校验不通过（SP9） | `delivered_no_notes`（`invalid_output`），运行记录写明原因 | 否 |
| Run 未能创建（创建前的授权复核未通过）或派发中断 | `delivered_no_notes`（`run_not_created` 或 `dispatch_interrupted`） | 是 |
| Run 失败、取消或超时（含 DSH 不可用、预算耗尽、执行配置已变化） | `delivered_no_notes`，关联 Run | 是 |
| 规则暂停或停用：Run 未能创建、被清理，或被实时授权以“规则不再启用”拒绝 | `delivered_no_notes`（`routine_inactive`） | 否 |

说明缺失不影响跟进项的正确性：事实与候选都来自程序，说明暂缺时如实标明，不以程序结果冒充 Agent 结论（AS-03）。规则暂停或停用是人为操作，不算失败。

### 6.9 跟进项

**定位：** 跟进项是业务数据的投影：某件事在业务系统里此刻成立、需要某个人处理，平台把它放到这个人面前，并随数据变化自动更新和关闭。它存在的依据是数据，不是人的意愿，这一点把它与站内通知、项目任务分开。

| | 站内通知 | 跟进项 | 项目任务（功能规则 3.9） |
| --- | --- | --- | --- |
| 表达的是 | 发生过一件事 | 一件事现在仍然成立，需要你处理 | 人与人约定要做的一件工作 |
| 由谁产生 | 平台事件 | 程序步骤按数据对账 | 成员明确新建，或明确要求 Agent 新建 |
| 状态由谁决定 | 没有状态，只有已读 | 主要由数据决定，人只能反馈 | 由人推进 |
| 可见范围 | 接收人 | 接收人与规则负责人 | 项目空间全体现任成员 |
| 附带内容 | 一句话与跳转 | 结构化事实、候选方案、反馈表单 | 任务对话、成果、执行规则 |

跟进项不做成项目任务：项目任务只在成员明确要求时新建、Agent 不得自行新建，且每个任务创建时都要建立任务对话，这两条都与“系统按数据自动产生、每人每天可能几十条”冲突。由定位得出五条规则：

1. **只能由程序步骤产生。** 员工不能手动新建，模型在对话中也不能新建；事实来自程序是跟进项的定义。第一期只有平台内部的交付接口，不提供对外提交入口，出现其他来源时再评审。
2. **人不能“完成”它，只能反馈。** 事项是否还成立由数据决定，下一次运行中不再出现才自动关闭；“误报”与“不再处理”是告诉平台不再提醒，不表示工作已完成。
3. **属于个人，不属于项目空间。** 规则的 Workspace 只用于承载 Agent 段的 Task 与 Run；跟进项不是空间内容，空间成员看不到他人的跟进项。
4. **不做成工单系统。** 没有人工指派与改派（转交只随数据中的接收人变化），没有评论串，没有审批与时限升级。
5. **平台保存业务事实，但模型不写。** 源系统不留历史（新增、变差、持续只能靠平台记住上一次的结果）、人补充的事实没有别处可放、评价效果需要历史，所以平台必须保存这些事实。它们只由程序步骤和人的反馈写入，分类与规则见下文“平台保存的业务事实”。

**平台保存的业务事实：** 范围只限经跟进项产生的以下四类，不提供供各 Agent 读写的通用业务数据存储（规范 3.3）。

| 类别 | 例子 | 以谁为准 | 谁能写 | 规则 |
| --- | --- | --- | --- | --- |
| 快照事实 | 缺口、最晚到货日、预计到货日 | 业务系统 | 程序步骤 | 带取数时间，平台上不可编辑，下一次运行整体覆盖 |
| 人工补充事实（反馈值） | 接收人录入的新交期、可到数量 | 平台，直到能写回业务系统 | 当前接收人，经声明的表单 | 记录录入人与时间，可以改写和撤销，每次变更留痕（6.6） |
| 处理状态 | 待处理、处理中、误报及原因 | 平台 | 当前接收人与对账程序 | 见下文“状态” |
| 变化历史 | 哪次运行新增、变差，分值与关键事实怎么变 | 平台 | 对账程序 | 只记严重度分值与场景声明的跟踪字段的前后值，不保存每次运行的完整快照 |

- 落库的字段由场景声明（事实字段、跟踪字段、敏感字段），未声明的取数结果与计算输出不进入跟进项。声明为敏感的字段，管理端的跟进项页签与审计不显示其值；接收人与规则负责人照常可见。
- 第一期这些数据只经跟进项页面与“问 AI”的快照使用，不提供给其他 Agent 的查询工具。
- 人工补充事实写回业务系统，随“经批准写入外部系统”一级另行设计；在此之前平台是它唯一的存放处，按正式数据对待（审计、备份、保留期），不视为临时数据。

与项目任务的衔接（第一期不做）：接收人认为某条跟进项需要与同事协作时，由他明确操作“据此新建项目任务”，带上当时的事实快照；这符合“任务只在明确要求时新建”，两类对象不合并。

**快照接口（平台内部，SP16）：** 跟进项模块与取数、计算管道之间只有一个接口，登记在[内部端口与契约](../development/internal-ports.md)。管道的交付段提交一份快照：规则、本次触发、取数时间，以及一组行，每行带去重键、接收人字段的值、严重度分值、声明的事实字段与候选方案。一次提交就是这条规则当前的完整结果；对账、接收人映射、按人分发、通知与批量关闭保护都在接口之后，由跟进项模块在一个事务内完成（6.4）。跟进项模块不关心快照由计算脚本产生还是由数据服务直接返回。第一期调用方只有程序步骤的交付段，不对外开放（规则 1）。

**归属与可见：** 跟进项属于工作规则，按接收人可见；规则负责人和具备该主动任务管理权限的管理员可以查看全部（负责人在员工端的负责人视图，6.10；管理员在管理端，6.11）。

**写权限：** 第一期只有当前接收人能执行反馈动作；规则负责人与管理员只读。影子运行时接收人就是规则负责人。

**对账：** 每次交付按去重键与该规则的未关闭跟进项比对：

| 情况 | 结果 |
| --- | --- |
| 新出现的键（含此前已自动关闭的键） | 新建，标“新增” |
| 已有的键，严重度分值比上一次高 | 更新事实，标“变差” |
| 已有的键，严重度分值没有升高 | 更新事实，标“持续”，记录持续天数 |
| 已有的键，接收人字段映射到另一名员工 | 转给新接收人，状态与处理记录保留，对新接收人标“新增”并计入其通知；原接收人不再可见 |
| 已有未关闭的键本次没有出现 | 自动关闭，原因写“本次结果中不再出现”（受 6.7 的批量关闭保护） |
| 被接收人标为误报或“不再处理”的键再次出现，严重度分值不高于标记时的分值 | 不新建，不通知 |
| 被接收人标为误报或“不再处理”的键再次出现，严重度分值高于标记时的分值 | 重新打开，标“变差” |

严重度分值由计算脚本按场景口径给出（SP13），平台只比较大小，不解释它的含义。误报与“不再处理”的抑制按（规则、去重键）查找接收人关闭的跟进项，随该项按 SP5 的保留期清理而结束；影子期由规则负责人标的误报只用于校准，不带入通知阶段。

**反馈后的重算（SP10）：** 反馈不发起触发。平台保存反馈值，跟进项按动作声明进入“处理中”或关闭；声明为计算输入的反馈，详情标“已录入，下次运行重算”，并显示当前结论所依据的取数时间。下一次运行读取反馈值重算：风险消除的，该键不再出现，按对账自动关闭；仍有风险的，按新的事实更新。

**放权阶段切换（SP11）：** 只能从影子运行进入通知相关人，不能退回。切换时锁住规则行，关闭影子期全部未关闭跟进项（原因“放权阶段切换”），清除影子期录入的反馈值；影子期的处理记录与误报都不带入（负责人为校准录入的交期不能抵消采购员的风险）。下一次运行全部按“新增”分发并通知。跟进项记录创建时的放权阶段，用来区分影子期的项。需要重新校准时，停用规则、新建规则从影子运行开始。

**接收人：** 接收人字段经 `erp` 渠道（SP3）映射到员工；映射出的员工还须是在职状态（账号未停用；AI Hub 账号经目录同步停用时不经过绑定失效路径，靠这条检查兜底）。映射不到、员工已停用或不在接收范围内的行不投递，记入运行记录，在负责人视图中提示（6.10）并发告警通知（6.12）。接收人离职或被移出接收范围后不再看到原跟进项；这些项在负责人视图中标为“无人负责”，外部账号对应更新后按“接收人变化”转交。

**规则暂停与停用：** 暂停期间跟进项照常可以反馈，反馈值照常保存，由恢复后的下一次运行使用。停用是终态（现有代码不能从停用恢复为启用）：停用时锁住规则行，关闭全部未关闭跟进项（原因“规则停用”），接收人仍可在“已关闭”页签查看，规则负责人仍可在负责人视图中只读查看（6.10）。所有跟进项关闭后按 SP5 保留 180 天。主动任务没有删除操作，不另设删除处理。

**状态：** 待处理 → 处理中 → 已关闭。关闭原因：自动关闭、误报、不再处理（如不再续签）、放权阶段切换、规则停用，以及动作声明的其他原因。

**数据：** 事实字段与候选方案直接来自计算输出，并记录来源与取数时间；AI 说明与排序记录来自哪次运行，单独存放、单独展示。

## 7. 欠料风险预警（首个场景）

### 7.1 业务背景

业务链为客户订单 → 物料统计 → 物料采购 → 欠料追踪 → 计划排产。采购员经常不能按期完成所需物料的采购到货。需要按计划排产日期倒推，定时找出有到货风险的物料，通知负责的采购员及时与供应商跟进，并给出可行的替代方案。

### 7.2 计算口径

- **需求：** `SUGGESTION_PLAN` 的建议计划行，已含 ERP 的最终计算结果。ERP 不保留历史，新增与变差靠跟进项对账（6.9）判断。
- **风险来源：** 建议计划行尚未转采购单；已下单，但对应采购单有到货风险。
- **最晚到货日** = 需求日（按订单交货日期倒推的排产日期）− 检验入库天数 − 安全缓冲。
- **预计到货日** 依次取：SRM 预计到货（发货单）› 供应商确认交期（SRM 中的确认与采购员录入取确认时间较晚的一个，SP2）› PO 承诺交期 › 今天 + 采购提前期（尚未下单时）。“今天”是规则时区的触发日期。
- **风险类型：** 未下单；交期未确认；确认交期晚于最晚到货日；应发未发；在途但晚到；数量不足；数据冲突（ERP 与 SRM 不一致）。
- **数量不足：** 最晚到货日之前预计能到的数量小于需求数量。能到的数量按已发货的取发货数量、未发货的取确认数量、未确认的取订购数量，采购员录入了可到数量时按 SP2 的同一规则取用。
- **紧急程度（阈值为参数）：** 紧急 = 预计晚到，且距最晚到货日不超过紧急阈值；重要 = 预计晚到但时间较多，或交期未确认、应发未发、数量不足，且距最晚到货日不超过重要阈值；关注 = 其余情况，含数据冲突。预计晚到且涉及重点客户订单时上调一级。
- **运输天数**（判断应发未发）按供应商近 6 个月发货到签收的中位数计算，数据与其他查询一轮取齐（7.3）。
- **接收人：** ERP 中该物料的采购员。
- **替代方案：** 只对预计晚到的风险计算，每类都核对能否赶上最晚到货日，不可行的也列出原因。
  - 分批催交：按需求日分段的缺口，算出首批最晚要多少、哪天前到；
  - 换或加供应商：货源清单中其他合格供应商，今天下单加提前期能否赶上，附价差与近 6 个月准时率；
  - 替代料：BOM 替代关系，可用量是否覆盖缺口且不挤占替代料自身的需求，需工艺或客户确认的标出；
  - 调拨：其他仓库或工厂未分配的可用库存与调拨天数。
- **反馈：** 已跟进（新交期、可到数量；两项按去重键保存为反馈值，所录入的交期过后脚本不再采用；由下一次运行重算，SP10）；采用方案（只能从可行候选中选，进入处理中，取数结果中出现对应采购单或调拨单后按新的事实更新）；误报（原因必填：数据错误、已到货 ERP 未入账、需求已取消或变更、其他）。

### 7.6 上线与放权

- **平台改造之前：** 按规范 1.1 的现行约束，可以先做模型编排的影子运行：一条主动任务，欠料助手经 MCP 读取上述查询，接收人只有采购主管，结果留在该次 Task 中。用它尽早核对数据口径与查询，不作为交付给采购员的依据。
- **平台上线后：** 影子运行 2～4 周，跟进项只交给采购主管；对照实际到货校准参数。
- **进入“通知相关人”的条件：** 采购主管确认口径无误，且误报率连续 2 周低于约定值。切换时按 6.9 关闭影子期跟进项，下一次运行全部按新增分发。
- **衡量指标：** 预警覆盖率（实际晚到的物料中提前预警过的比例）、误报率、平均提前预警天数、替代方案采纳率。

## 9. 风险

| 风险 | 处理 |
| --- | --- |
| 场景声明不断加功能，演变成工作流引擎 | 固定五段与固定判断方式；新增声明能力须有实际场景并经评审 |
| 通用渲染满足不了个别场景的展示 | 字段类型按场景需要逐个加入（如日期对比），不允许场景自带页面代码 |
| 计算脚本是租户代码 | 一次性断网容器、依赖只来自执行镜像、输出按字段校验、只由管理员发布 |
| 计算数据量超出档位 | 档位按样例实测定稿；超出时把候选计算下推到数据服务 |
| 数据服务不按人过滤 | 交付由程序按接收人拆分；数据边界是 Agent 的可见角色，保存规则与修改可见角色时按接收范围校验（SP4）；敏感场景先解决身份传递 |
| 反馈后要等下一次运行才重算 | 详情标注“已录入，下次运行重算”与结论所依据的取数时间；ERP 数据每天只刷新一次，立即重算也只能用同一批数据（SP10）；确有需要时再评审 |
| 更换场景包版本后不自动回到影子运行 | 重新启用前管理员查看新版本的样例运行证据并确认；口径有实质变化时停用旧规则、新建规则重新影子运行（SP11） |
| 模型服务故障时跟进项没有说明 | 事实与候选照常送达，标“说明暂缺”并告警负责人；下一次运行补上（SP12） |
| 数据服务异常返回空结果，跟进项被批量关闭 | 批量关闭保护：一次要关闭过半且不少于 10 条时暂缓并告警，下一次运行结果相同才关闭（6.7） |
| 外部账号对应维护不及时，跟进项发不出去 | 未投递行进入运行记录并告警规则负责人；数据服务提供核对查询 |
| 去重键不稳定，跟进项每天都变成新增 | 去重键用稳定的业务标识，不含采购单号；欠料-0 请客户 IT 确认行号与需求序号的稳定性 |
| ERP 刷新晚于运行时间，导致用旧数据 | 取数段按规则时区检查数据刷新时间，未刷新记取数失败并告警 |
| AI 说明与事实不一致 | 事实只取计算输出，AI 说明单独展示并注明仅供参考；候选编号校验 |
| 误报多，采购员不再看 | 影子运行校准；误报率作为进入下一级的门槛；误报原因用于修正口径 |
| 场景包自带的任务说明被用来扩大 AI 同事的能力 | 任务说明只作为该次 Run 的文字输入，不能声明工具、Skill 或权限；发布时做密钥预检；场景包只由管理员发布（SP15） |
| 场景包成为新的一套版本与发布流程，增加管理负担 | 复用 Skill 包的解包、依赖登记与存储做法；发布证据由平台自动产出；只做列表、上传与只读详情，不做在线编辑 |

**P1 清单：**

- **不唤醒模型（AS-03）：** 条件不满足、取数失败、计算失败与交付失败的路径上不创建 Run，模型网关与 DSH 的请求数为 0；`no_work`、`fetch_failed`、`compute_failed`、`delivery_failed`、`delivered`、`delivered_no_notes` 六种记录可区分。
- **交付先于 Agent（SP12）：** DSH 不可用时跟进项与通知照常送达，触发记 `delivered_no_notes` 并告警，详情显示“说明暂缺”；Run 成功后说明与排序写入已交付的跟进项；输出不合格时记 `delivered_no_notes`、不告警；此前已有说明的项在新说明写入前保留旧说明并标注来源。
- **受理与状态：** 受理时授权复核未通过不取数；场景包停用或依赖缺失时不予受理并告警；取数中暂停规则，触发收敛为 `skipped` 且不告警；Agent 段进行中暂停规则，记 `delivered_no_notes`（`routine_inactive`）且不告警，已交付的跟进项不受影响；上一次触发的 Agent 段尚未结束时，新的触发按重叠跳过。
- **恢复与交付：** 取数、计算或交付中重启后收敛为 `interrupted`、名额释放且不留部分跟进项；交付失败记 `delivery_failed`，跟进项保持上一次状态，下一次运行正常对账；交付后、Run 创建前重启，启动后记 `delivered_no_notes`（`run_not_created`）；派发中断记 `delivered_no_notes`；Run 结束后收尾抛错，不重启也能在下一个调度周期收敛，后续定时触发不被记为重叠；交付与停用、放权阶段切换并发时互斥，停用后不留下未关闭项。
- **取数与计算：** 标记因 Schema 变化失效后取数失败；数据未刷新记取数失败；返回行数与实际不一致或超限时记取数失败；计算排队超时与运行超时分开记录；计算容器断网且输入输出目录用后删除。
- **场景包（SP14、SP15）：** 更换场景包版本不需要新的 Agent Version；通知相关人阶段更换版本须管理员确认后才能重新启用；没有 `agent` 一节的场景交付后记 `delivered` 且不创建 Run；模型在对话中加载不到场景包，计算脚本不是模型可调用的入口；Skill 的安装、起草与广场行为不变。
- **跟进项：** 同一键连续两次运行标“持续”、严重度分值升高标“变差”、消失后自动关闭；风险全部消除时这次交付关闭全部未关闭项且不创建 Run；录入交期后跟进项标“已录入，下次运行重算”，下一次运行风险消除则关闭，之后连续两次运行都不重新出现“新增”；误报后分值高于标记时才重新打开；规则停用时未关闭项全部关闭；影子运行只交给规则负责人；影子运行切换到通知相关人后，影子期的项关闭、反馈值清除，下一次运行全部按新增分发；数据服务返回空结果时暂缓批量关闭并告警，下一次结果相同才关闭。
- **通知与权限：** 通知按人合并、告警按规则合并；采购员能打开跟进项通知（不依赖主动任务的查看权限）；非管理员的规则负责人能看到告警与负责人视图；授权复核未通过的跳过与停机错过会告警；ERP 绑定在重置密码后仍有效，账号停用或钉钉离职确认后失效；可见角色超出接收范围并集时保存规则与修改可见角色被拒绝；这类 Agent 不能加入规则 Workspace 以外的项目空间；负责人失去 Workspace 成员资格或数据范围后看不到负责人视图与告警；已停用账号不再收到跟进项。
