## 2. 结论摘要

本轮确认 21 个逻辑断点：5 个 P1、15 个 P2、1 个 P3。最先应处理的不是页面细节，而是五条端到端契约缺口：

1. 团队消息、讨论、@ 与 Run 根本不能进入当前通知模型；“消息提醒缺失”不是偶发刷新问题，而是事件类型和数据库约束均未覆盖。
2. 团队文件上传存在“对象已写入，但业务事务失败”的窗口；上传新版本时使用不存在的逻辑文件 ID，可留下对象存储孤儿。
3. “引用团队文件”入口只插入文字 `@工作空间文件`，没有选择文件，也没有绑定文件 ID，用户看到的是成功引用的外观，实际没有引用对象。
4. 客户端只在单次 HTTP 请求里生成幂等键；响应丢失后用户重试会生成新键，服务端会把同一次业务意图当成新的消息、Run 或自动任务执行。
5. 无 Run 的团队讨论从全局历史恢复时，页面允许“继续发送”，却没有团队逐消息 `@Agent` 选择，提交必然被服务端拒绝。

架构边界脚本通过，未发现为了补这些功能另建 Agent Loop 或绕过 DSH 的直接模型调用路径。当前问题主要集中在业务状态机、前后端返回契约、事件模型与实时同步，不是 DSH 执行引擎分叉。

## 3. 已确认问题

### F-01 · P1 · 团队消息、讨论、@ 与 Run 无法产生提醒

**用户表现**

- 团队空间里的新讨论、回复、@ 成员、Agent Run 开始/完成不会进入未读提醒。
- 现有提醒只覆盖成员、Agent 成员、文件、归档/恢复等管理事件。

**代码证据**

- `server/src/modules/workbench/application/workspace-activity-writer.ts:7-25` 明确关闭事件集合，并注明 message、未共享会话活动和 Run 详情不可表示。
- `server/migrations/0026_workspace_activity.sql:28` 的 `CHECK` 约束使用同一关闭集合。
- `server/src/modules/workbench/application/postgres-workspace-activity-service.ts:132-155` 的通知列表仅消费 `workspace_activities`，因此前述事件没有其他入口。

**影响**

这是数据模型断点，不是增加前端轮询即可修复。需要先定义可通知事件、收件人和隐私边界，再扩展迁移、writer、读模型和 E2E。

### F-02 · P1 · 上传新版本可在事务失败前留下对象存储孤儿

**用户/运维表现**

- 传入不存在、已移除或并发失效的 `logicalFileId` 时，请求失败，但原始字节可能已写入存储。
- 多次失败会形成数据库不可达、无法从产品界面清理的对象，带来无界磁盘增长。

**代码证据**

- `postgres-content-service.ts:1006-1015` 先调用 `prepareObjectWrite`。
- `postgres-content-service.ts:1982-2004` 的 `prepareObjectWrite` 在返回前执行 `storage.putIfAbsent`。
- `postgres-content-service.ts:1027-1034` 之后才在数据库事务内验证逻辑文件存在且 active。
- 该失败路径没有删除已写对象或孤儿回收登记。

**建议方向**

在落盘前完成可安全完成的对象级验证，并为不可消除的 TOCTOU 窗口提供对象写入补偿或可追踪的垃圾回收队列；不能削弱事务内的最终权限复核。

### F-03 · P1 · “引用团队文件”是无对象绑定的伪引用

**用户表现**

- 团队空间输入框的“引用团队文件”不会打开文件选择器。
- 点击后只往 prompt 插入 `@工作空间文件`，没有 `logicalFileId` / `fileId`，也没有加入 `referencedWorkspaceFileIds`。
- `team-space-composer` 虽监听 `open-files` 并跳 `/files`，但团队模式分支不会发出该事件；即使发出，`/files` 也是个人文件入口。

**代码证据**

- `packages/workbench-components/src/TaskComposer.vue:323-329`：`showWorkspaceContext` 为真时仅插入文字。
- 同文件 `540-543` 把该命令展示为“引用团队文件”。
- `apps/workbench-web/src/components/team-space-composer/team-space-composer.vue:20`：死分支仍指向 `/files`。
- 真正的团队文件引用只存在于团队空间 Files 页的“引用到对话”，经 `referencedWorkspaceFileIds` 传递。

**建议方向**

要么把该入口接到当前空间的受权文件选择器并提交稳定 ID，要么在选择器完成前移除/改名，不能保留会制造已引用错觉的文本标记。

### F-04 · P2 · 首次上传解析失败被当作“完全失败”，实际已持久化文件与动态

**用户表现**

- 服务端先创建逻辑文件、pending 版本和 `file_uploaded` 动态；解析失败后把版本改为 failed 并抛错。
- 前端只显示上传失败，不刷新列表。用户重试会再次创建逻辑文件，容易形成重复条目。

**代码证据**

- `postgres-content-service.ts:684-734` 在解析前提交对象、逻辑文件、版本和动态。
- `postgres-content-service.ts:736-766` 解析失败后保留 failed 记录并抛错。
- `apps/workbench-web/src/stores/content.ts:74-80` 只在请求成功返回后插入本地列表。

**建议方向**

统一“上传已接收但解析失败”的 API 语义：返回可展示的失败文件投影，或在前端捕获已创建对象并刷新；重试应是同一逻辑文件的新版本/重解析，而不是静默再建一份。

### F-05 · P2 · 成功上传后的文件暂时不可引用，刷新后才恢复

**用户表现**

- 上传成功后文件立即出现在列表，但“引用到对话”按钮缺失。
- 刷新工作空间后按钮出现。

**代码证据**

- `content.ts:74-80` 把上传响应直接插入 `workspace.files`。
- `postgres-content-service.ts:749-759` 的上传响应没有 `canReference`、`canDownload`、`parseStatus`、`versionCount` 等列表投影字段。

**建议方向**

上传接口返回与列表接口相同的服务端派生投影，或成功后只按逻辑文件 ID 重取该行；不要在前端猜权限和解析状态。

### F-06 · P2 · 首条消息或附件失败会留下空会话

**用户表现**

- 新任务先创建 Session，再上传附件并启动 Run；后续任一步失败都没有补偿。
- 纯讨论同样先创建 Session，再发送首条消息；发送失败会留下没有消息的会话。

**代码证据**

- `apps/workbench-web/src/stores/tasks.ts:125-137`：`createSession` 与 `startRunWithSessionFiles` 分成两步，无清理/幂等继续机制。
- `ConversationStarter.vue:226-231`：纯讨论的建会话和发首条消息分开，无失败补偿。

**建议方向**

优先提供服务端原子“创建会话 + 首条消息/启动意图”，或把 draft Session 显式建模并支持安全重试/回收；不要从前端直接删除可能已有并发写入的会话。

### F-09 · P2 · “全部已读”使用当前时间，存在提交时序竞态

**风险场景**

事务 A 在点击“全部已读”之前开始写 activity，但在 `last_read_at = now()` 之后才提交。该活动的数据库时间戳可能早于 read watermark，提交后也不会再次进入未读。

**代码证据**

- `postgres-workspace-activity-service.ts:158-175` 直接把 `last_read_at` 推进到 `now()`，没有记录已观察到的 activity 游标/最大序号。

**建议方向**

用“用户确实看到的最后一条 activity”的稳定游标或单调序号标记已读；API 应提交该游标，而不是服务器墙钟时间。

### F-10 · P3 · 工作空间总列表携带所有团队文件摘要，数据量无上界

**风险场景**

- `GET /workspaces` 为所有可访问空间加载完整成员名和完整文件摘要。
- 团队文件数量增长后，团队空间首页和任何 `contentStore.refresh()` 都会承受与“所有空间文件总数”线性增长的查询、序列化和前端状态开销。

**代码证据**

- `postgres-content-service.ts:222-315` 的 `listWorkspaces` 批量挂载每个空间的 `files`。
- `postgres-content-service.ts:323-360` 的团队文件摘要查询没有 limit/cursor。
- 已存在分页文件接口，但团队空间详情仍主要消费全局 workspace 投影。

**建议方向**

列表接口只返回 `fileCount`/少量预览；详情 Files Tab 使用现有分页接口并独立缓存。该项在小数据量下不阻塞当前使用，但应在通知和文件 UX 修复时一并拆契约，避免重复迁移前端状态。

### F-11 · P1 · 不确定结果重试会绕过服务端幂等保护

**风险场景**

- 服务端已经提交消息、Run 或自动任务执行，但响应在代理/网络层丢失或超时。
- 页面显示失败；用户再次点击时，前端重新生成 `crypto.randomUUID()`。
- 服务端只把“相同幂等键”识别为重放，新键会创建第二份业务记录或第二次执行。

**代码证据**

- `apps/workbench-web/src/stores/tasks.ts:169`、`:225` 分别在每次消息提交和 Run 启动时生成新键。
- `SessionResumeView.vue:50`、`AutomationsView.vue:296-298` 的继续对话、立即运行、试运行也在每次点击时生成新键。
- `automation-service.ts:323-335` 明确约定“同键重放返回原执行，新键 = 新触发”。

**建议方向**

在一次用户业务意图开始时生成并持久保存键，只有明确收到终态结果或用户选择“再次执行”后才轮换；遇到网络不确定结果时用原键查询/重放。对消息、Run、自动任务分别增加“服务端已提交但客户端未收到响应”的集成测试。

### F-12 · P2 · “继续对话”附件失败不会清理已上传文件

**用户/数据表现**

### F-13 · P2 · 工作空间读取被无关的成果/Agent 接口绑成全有或全无

**用户表现**

- 文件版本、恢复等成功操作后的整页刷新也会受无关接口拖累，使成功写入看起来没有生效。

**代码证据**

**建议方向**

### F-14 · P2 · Run 终态快照遇到一次瞬时失败就停止恢复

**用户表现**

SSE 已收到完成/失败事件后，前端会关闭 Run 流。如果随后第一次 `GET Run` 短暂失败，最终回答、成果、token 使用量或错误详情可能停留在不完整的本地快照，直到用户手工刷新。

**代码证据**

- `tasks.ts:466-470` 在 `settleRunSnapshot` 后关闭流。
- `tasks.ts:478-495` 虽设计了 6 次投影重试，但 `expectTerminal` 为真时 catch 在第一次错误就返回旧快照；后续重试不执行。
- `scheduleRunReconciliation` 在本地已是终态时又会直接跳过，不能补偿这一失败。

**建议方向**

把“投影仍非终态”和“GET 瞬时失败”统一纳入有界重试；关闭 SSE 后仍保留一次可取消的终态对账，页面卸载/账号切换时终止。

### F-15 · P2 · 自动任务“停用”实际是不可恢复的软删除，并同时隐藏审计历史

### F-16 · P2 · 自动任务执行历史静默截断为最近 50 条

**用户表现**

长期每日/高频任务只能看到最近 50 次执行；页面没有“仅显示最近 50 条”、分页或加载更多，因此用户会误认为更早记录不存在。

### F-17 · P2 · 广场展示版本与实际创建会话版本之间存在静默切换

**风险场景**

用户在 Agent/Skill 广场看到 v1 并进入新对话；管理员随后发布 v2。用户提交时只发送业务 `agentId`/`skillId`，服务端解析“当前已发布版本”，会话可能静默绑定 v2，与用户刚刚查看的详情不一致。

**代码证据**

- `types/domain.ts:611-628` 的广场投影只有业务 ID 和展示版本，没有可提交的 version ID/reference。
- `AgentPlazaView.vue:17`、`SkillPlazaView.vue:27` 跳转只携带业务 ID。
- `api/client.ts:152` 的 `createSession` 也只接收 `agentId`/`skillId`。
- `conversation-routes.ts:132-162` 在创建 Session 的当下重新解析当前可用版本。

**建议方向**

让“选择”返回并提交不可变版本引用，服务端验证该版本仍可用；如产品明确选择“永远使用最新”，提交前必须刷新并向用户展示将实际绑定的版本，不能静默变化。

### F-18 · P2 · 后台/跨页产生的新任务和自动任务状态不会主动进入当前页面

**用户表现**

- `taskStore` 首次加载后永久短路；另一标签页或定时自动任务创建的新 Run 不会进入侧栏最近对话，也不会建立对应 Run SSE。
- 自动任务列表和已打开的执行记录抽屉只在进入或本页按钮动作后刷新；定时触发、Worker 状态变化不会自动更新。

**代码证据**

- `tasks.ts:72-82` 在 `initialized` 后直接 return，只对首次加载时已活跃的 Run 订阅。
- `AutomationsView.vue:326-367` 只在打开抽屉、页面装载和本页动作后加载，没有 SSE、可见性刷新或有界轮询。
- `admitAction` 只刷新自动任务/执行记录，没有把受理产生的 Run upsert 到 `taskStore`。

**建议方向**

建立统一的数据新鲜度契约：窗口重新可见、路由回到相关页时做条件刷新；对后台 Run 用账号级有界事件/轮询发现，再为活跃 Run 复用现有 SSE。不要为此新增 Agent 执行链路。

### F-19 · P1 · 无 Run 的团队讨论从全局历史恢复后无法启动 Agent

**用户表现**

- 团队会话只有讨论消息、还没有 Run 时，从全局历史或来源会话进入 `/sessions/:id`。
- 页面显示“继续发送会沿用原对话”并提供输入框；提交后必然收到“团队空间对话必须通过 @Agent 成员发起执行”。
- 该页面没有团队空间逐消息 `@Agent` 的成员选择能力，因此用户无法在当前旅程内完成操作。

**代码证据**

- `HistoryView.vue:46` 对所有历史项统一进入 `/sessions/:id`。
- `SessionResumeView.vue:50,72` 使用通用 `TaskComposer` 并直接 `startRun`，请求没有 `workspaceAgentMemberId`。
- `run-orchestration-service.ts:294-303` 明确要求团队空间每次执行都必须显式绑定 Agent 成员，不再回退会话级版本。

**建议方向**

团队 Session 恢复应复用团队空间会话 composer 和 Agent 成员解析；若当前入口只支持讨论，应发送普通团队消息而不是暗中启动 Run。P1 集成旅程需覆盖“纯讨论 → 全局历史 → @Agent → Run”。

### F-20 · P2 · “导出对话记录”只导出当前 Run，却命名为完整对话

**用户表现**

从最近对话菜单导出一个多轮团队会话时，文件会遗漏其他成员的纯讨论以及同 Session 的其他 Run，但下载名称仍是“对话记录”。用户无法从 UI 判断导出是不完整的。

**代码证据**

- `EmployeeShell.vue:84-95` 直接把侧栏 `TaskRun.messages` 拼成文本。
- `postgres-conversation-repository.ts:1296-1303` 明确让团队 `TaskRun` 只加载该 Run 的消息，而个人 Run 才加载 Session 完整历史。

**建议方向**

将“导出本次 Run”和“导出完整会话”拆成清晰动作；完整会话导出必须走受权的 Session thread 分页/导出端点，并包含范围、生成时间和是否截断的元数据。

### F-21 · P2 · 管理员被降权后，管理导航和写入口保持旧权限直到整页刷新

**用户表现**

管理员保持页面打开期间被降权、角色停用或数据范围收回，客户端仍展示原导航和写按钮；后续操作持续收到 403，页面没有自动收敛到当前可用范围。

**代码证据**

- `apps/admin-web/src/stores/auth.ts:55-78` 初始化后直接 return，没有刷新当前 Session 的路径。
- `apps/admin-web/src/api/client.ts:108-113` 只对 401 跳转登录；403 不触发身份刷新或路由/能力重新计算。

**边界与建议方向**

服务端仍执行授权检查，因此这不是权限绕过，而是撤权后的长会话体验和误操作问题。可在窗口重新可见、关键路由进入和授权相关 403 时有界刷新 Session；刷新后立即隐藏失效入口并导航到仍允许的页面。
