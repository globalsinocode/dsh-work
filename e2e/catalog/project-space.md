# 项目空间

团队空间导航与共享讨论、项目空间 S0–S4、Agent 维护项目任务（S6）。证据层级与写法见[验收目录索引](../TEST-CATALOG.md)。

### TW-E2E-01 项目空间导航与资源查看

**优先级：** P0
**角色：** 员工（冒烟测试身份）
**前置数据：** `ws-supply` 项目空间，包含两个共享文件及团队成果
**spec：** `e2e/mvp-smoke.spec.ts`

1. 从主导航“项目空间”打开 `/workspaces`，选择“供应链经营分析”。
2. 验证“任务”“对话”“共享文件”“成果”“档案”五个页签可见，默认选中“任务”。
3. 进入“共享文件”，验证两个合成文件名称；原型数据没有明确的可引用授权，因此不显示“引用到对话”入口。
4. 进入“成果”，验证团队成果名称可见。

**验收：** 当前空间 URL 正确；对应页签处于选中状态；文件和成果内容没有串到其他空间。

### TW-E2E-10 团队共享讨论与 @Agent 触发（TW-10）

**优先级：** P1
**角色：** 空间成员（member）、负责人（owner）、只读成员（viewer），各自独立 browser context
**运行层级：** P1 集成用户旅程（P0 不可达：Prototype 模式无会话持久化，命令面 503）
**前置数据：** 专用可丢弃 PostgreSQL；团队空间含 owner/member/viewer 三个测试身份与至少一个可发起的 Agent 成员
**spec：** `e2e/team-discussion.integration.spec.ts`（计划）；API 契约已由 `server/src/http/team-workspace-discussion-api.integration.test.ts` 固化

1. 成员 A 在空间「新对话」直接输入普通消息发送（不 @）：创建讨论会话并出现全员可见的讨论消息，不产生 Run。
2. 成员 B 打开同一会话（历史列表对全员可见）：读到 A 的消息并回帖，消息标注各自发送者。
3. 成员 B 输入 `@` 触发 Agent 成员补全，选择 Agent 后发送：创建 Run 并沿用该成员固定版本，回复进同一消息流且标注「由 B 发起」。
4. viewer 打开同一会话：消息流可读，输入框隐藏并显示只读提示。

**验收：** 无 @ 消息零 Run；@ 触发复用既有 Run/Attempt/Runtime 链路；发送者与触发人归因逐条可见；viewer 写入口不出现；归档空间全部写入口隐藏。

### TW-E2E-11 空间内对话视图（TW-10 导航）

**优先级：** P1
**角色：** 空间成员（member）
**运行层级：** P1 集成用户旅程（P0 不可达：Prototype 模式无会话持久化）
**前置数据：** 专用可丢弃 PostgreSQL；团队空间含至少一个可发起的 Agent 成员与一段历史会话
**spec：** `e2e/team-discussion.integration.spec.ts`（计划，与 TW-E2E-10 同文件）；组件行为由 `WorkspaceDetailView`/`ConversationView` 单测固化

1. 成员在空间页「新对话」发送消息（或 @Agent 触发 Run）：不离开 `/workspaces/:id` 上下文，地址栏进入 `/workspaces/:id/conversations/:target`，空间标题、页签与右栏保持可见。
2. 在对话视图内点「返回」：回到同一空间页的「新对话/历史对话」页签。
3. 「历史对话」打开任一会话：同样落在空间内对话视图。
4. 从空间外入口（工作台最近对话）打开团队会话 `/conversations/:id`：自动跳转到对应 `/workspaces/:id/conversations/:id`，空间外壳完整。
5. 个人空间会话仍使用 `/conversations/:id` 独立页，不发生跳转。

**验收：** 空间内发起/打开团队会话始终停留在空间上下文；返回键回到空间页而非工作台；空间外旧链接可解析但归位到空间 URL；个人空间路径行为不变。

### PS-E2E-00 团队交付边界按全体成员数据范围（项目空间 S0）

**优先级：** P1
**角色：** 负责人（owner，数据范围 A+B）、成员（member，数据范围 A+B）、待加入员工（数据范围仅 A），各自独立 browser context
**运行层级：** P1 集成用户旅程（受控 Runtime/Worker；P0 冒烟服务无授权计算，不可达）
**前置数据：** 专用可丢弃 PostgreSQL；团队空间含一个 Agent 成员，其 Agent 岗位授权包含数据范围 A、B 及一个 owner/member 都不具备的岗位角色；范围 A、B 各有一条可识别的合成业务数据
**spec：** `e2e/project-space-disclosure.integration.spec.ts`（计划）；授权契约先由服务端集成测试固化
**方案：** [项目空间方案第 3 节](../../docs/design/project-space-plan.md#3-团队交付边界s0)

1. 负责人打开 Agent 成员详情：显示“在本空间可交付的数据范围”为 A、B。
2. 成员在任务讨论中 @Agent 请求同时查询 A、B 两类数据：执行成功，回复含两条合成数据；成员本人不具备的岗位角色对应能力仍可用（角色只取 Agent 授权）。
3. 负责人添加只具备范围 A 的员工：确认前提示“加入后 Agent 在本空间的可交付范围将缩小为 A”。确认加入。
4. 成员再次发起同一请求：回复只含范围 A 的数据，不出现 B 的数据；Agent 成员详情的可交付范围显示为 A。
5. 负责人移除该员工后再次发起：范围恢复为 A、B，只影响新的执行。

**验收：** 可交付数据范围始终等于 Agent 授权与全体现任成员（含只读成员）数据范围的交集；岗位角色不随成员变化；加入成员收紧范围时有前置提示，在途执行按收权链路收敛；个人空间与员工个人请求行为不变。

### PS-E2E-02 员工任务创建与完成（项目空间 S1）

**优先级：** P0
**角色：** 员工（冒烟测试身份）
**运行层级：** P0 冒烟服务、内存数据
**前置数据：** `ws-supply` 项目空间，含至少一位员工成员
**spec：** `e2e/project-space.spec.ts`
**方案：** [项目空间方案第 5 节](../../docs/design/project-space-plan.md#5-项目任务s1)

1. 打开项目空间：默认进入“任务”页签，页签顺序为“任务、对话、共享文件、成果”。
2. 新建任务，填写标题、说明，负责人选择一位员工：任务出现在列表中，状态为“待办”。
3. 将任务标记为“进行中”，再点击“完成”，填写完成说明：状态变为“已完成”，卡片显示完成说明。

**验收：** 任务列表和状态变化对空间成员可见；空列表有引导，有任务时不显示空状态；表单字段有 label。

**S3 补充（统一任务与任务对话）：** 员工任务创建时即有任务对话；负责人在对话中首次发言自动进入“进行中”，状态推进与完成以系统记录出现在对话中，输入框旁可“标记完成”，对话中 @Agent 被拒绝。P0 冒烟服务没有会话，任务详情只验证页签隐藏、面包屑与任务信息卡片；对话部分由组件单测与服务端集成测试（`S3 员工任务对话…`）覆盖，P1 浏览器旅程见 PS-E2E-07。

**分页（P2-15）：** 列表每页 50 条，按创建时间倒序，超过一页时底部显示“加载更多任务”，页签计数取全部任务数。新建、编辑、完成、移除等写操作后列表重新读取并回到第一页，已加载的后续页需再次点击加载；该行为由组件单测与服务端集成测试覆盖，P0 冒烟数据不足一页，不验证翻页。

### PS-E2E-03 Agent 任务执行、线程续接与成果（项目空间 S1）

**优先级：** P1
**角色：** 成员 A、成员 B，各自独立 browser context
**运行层级：** P1 集成用户旅程（受控 Runtime/Worker；P0 冒烟服务无执行链路）
**前置数据：** 专用可丢弃 PostgreSQL；项目空间含一个可用 Agent 成员、一版简报与一个可引用的共享文件
**spec：** `e2e/project-space.integration.spec.ts`（`pnpm test:e2e:project-space`）；任务与执行契约另由服务端集成测试固化

1. 成员 A 新建任务，负责人选 Agent，引用共享文件后启动：生成任务线程并在任务详情内打开（停留在“任务”页签），状态为“进行中”；Manifest 携带当前简报版本与该文件。
2. 执行成功后：任务状态为“已完成”，成果出现在“成果”页签并标注所属任务。
3. 成员 B 打开任务线程直接回复（不 @）：交给同一 Agent 再次执行，回复标注由 B 发起；执行期间输入框不可发送并提示等待或停止。
4. 讨论中 @Agent 的一条线程被“设为任务”：任务列表出现该任务，负责人为该 Agent，当前线程转入该任务的详情。

**验收：** 每次执行都经既有 Run/Attempt；状态由最近一次执行推算；任务线程外的普通讨论仍须 @；任务线程始终在任务详情内打开，“对话”页签历史中的任务线程带“任务”标记。

**S3 补充：** Agent 任务创建时即有任务对话，未开始前可先评论；“交给 Agent”在未执行过时经任务启动（带补充要求与引用文件）；执行中只能“仅评论”，评论不产生 Run；执行记录紧跟发起它的消息，点击进入执行详情并可返回任务对话。由组件单测与服务端集成测试覆盖，P1 浏览器旅程见 PS-E2E-07。

**S4 调整：** 执行成功不再把任务推为“已完成”；任务保持“进行中”，由人标记完成（见 PS-E2E-07、08）。表格行内按钮为“立即执行”。

**覆盖（P1）：** 成员创建 Agent 任务并在任务线程直接续接，第二次运行落在同一线程，任务状态保持“进行中”（S4）。用例自建的任务标题带随机后缀，同一夹具上重跑（`--repeat-each=2`）互不干扰。
**未覆盖：** 引用共享文件、成果页签标注、讨论线程“设为任务”、成员 B 独立上下文；由服务端集成测试与后续旅程补足。

### PS-E2E-04 只读成员与归档空间的任务写入口（项目空间 S1）

**优先级：** P1
**角色：** 只读成员（viewer）、负责人，各自独立 browser context
**运行层级：** P1 集成用户旅程
**前置数据：** 专用可丢弃 PostgreSQL；项目空间含简报与若干任务；另有一个已归档空间
**spec：** `e2e/project-space.integration.spec.ts`（`pnpm test:e2e:project-space`）

1. 只读成员打开任务页签：可查看任务与简报，不显示“新建任务”“编辑简报”和任务线程输入框。
2. 负责人打开已归档空间：任务和简报只读，全部写入口隐藏。

**验收：** 写入口不渲染；服务端对应写接口返回 403 或 409；读取不受影响。

**覆盖（P1）：** 只读成员在活跃空间、负责人在归档空间均只能读任务列表，看不到新建/编辑/移除等任务按钮。
**未覆盖：** 任务线程输入框与简报编辑入口的只读态；服务端 403/409 由服务端集成测试覆盖。

### PS-E2E-05 项目档案查看、编辑与回退（项目空间 S2）

**优先级：** P0
**角色：** 员工（冒烟测试身份，空间负责人）
**运行层级：** P0 冒烟服务、内存数据
**前置数据：** `ws-supply` 项目空间，已有若干版项目档案
**spec：** `e2e/project-space.spec.ts`
**方案：** [项目空间方案第 7 节](../../docs/design/project-space-plan.md#7-项目档案与项目档案员s2)

1. 打开项目空间，切到“档案”页签（位于“成果”之后）：显示条目列表，标题下方标注当前版本号、来源与时间。
2. 编辑一条并保存：列表显示新内容，版本号加一，来源为本人手动编辑。
3. 添加一条、删除一条（删除前确认）：每次保存都生成新版本。
4. 打开“版本历史”：各版本标注来源；选择一个旧版本查看变更，点击“回退到此版”并确认：生成新版本，内容恢复为该版本，历史仍保留。
5. 右栏“项目简报”和“项目成员”卡片可分别收起和展开；成员卡片列出员工与 Agent，Agent 分组含“项目档案员（系统）”。

**验收：** 档案只在“档案”页签展示；编辑框和按钮有可访问名称；保存失败保留输入；手机宽度无横向滚动。

### PS-E2E-06 任务完成后档案员整理、Agent 读取档案（项目空间 S2）

**优先级：** P1
**角色：** 成员、只读成员，各自独立 browser context
**运行层级：** P1 集成用户旅程（受控 Runtime/Worker）
**前置数据：** 专用可丢弃 PostgreSQL；项目空间含一个可用 Agent 成员、一版简报
**spec：** `e2e/project-space.integration.spec.ts`（`pnpm test:e2e:project-space`）；档案员与读取契约另由服务端集成测试固化

1. 成员完成一个员工任务并填写完成说明：受控 Runtime 收到一次 `project-archive` 运行，输入含该说明；运行成功后“档案”页签出现档案员生成的新版本。
2. 档案员运行期间成员手动修改档案：本次输出被丢弃，基于最新版本重新整理，人工条目保留。
3. 成员启动一个 Agent 任务：Manifest `project_context.archive` 携带当前档案版本。
4. 只读成员打开“档案”页签：可查看条目与版本历史，不显示编辑、删除、添加与回退。

**验收：** 档案员每次运行都经既有 Run/Attempt；任务线程、最近动态不出现档案提示；服务端写接口对只读成员和归档空间返回 403。

**覆盖（P1）：** 仅第 1 步。完成员工任务触发 `project-archive` 运行，合成 Runtime 按本批任务标题生成档案条目（标题带随机后缀，重跑时不会被旧条目提前满足），轮询到档案出现该条目并在“档案”页签可见。
**未覆盖：** 档案员运行期间人工改写冲突、Agent 任务 Manifest 的档案版本、只读成员档案查看；由服务端集成测试覆盖。

### PS-E2E-07 任务对话（项目空间 S3）

**优先级：** P1
**角色：** 成员（受控测试身份 U00002）
**运行层级：** P1 集成用户旅程（受控 Runtime/Worker）
**前置数据：** 专用可丢弃 PostgreSQL；项目空间含一个可用 Agent 成员
**spec：** `e2e/project-space.integration.spec.ts`（`pnpm test:e2e:project-space`）
**方案：** [项目空间方案第 10 节](../../docs/design/project-space-plan.md)

1. 成员新建一个由自己承接的员工任务并打开：任务详情内显示任务对话，没有“交给 Agent”，提示发言不会触发 Agent，状态为“待办”。
2. 负责人在对话中发言：消息带“负责人”标记，出现“更新了进度，任务进入进行中”系统记录，状态变为“进行中”。
3. 点击输入框旁“标记完成”并填写完成说明：对话中出现“标记完成”记录与完成说明，状态变为“已完成”；全程没有 Run。
4. 成员新建一个由 Agent 承接的任务并打开：显示“还没有交给 Agent”。选择“仅评论”发言：消息带“评论”标记，仍未开始，没有 Run。
5. 切回“交给 Agent”并写补充要求发送：任务开始执行，对话中出现“交给 Agent 执行 · 执行完成”记录，状态保持“进行中”，“最近执行”为成功，只有一次 Run（S4）。
6. 点击执行记录进入执行详情：不显示输入框，只提供“返回任务对话”；返回后回到任务对话。
7. 在输入框旁“标记完成”并填写完成说明（S4）：状态变为“已完成”，“交给 Agent”不可选，只能评论。

**验收：** 员工任务与 Agent 任务规则一致，只是执行人不同；评论与员工发言不产生 Run；系统记录与执行记录按时间出现在任务对话中。

**覆盖（P1）：** 第 1～7 步。用例自建的任务标题带随机后缀，同一夹具上重跑互不干扰。
**未覆盖：** 执行中只能评论（合成 Runtime 立即完成，无法稳定停在执行中）、改派、他人在员工任务中发言不推进状态、只读成员的任务对话；由组件单测与服务端集成测试覆盖。

### PS-E2E-08 执行规则（项目空间 S4）

**优先级：** P1
**角色：** 成员（受控测试身份 U00002）
**运行层级：** P1 集成用户旅程（受控 Runtime/Worker；到点由仅在可丢弃夹具注册的测试钩子 `POST /api/workbench/v1/test/project-tasks/:taskId/fire-schedule` 拨动时间点并跑一轮调度）
**前置数据：** 专用可丢弃 PostgreSQL；项目空间含一个可用 Agent 成员
**spec：** `e2e/project-space.integration.spec.ts`（`pnpm test:e2e:project-space`）
**方案：** [项目空间方案第 11 节](../../docs/design/project-space-plan.md)

1. 新建任务，负责人选 Agent：弹窗出现“执行规则”，默认“每天 09:00”；改选“工作日”，点“保存并立即执行”：进入任务对话，任务信息显示“工作日 09:00”，第一次执行完成后任务保持“进行中”。
2. 在任务信息卡片点执行规则旁的“修改”，改为“手动”并保存：任务信息显示“手动”，对话中出现“将执行规则改为手动”系统记录。
3. 测试钩子触发一次定时执行：对话中出现“定时执行 · 执行完成”记录，不显示定时执行的固定提示。

**验收：** 每个 Agent 任务都有执行规则，手动只是没有定时触发；执行成功不改任务状态；定时执行以“定时执行”标注，不显示为某人发起。

**覆盖（P1）：** 第 1～3 步。
**未覆盖：** 执行中跳过、停机错过不补跑、过截止停止、规则设置人失效暂停、连续失败 3 次暂停与恢复、“无变化”回复折叠；由服务端集成测试（`S4 执行规则…`、`S4 定时执行…`、`S4 连续失败…`）与组件单测覆盖。真实时钟下跨天推进未验证。

### PS-S6-01 Agent 查看与维护项目任务（项目空间 S6）

**优先级：** P1（工具与权限）+ P0（结果卡片展示）
**角色：** 群组成员 roy（非只读）、只读成员、开启“项目任务管理”的 Agent 成员（dsh-work 助手）
**运行层级：** 服务端集成测试 `pnpm test:s6:project-task-tools:integration`（`project-task-tools.integration.test.ts`：工具处理器、复核、权限、归因，专用可丢弃 PostgreSQL）；P0 冒烟（`e2e/collab-mode.spec.ts` MODE-E2E-09，结果卡片展示「经 dsh-work Assistant」）。合成 Runtime 不能驱动真实工具调用，真实 DSH 中 Agent 选择并调用工具属于 P2，单独留证。
**前置数据：** 一个活动群组，含员工成员、只读成员与开启开关的 Agent 成员；若干项目任务

1. 群聊中 @Agent 查询任务：Agent 用 `project_tasks_list` / `project_task_get` 读到本群任务（标题、负责人、状态、截止、最近执行）与可指派成员，不读任务对话内容。
2. @Agent 给员工新建任务：任务写入成功，创建人为发起人并标注“经 dsh-work 助手”；群聊时间线出现结果卡片。
3. @Agent 新建或改派给 Agent 的任务：执行规则为“手动”，不自动执行。
4. @Agent 修改、改派、推进状态（含完成说明）：写入沿用任务服务的校验与事件，结果卡片列出改动并标注“经 某 Agent”。
5. 只读成员 @Agent 改任务、空间已归档、Agent 已停用、任务不属于本群：拒绝写入，不出卡片。
6. Agent 未开启开关、个人对话、系统运行：不装配任务工具；定时执行只装配读取工具。
7. 同一工具调用重放不会重复写入。

**验收：** Agent 只在发起人权限内读写本群任务；写入复用既有任务服务；结果以任务事件为准在时间线展示。

### PS-S6-P2 Agent 维护项目任务真实验收（项目空间 S6）

**优先级：** P2（发布前真实验收，单独留证）
**角色：** 群组负责人 A、普通成员 B、只读成员 C（三个真实账号，真实登录）；dsh-work 助手（开启“项目任务管理”的已发布版本）
**运行层级：** 真实 DSH Run/Attempt → Runtime Adapter → DSH，真实模型与平台默认时区；不得用 P0/P1 结果代替
**前置数据：** 一个群组，含 A、B、C 与升级到开启开关版本的 dsh-work 助手成员；群里已有 2～3 个员工任务（其中至少一个已完成）与一个由人创建、每天执行的 Agent 任务

1. **查询：** B 在群聊 @dsh-work 助手“现在有哪些没完成的任务？”。助手调用 `project_tasks_list`，回答与任务页签一致，不提及任务对话内容。
2. **新建员工任务：** B @助手“给 A 建一个任务：周五前提交周报”。任务页签出现该任务，负责人 A，截止日期为按平台时区换算的本周五；创建人为 B；群聊出现“B 创建了任务 · 经 dsh-work 助手”卡片。
3. **新建 Agent 任务：** B @助手“建一个任务让 dsh-work 助手每周整理库存周报”。任务的执行规则为“手动”，没有自动开始执行；助手回复说明需手动执行或修改规则。
4. **修改与改派：** A @助手“把周报任务截止改到下周一，改派给 B”。卡片列出“截止 原 → 新”“负责人 A → B”；任务对话系统记录标注“经 dsh-work 助手”。
5. **只改标题不动规则：** A @助手修改那个每天执行的 Agent 任务的标题。执行规则仍为“每天”。
6. **标记完成：** B @助手“周报完成了，备注已提交”。任务为已完成，卡片带完成说明。
7. **只读成员被拒：** C @助手“把任意任务标记完成”。没有任何写入，助手如实说明是只读成员、无法修改。
8. **定时执行只读：** 等那个每天执行的 Agent 任务定时触发一次。该次 Attempt 的工具清单只有 `project_tasks_list`、`project_task_get`。
9. **关闭开关：** 管理员发布关闭开关的新版本，负责人升级该成员后再 @助手建任务。工具不再装配，助手说明无法操作，不写入。

**留证：** 每步的群聊截图；对应 Run ID 与 Attempt 的 Manifest `tools`、工具调用记录（名称、参数摘要、结果或错误码）；`project_tasks` 的 `created_by` / `created_via` 与 `project_task_events` 的 `metadata.via`；第 7 步确认数据库无新增写入。按发布 / 验收流程归档，记录执行日期、环境、模型路由与 dsh-work 助手版本。
**通过标准：** 1～9 全部符合；任一步写入了不该写的数据、或卡片与数据库不一致，即为不通过。
